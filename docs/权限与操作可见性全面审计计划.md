## 1. 审计目标

建立一致的权限体验和服务端安全边界：用户只看到自己获准且当前业务状态允许的操作；直接调用未授权接口仍由后端拒绝；页面不以打开编辑抽屉后再报“没有执行该操作的权限”作为权限提示。

本计划区分三种事实：

- **现状**：代码中的演示角色授权、前端操作菜单和后端权限依赖。
- **建议基线**：根据岗位职责推导的最小权限建议，供逐项核对；不是已经确认的业务规则。
- **待验证**：真实浏览器、直接接口访问、记录归属和状态机边界的实测结果。

执行记录中的每项结论还应标注证据状态：**静态确认**（代码或配置位置）、**浏览器已验证**、**接口已验证**、**业务待确认**或**未覆盖**。静态配置只能证明代码/种子中的定义，不能替代当前数据库授权或运行时结果。

### 2.3 入口行为判定口径

矩阵中的“预期界面行为”按以下规则填写，并允许业务状态与权限分别给出结果：

- **隐藏**：用户没有该操作权限，或该操作不适用于当前角色；入口不出现。用于避免将无权操作呈现为可用能力。
- **禁用并说明原因**：用户有该操作权限，但当前业务状态或前置条件不满足；入口保留但不可执行，并提供明确原因。若状态信息敏感，则不展示原因中的敏感字段。
- **可用**：用户有权限、记录在其数据范围内且状态条件满足；界面入口可执行，服务端仍需再次校验。
- **服务端拒绝**：无权、越界或状态非法的直接请求被拒绝；按对象存在性泄漏风险返回 403 或 404，并记录适当审计信息。界面隐藏不能替代此检查。

对于因权限不足而隐藏的入口，测试仍需通过已知路由或直接 API 验证服务端拒绝；对于有权限但状态不允许的操作，则分别验证界面反馈和接口状态机拒绝。不得把“按钮隐藏”单独记为该权限控制通过。

## 2. 初步盘点发现

### 2.1 截图所示问题

1. 采购员打开化学品编辑抽屉后收到“没有执行该操作的权限”。这表明当前页面把编辑入口展示给用户，而后端 `master.chemicals.write` 校验拒绝了保存。权限缺失时应在列表/详情入口处隐藏编辑能力；后端 403 仍须保留。
2. 表格操作菜单出现“MSDS版本核对、修改、删除”。这三项含不同权限语义，不能仅由菜单统一开放：版本核对是否为只读检查、修改是否需要化学品维护权限、删除是否允许以及是否应受引用关系保护，都应分别定义。

### 2.2 静态代码盘点

- 演示账号授权定义了 12 个角色：系统管理员、采购经理、采购员、技术研发人员、仓库收货人员、质量人员、质量负责人、财务查看者、财务经办、财务经理、管理层查看者、供应商门户。
- `CellOperation` 至少出现在 13 个业务列表：化学品、产品规格、供应商、采购申请、询价、采购订单、到货、库存、质量验收，以及用户、角色、权限、部门。
- 化学品和供应商操作列定义了无统一角色权限过滤的编辑/删除项。采购申请、询价、订单等菜单已有部分状态判断，但状态判断不能替代角色权限判断；例如“草稿可编辑”还需同时满足用户有写权限及记录可操作范围。
- 初步静态盘点发现，自定义 `CellOperation` 仅按 `show !== false` 过滤，没有检查 `auth`；库存退货操作虽配置了 `auth: 'warehouse.inventory.return.write'`，当时该渲染器没有执行权限过滤。本轮已在渲染器加入 `auth` 权限码判断，并给化学品/供应商主数据新增入口及行编辑/停用操作加写权限条件；这些代码尚未经过本轮类型、构建或浏览器验证，不能视为缺陷已验收关闭。`VbenTableAction` 的 `auth` 检查是另一套组件实现，不能推定原表格菜单也受保护。
- 后端化学品、产品、供应商的增改删接口分别依赖对应 `master.*.write`；系统用户/部门/角色/权限也有服务端写权限依赖。多个业务控制器对操作使用 `require_permission`。后端权限拒绝是必要防线，但不能解决前端多显入口和抽屉误导。
- 当前化学品、产品、供应商接口把新增、修改和删除共用模块级 `*.write` 权限。该设计无法表达“可编辑但不可删除”等常见职责差异；目标矩阵需决定是否拆为 create/update/delete 或按明确业务动作拆分，并兼容现存授权迁移。
- 当前演示配置中，采购员不具有化学品和产品写权限、不具有采购申请/订单审批权限；但仍有 `master.suppliers.write`。该权限是否符合采购员实际职责需要业务确认，不能据截图擅自改成确定规则。
- 角色配置还显示采购经理持有库存领用/调拨/盘点审批、FIFO 成本出库及质量验收写权限；仓库角色持有 FIFO 成本出库权限；技术角色持有库存领用、调拨、盘点写权限。这些可能是业务特例，也可能是角色职责混配，列入核实清单，不能仅凭岗位名称直接撤权。
- 财务查看者被授予 `system.notifications.write`，当前含义是处理个人站内通知，不等同于财务单据写入；矩阵应按“操作对象”描述，避免把模块之外的个人自助动作误认为违反只读原则。

## 3. 建议的角色权限基线（需按业务流程确认）

“查看”表示可访问列表/详情；“办理”表示只允许处理本职业务记录及合法状态；“维护”表示主数据增改；“审批”表示独立审批权限。删除默认从日常角色中收紧，优先采用停用、作废、退回或撤回，并保留审计轨迹。

| 角色 | 建议工作范围 | 主数据修改/删除 | 业务办理 | 审批/复核 | 关键边界 |
|---|---|---|---|---|---|
| 系统管理员 | 平台全部模块 | 拥有所有主数据及系统配置权限，包含修改、删除 | 拥有全部业务操作权限 | 拥有全部审批/复核权限 | 全权限不绕过业务状态、数据完整性约束；所有关键操作留审计记录 |
| 采购经理 | 采购、供应商协作和采购流程管理 | 采购相关主数据可维护；删除限制 | 可办理申请、询价、订单 | 采购审批 | 与普通采购员分权；审批范围/金额待确认 |
| 采购员 | 采购申请、询价、订单执行 | 化学品/产品不应有修改删除；供应商维护待确认 | 可新建或编辑本人/授权范围内草稿，提交后按状态锁定 | 默认无审批 | 不允许删除已提交、已审批或已形成后续单据的记录 |
| 技术研发人员 | 化学品和产品技术资料维护 | 可维护化学品/产品；删除建议禁用或受引用约束 | 可处理技术相关任务 | 不默认承担采购/财务审批 | 是否允许改供应商等非技术字段需字段级确认 |
| 仓库收货人员 | 到货、库存、收发存及退货 | 不维护化学品/产品/供应商主数据 | 可确认收货、入库、出库、调拨、盘点等授权操作 | 仅开放明确分配的库存/退货审批 | 以仓库/库位范围隔离数据；冻结/成本出库单独审计 |
| 质量人员 | 质量验收与质量记录 | 不维护采购主数据 | 可检查资料、录入验收结果 | 默认不做最终复核 | 已定稿结果不可直接覆盖，复检须走状态机 |
| 质量负责人 | 质量验收管理 | 不维护采购主数据 | 可维护质量流程记录 | 可复核/批准质量报告 | 复核需与录入权限按需要分离 |
| 财务查看者 | 查看财务相关采购/库存/订单信息 | 不维护 | 只读 | 无 | 不显示写入、核验、付款或结算确认操作 |
| 财务经办 | 对账、发票、付款和结算录入 | 不维护业务主数据 | 可录入及编辑未提交的财务草稿 | 默认不批准本人经办事项 | 付款、结算与发票变更留审计轨迹 |
| 财务经理 | 财务全流程管理 | 不维护业务主数据 | 可管理财务流程 | 可核验发票、批准付款/结算 | 经办人与审批人分离规则待确认 |
| 管理层查看者 | 运营看板和跨模块经营查询 | 不维护 | 只读 | 无 | 看板可见不等于底层操作权限；敏感字段另行核验 |
| 供应商门户 | 仅查看分配给本供应商的订单并确认 | 不访问内部主数据 | 仅处理本供应商订单确认 | 无内部审批权限 | 必须以供应商账号绑定关系过滤数据，防止跨供应商读取 |

除系统管理员全权限基线已明确外，此基线只用于发现差异，不会将其他角色的“写”进一步假定为“修改、删除、批量操作、审批”一揽子能力。每个操作均要映射到明确权限码和业务状态。对管理员，“全权限”指所有已定义的应用功能权限与可见操作；业务状态、记录关联完整性、租户/供应商对象归属等仍由服务端规则执行。若确需人工越过正常状态机，应新增单独的受控例外动作、填写原因并留审计，而不是隐式跳过规则。

## 3.1 结合通行安全实践的复核结论

参考 NIST RBAC 对用户/角色/权限关系及静态、动态职责分离的定义，以及 OWASP 关于默认拒绝、每次请求校验、最小权限和定期清理权限膨胀的建议，本方案方向正确，但需明确以下边界：

1. **管理员全权限是应用权限基线，不等于数据库/状态机的万能绕过。** 当前 `SYS_ADMIN` 演示角色确实从权限目录取得全部权限码；应在矩阵里将这点作为已知配置事实，同时另测所有管理员页面按钮与 API。删除被引用对象、跨供应商读取、质量定稿覆盖等完整性约束仍需显式定义。
2. **审批职责分离看“同一人对同一笔业务的动作历史”，不能只看角色名。** 财务经理和质量负责人拥有审批/复核权限，同时也有部分写权限；如果同一账号可既经办又审批，单纯拆成两个角色并不构成 maker-checker。应验证后端是否阻止本人审批/复核本人提交的同一记录，并验证多角色叠加不会绕开约束。
3. **本项目需要 RBAC + 对象属性/关系约束。** 供应商门户要绑定供应商主体；仓库业务可能按仓库/库位隔离；采购申请、财务单据可能按创建人/部门范围限制。仅有 `*.read` 或 `*.write` 只能表达功能权限，不能代替记录级过滤。
4. **权限粒度要与界面动作对应。** 现有主数据 `*.write` 同时保护 create/update/delete，采购业务的 write 码也可能覆盖提交等动作。若业务要求编辑与删除不一致，应拆分服务端权限并同步前端；仅在浏览器隐藏“删除”而后端仍允许同一角色调用删除接口，不算完成。
5. **角色授权需有周期性复核和例外记录。** 给权限应可说明岗位需要；对高危权限（删除、审批、付款、成本调整、权限管理）记录责任人、复核周期和例外依据，防止角色长期累积权限。

以上是基于公开安全框架的审计原则，不是对化工行业所有公司的统一岗位配置标准。具体授权仍由本项目真实流程、组织规模和内部控制要求决定。

## 4. 全面审计范围与产物

### A. 角色与授权源

- 对照数据库当前生效角色授权、演示账号脚本默认授权、角色管理页面可配置授权及所有权限码。
- 记录角色继承/多角色叠加、撤销权限、账号禁用、未登录访问的最终有效权限计算方式。
- 输出逐角色权限码清单，标出“代码默认值”和“当前数据库值”不一致的情况。

### B. 功能入口与操作清单

逐路由/页面检查侧边菜单、快捷入口、列表按钮、行菜单、批量工具栏、详情页、编辑抽屉、弹窗、导入导出/下载、附件、AI 工具、通知和状态流转按钮。每个入口登记：角色、权限码、业务状态条件、记录范围条件、预期显示/禁用/隐藏行为。

特别区分新增、查看、编辑、删除、停用、提交、撤回、审批、复核、确认、导入、导出、下载、批量处理；确认每个动作是否有独立服务端权限码，禁止只拆前端菜单而保留后端共享写权限。

### C. 服务端授权与数据范围

- 将每个前端操作映射到 API 路由、HTTP 方法、权限依赖和状态机服务规则。
- 检查列表/详情、附件下载、搜索、统计、导出和 AI 检索是否发生越权数据泄漏。
- 检查本人/部门/仓库/供应商等数据范围；RBAC 功能权限通过不代表对象级授权也正确。
- 对关键操作检查审计日志、不可逆操作保护、引用关系限制和重复请求行为。

### D. 浏览器角色矩阵

使用 12 种演示角色逐一登录。每个角色至少覆盖：侧边菜单、代表性列表、无权操作隐藏、可权操作可用、工作流状态变化后按钮更新，以及直接访问受限页面。每个模块挑选只读、写入、审批和高风险操作做正反例；高危业务再覆盖不同记录归属与状态。

浏览器检查不能替代 API 检查；API 403 也不能替代用户界面的入口检查。测试数据不得执行真实付款、真实供应商通知或不可逆生产操作。

### E. 验收与交付

- 角色 × 页面 × 操作 × 权限码 × 状态 × 数据范围矩阵，至少包含：当前授权来源/值、目标值及确认人、入口位置、预期界面行为、API 路由与 HTTP 方法、后端权限依赖、对象范围/状态条件、正向与负向用例、实际结果、证据链接、执行日期/账号角色、未决问题和覆盖状态。
- 每个矩阵行分别记录浏览器与接口证据；证据应可复现并指向截图/录屏、请求与响应摘要、相关代码或配置位置。不得在文档或截图中保存密码、令牌等凭证。
- 前端显隐/禁用策略和后端拒绝策略逐项一致。
- 测试账号可复现；权限变更无需用户重新登录或有清晰的刷新策略。
- 至少验证：单角色、多个角色叠加、权限撤销后的现有会话、账号禁用/未登录访问，以及权限目录或角色授权变更后的生效时机；记录缓存、令牌或重新登录要求。
- 更新本计划的审计结果，并在实质权限变更完成后同步更新 `docs/项目介绍与成果（STAR）.md` 及直接相关业务文档；只写已验证能力。

## 5. 分阶段执行计划

| 阶段 | 工作 | 交付/退出条件 |
|---|---|---|
| 0. 固定授权快照 | 导出 12 个演示角色的有效权限码，与权限目录、种子脚本、数据库现值比较；记录环境、快照时间、账号映射及授权生效方式 | 可复查的角色授权差异表；确认正在测试的数据库及账号映射；无法读取的来源明确标为未验证 |
| 1. 建立操作资产清单 | 扫描路由、菜单、按钮、表格操作、弹窗字段和批量能力；逐项映射 API 权限与状态约束，并记录数据范围 | 全量操作台账；每项有稳定标识、页面入口、权限码、状态、数据范围及当前证据状态 |
| 2. 定义目标矩阵 | 以第 3 节建议为起点，与现有业务流程逐岗位核定新增/编辑/删除/审批/导出/对象范围；明确隐藏、禁用和可用口径；确认是否拆分粗粒度 `write` 权限及迁移方案 | 经业务责任人确认的目标授权矩阵；高危例外有责任人和依据；待决项不进入自动授权变更 |
| 3. 修正前端显隐与交互 | 统一权限判断；无操作权限时隐藏入口；仅因状态/前置条件不满足时按矩阵禁用并说明；批量操作、详情按钮、字段编辑状态同步处理 | 无权角色看不到入口；有权限者在非法状态不能执行且反馈符合矩阵；组件 `auth` 已用正反例确认真实生效 |
| 4. 校验后端与对象范围 | 补齐或修正 API 权限码、状态机、本人/组织/仓库/供应商范围；检查下载、导出、AI 检索旁路 | 负向请求返回 403/404；合法请求按角色及对象范围通过；无数据泄漏 |
| 5. 全角色浏览器与接口回归 | 按最终矩阵登录每个演示角色，对菜单、行操作、批量动作、状态和直接 API 做可重复检查；覆盖本人/他人、组织/仓库/供应商归属及授权撤销场景 | 全角色矩阵无未解释差异；每行均有浏览器和接口结果或明确未覆盖理由；缺陷关闭或登记风险/例外 |
| 6. 文档与交付 | 同步 STAR 展示文档及受影响功能说明，记录测试日期、账号角色、范围、结果和未覆盖项 | 文档仅陈述已实现且已验证的权限控制；留下后续业务决策项 |

## 6. 采购员的暂定操作规则

在业务负责人确认前，建议先按最小权限评估：

- **化学品、产品规格、供应商主数据**：可查看；不显示新增、修改、删除、启停等维护入口。截图中化学品“修改/删除”应隐藏；保存接口仍由后端拒绝。供应商写权限现虽已授予采购员，但需确认是否仅限履约信息/联系人，还是应完全撤销主数据写权限。
- **采购申请、询价、采购订单**：可处理自己或授权范围内的未提交草稿；提交后锁定普通编辑。采购员无审批权限，不能看到“审批通过/驳回”。是否能撤回、取消、作废按状态机单独配置。
- **删除**：一般采购员不应删除已提交或被引用记录。草稿是否可删除也建议优先使用“撤销/作废”留痕，并由业务负责人决定是否需要硬删除入口。
- **批量、附件和导出**：逐项确认权限，不因可以查看列表就自动开放下载、导出或批量改状态。

后续更新审计结果时，每项应使用统一记录格式，避免只写“通过/失败”而缺少复现条件：

| 字段 | 记录内容 |
|---|---|
| 用例标识 | 角色、页面/入口、操作及用例编号 |
| 环境与身份 | 环境/数据库标识、测试账号角色、单角色或角色组合；不记录密码和令牌 |
| 前置条件 | 记录归属、业务状态、权限快照时间及必要数据准备 |
| 预期结果 | 界面行为、接口状态码/业务结果、数据范围和审计要求 |
| 实际结果 | 浏览器与接口分别记录；失败时记录复现步骤及影响范围 |
| 证据与状态 | 截图/录屏/请求摘要/代码位置链接、执行日期、验证人及证据状态 |
| 后续处理 | 缺陷编号、业务决策责任人、风险例外或未覆盖原因 |

未能执行的用例应标为“未覆盖”并说明阻塞条件，不得按通过处理。环境、账号或数据无法确认时，结论保持待验证。

## 8. 外部依据

- [NIST RBAC FAQ](https://csrc.nist.gov/Projects/Role-Based-Access-Control/faqs)：RBAC 的核心关系，以及层级、静态职责分离和动态职责分离模型。
- [NIST SP 800-171 Rev. 3，3.1.4 Separation of Duties / 3.1.5 Least Privilege](https://nvlpubs.nist.gov/nistpubs/SpecialPublications/800-171r3/NIST.SP.800-171r3.html)：识别需要分离的职责、定义对应授权，并定期审查角色权限。
- [OWASP Authorization Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html)：默认拒绝、每次请求验证权限、最小权限及部署后定期复核权限膨胀。
- [NIST ABAC 定义与考虑事项](https://csrc.nist.gov/pubs/sp/800/162/upd2/final)：访问决策可结合用户、对象和环境属性，支持记录/主体关系范围；用于解释为何角色权限还需对象级规则。
