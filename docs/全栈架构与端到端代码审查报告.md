## 零、架构亮点与防护完备模块（无明显缺陷）

在展开问题清单前，以下核心机制在源码中已具备扎实的工程实现与防护，不重复报告：

1. **数据库任务队列与防脑裂隔离机制**（`backend/app/modules/task_queue/service.py`、`worker.py`、`execution.py`、`processes.py`）：
   - 使用 `with_for_update(skip_locked=True)` 抢占任务，通过 `TaskExecution.fencing_token`、`delivery_generation` 与 `TaskResourceLock` 防止陈旧 Worker 写回覆盖新状态。
   - 结合操作系统级进程树监管（Windows Job Object `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` / Linux `PR_SET_PDEATHSIG(SIGKILL)`），当跨节点租约过期且无法证明旧进程已终止时，将任务置为 `FAILED (RECOVERY_ISOLATION_REQUIRED)` 并保留 `TaskResourceLock` 阻止脑裂并发重入。
2. **Agent Runtime 乐观锁、取消屏蔽与双层超时治理**（`backend/app/modules/ai/agent_runtime.py`、`tool_sql_timeout.py`）：
   - 通过 `AIAgentTask.revision` 乐观锁与 `status == "RUNNING"` 状态断言保障单步推进原子性；在捕获 `asyncio.CancelledError` 时使用 `await asyncio.shield(worker)` 等待工作协程安全收尾，避免同步 SQLAlchemy `Session` 被并发访问或遗留半途事务。
   - 具备任务快照 RBAC 与实时 RBAC 双重校验（`agent_runtime.py:_check_trace_access`，第 462–492 行）。
3. **事务提交后缓存版本轮转**（`backend/app/core/cache.py`）：
   - 通过 SQLAlchemy `before_flush`、`do_orm_execute` 与 `after_commit` 事件监听器，仅在事务真正 `commit` 后轮转 `cache-version:ai_history`，并在脏会话期内自动旁路缓存读取。
4. **受控 Text2SQL 与 AST/权限范围强校验**（`backend/app/modules/ai/text2sql.py`）：
   - 模型仅输出受控 `QueryPlan` JSON，由 `_validate_plan`（第 943–1060 行）校验 RBAC 权限、模板白名单与字段白名单，再由 SQLAlchemy ORM 注入部门/仓库范围谓词并通过 `_validate_scoped_statement`（第 1063–1142 行）二次校验，无拼接 SQL 注入面。
5. **库存出入库锁序设计与财务对账防篡改快照**（`backend/app/modules/inventory/quality_hold.py`、`backend/app/modules/finance/reconciliation_items.py`、`invoice_matches.py`）：
   - 领用、调拨、盘点、退货与质检冻结统一遵循“批次 (`lock_available_batches`) → 库存余额 (`InventoryBalance` 固定元组排序) → FIFO 成本层 (`InventoryCostLayer`)”的加锁顺序，避免循环死锁。
   - 财务对账采用确定性 `basis_hash` 锁定订单/到货/退货快照，并在提交、匹配、复核三阶段强制执行职责分离（SoD）。
6. **前端 Markdown 渲染 XSS 防护与文件上传基础安全防线**（`frontend-design/apps/web-chemicalops/src/utils/markdown.ts`、`backend/app/modules/files/service.py`）：
   - `renderMarkdownToSafeHtml`（`markdown.ts:100-157`）先做全量 HTML 转义再开放受控标签与 `http(s)://` 链接；文件上传强制校验扩展名、MIME、魔数签名（`files/service.py:_validate_file_signature`，第 98–114 行）及沙箱响应头。

### 【严重 (Critical)】

#### 1. MySQL `REPEATABLE READ` 下 `with_for_update()` 配合 `selectinload()` 导致子表明细读取旧 MVCC 快照，引发并发超额收货、超额发货与丢失更新

- **问题位置：**
  - `backend/app/modules/deliveries/crud.py`：`get_by_id`（第 10–16 行）、`get_order`（第 49–57 行）
  - `backend/app/modules/deliveries/service.py`：`create_delivery`（第 67–85 行）、`receive_delivery`（第 148–189 行）
  - `backend/app/modules/supplier_portal/service.py`：`_require_order`（第 207–216 行）、`update_expected_delivery`（第 266–278 行）、`create_shipment_notice`（第 315–336 行）
- **证据与触发条件：**
  - 在 `deliveries/crud.py:49-57` 中：
    ```python
    def get_order(db: Session, po_id: int, *, for_update: bool = False) -> PurchaseOrder | None:
        from app.modules.purchase_orders.crud import detail_options
        statement = select(PurchaseOrder).options(*detail_options()).where(PurchaseOrder.id == po_id)
        if for_update:
            statement = statement.with_for_update()
        return db.scalar(statement)
    ```
  - 在 `deliveries/service.py:151-189`（`receive_delivery`）中：
    ```python
    delivery = get_delivery(db, user, delivery_id, for_update=True)
    if delivery.status != "IN_TRANSIT":
        raise BusinessValidationError("只有运输中的到货单可以确认收货")
    order = crud.get_order(db, delivery.po_id, for_update=True)
    ...
    for item in delivery.items:
        ...
        if po_item.received_quantity + item.actual_quantity > po_item.order_quantity:
            raise BusinessValidationError(f"到货明细 {item.line_no} 超出订单剩余未收数量")
        po_item.received_quantity += item.actual_quantity
    ```
  - **复现路径：**
    1. 同一采购订单 `PO-1`（明细 `order_quantity = 50, received_quantity = 0`）下有两张运输中到货单 `D1`（实收 30）与 `D2`（实收 30）。
    2. 两个请求同时调用 `POST /api/v1/deliveries/{D1}/receive` 与 `POST /api/v1/deliveries/{D2}/receive`。
    3. 两个请求在进入路由前的依赖项 `get_current_user` 中已开启 MySQL InnoDB `REPEATABLE READ` 事务并建立初始快照（此时 `po_item.received_quantity = 0`）。
    4. 请求 1 获得 `PurchaseOrder` 主行锁，将 `po_item.received_quantity` 更新为 `30` 并提交。
    5. 请求 2 随后获得 `PurchaseOrder` 主行锁，但 `selectinload(PurchaseOrder.items)` 发出的是独立第二条普通 `SELECT ... FROM purchase_order_items WHERE po_id IN (...)`（**既无 `FOR UPDATE`，也无 `populate_existing=True`**），在 MySQL `REPEATABLE READ` 下直接读取请求 2 事务启动时的旧快照 `received_quantity = 0`。
    6. 请求 2 判断 `0 + 30 <= 50` 通过，将 `po_item.received_quantity` 写成 `0 + 30 = 30` 并生成 30 单位批次入库。
- **根因分析：**
  - SQLAlchemy 的 `selectinload` 不会继承父查询的 `with_for_update()`。项目在 `purchase_orders/followup_service.py:40-44`（`_lock_order_items`）和 `inventory/crud.py:196-205`（`_locked_request`）中已专门针对该问题做了当前读加锁修复，但 `deliveries` 和 `supplier_portal` 模块仍直接依赖 `selectinload` 的快照读，且 `receive_delivery` 未校验 `order.status in {"ORDERED", "PARTIAL"}`。
- **影响范围：**
  - 并发确认收货导致超额收货入库、`po_item.received_quantity` 丢失更新（累计入库 60 而订单显示已收 30），进而触发下游财务对账 `basis_hash` 数量不一致告警；并发创建发货通知同样可突破订单剩余未收数量。
- **修复方案：**
  - 在 `deliveries/crud.py` 的 `get_order(..., for_update=True)`、`get_by_id(..., for_update=True)` 以及 `supplier_portal/service.py` 的 `_require_order(..., for_update=True)` 中，主单查询加 `.with_for_update().execution_options(populate_existing=True)`，随后显式对 `PurchaseOrderItem` / `DeliveryItem` 执行带 `.with_for_update().execution_options(populate_existing=True)` 的查询并通过 `set_committed_value` 挂载；在 `receive_delivery` 中补充 `order.status in {"ORDERED", "PARTIAL"}` 校验。
- **验证方式：**
  - 编写双线程并发收货集成测试：对同一订单（`order_quantity = 50`）下的两张到货单（各 `30`）并发调用 `receive_delivery`，断言一笔成功、一笔返回 400 `超出订单剩余未收数量`，且最终 `received_quantity == 30`。
- **结论可信度：** 已确认。

#### 2. 财务付款仅校验“单笔付款金额 <= 已复核发票总额”，未校验“累计付款金额 <= 已复核发票总额”，可通过拆单实现超额无票付款

- **问题位置：**
  - `backend/app/modules/finance/service.py`：`create_payment`（第 335–346 行）、`approve_payment`（第 372–389 行）
- **证据与触发条件：**
  - 在 `finance/service.py:342-345`（`create_payment`）中：
    ```python
    if _sum_payments(db, reconciliation.id) + data.amount > reconciliation.total_amount:
        raise BusinessValidationError("付款累计金额不能超过对账应付总额")
    if _sum_invoices(db, reconciliation.id, verified_only=True) < data.amount:
        raise BusinessValidationError("人工复核通过的发票金额不足，不能发起本次付款")
    ```
  - 在 `finance/service.py:387-388`（`approve_payment`）中：
    ```python
    if _sum_invoices(db, reconciliation.id, verified_only=True) < payment.amount:
        raise BusinessValidationError("人工复核通过的发票金额不足，不能审批付款")
    ```
  - **复现路径：**
    1. 某已确认对账单 `total_amount = 1000`，仅有一张人工复核通过的发票 `amount = 500`（`_sum_invoices(verified_only=True) == 500`）。
    2. 发起第 1 笔付款申请 `amount = 500`：`_sum_payments(0) + 500 <= 1000` 且 `500 >= 500`，创建并审批通过。
    3. 再发起第 2 笔付款申请 `amount = 500`：`_sum_payments(500) + 500 <= 1000`，而发票校验仅比较 `500 < 500`（单笔 `data.amount`），再次通过创建与审批，最终在仅有 500 元有效发票的情况下支付了 1000 元并完成结算。
- **根因分析：**
  - 已复核发票金额 `_sum_invoices(db, reconciliation.id, verified_only=True)` 的比较右值误写为单笔付款金额 `data.amount` / `payment.amount`，而非对账单下所有非驳回付款申请的累计金额。
- **影响范围：**
  - 财务付款申请（`POST /api/v1/finance/payments`）与付款审批（`POST /api/v1/finance/payments/{payment_id}/approve`），破坏“见票付款、票款一致”的核心内控约束。
- **修复方案：**
  - 在 `create_payment` 中令 `total_requested = _sum_payments(db, reconciliation.id) + data.amount`，校验 `_sum_invoices(db, reconciliation.id, verified_only=True) < total_requested`；在 `approve_payment` 中同样校验已核验发票总额不少于累计有效付款总额。
- **验证方式：**
  - 编写单元测试：对 `total_amount = 1000`、已复核发票总额 `500` 的对账单连续创建两笔 `500` 的付款单，断言第二笔抛出 `BusinessValidationError("人工复核通过的发票金额不足，不能发起本次付款")`。
- **结论可信度：** 已确认。

#### 3. 站内通知 `notify_users` 按角色码全局广播业务详情，导致跨部门、跨仓库敏感业务数据越权泄露

- **问题位置：**
  - `backend/app/modules/notifications/service.py`：`notify_users`（第 22–79 行）
  - 调用方：
    - `backend/app/modules/jobs/service.py`：`scan_overdue_deliveries`（第 96–111 行）、`scan_expiring_inventory`（第 150–163 行）、`scan_pending_quality_acceptances`（第 212–225 行）、`scan_low_inventory`（第 329–343 行）
    - `backend/app/modules/deliveries/service.py`：`receive_delivery`（第 154–169 行）
    - `backend/app/modules/quality_acceptances/service.py`：`submit_result`（第 265–282 行）
- **证据与触发条件：**
  - 在 `notifications/service.py:22-48` 中，`notify_users` 默认 `exclude_scoped: bool = False`，当传入 `role_codes` 时直接查询全系统拥有该角色的所有活跃用户：
    ```python
    stmt = (
        select(User.id)
        .join(UserRole, UserRole.user_id == User.id)
        .join(Role, Role.id == UserRole.role_id)
        .where(User.status == "ACTIVE", Role.status == "ACTIVE", Role.role_code.in_(codes))
    )
    ```
  - 调用方将包含订单号、到货单号、产品名称、批次号、缺货数量、质检不合格结论等敏感业务数据的 `description` 作为 `content` 传给 `role_codes=["PROCUREMENT_MANAGER", "WAREHOUSE", "QUALITY"]`。
- **根因分析：**
  - 业务查询接口通过 `UserDepartmentScope`（部门范围）和 `Warehouse.manager_id`（仓库范围）实现了数据隔离，但站内通知分发层仅按 `Role.role_code` 广播，未过滤接收人的部门范围或仓库归属。
- **影响范围：**
  - 受限范围的采购主管、仓管员、质检员在右上角通知中心（`GET /api/v1/notifications`）会收到其他部门采购订单、其他仓库到货缺货及库存批次预警的完整业务详情文本。
- **修复方案：**
  - 为 `notify_users` 增加 `department_id: int | None = None` 与 `warehouse_id: int | None = None` 过滤参数（或按目标业务单据的可见范围解析接收人 ID 列表），仅向对该部门/仓库具备管辖权的用户生成通知。
- **验证方式：**
  - 构造仅管理“仓库 A”的仓管员账号，在“仓库 B”触发到货短缺或临期批次扫描，验证“仓库 A”仓管员不会收到该条 `SysNotification`。
- **结论可信度：** 已确认。

- **修复方案：**

#### 5. 文件权限体系与业务附件绑定断链：内部角色无法下载供应商上传的质量资料，且质检报告/报价源文件/任务评论附件缺少权限校验与 `SysFileAttachment` 绑定

- **问题位置：**
  - `backend/app/modules/files/service.py`：`RESOURCE_READ_PERMISSIONS`（第 42–50 行）、`_can_access_resource_instance`（第 242–247 行）、`_check_file_access`（第 290–313 行）
  - `backend/app/modules/supplier_portal/service.py`：`create_quality_document`（第 409–428 行）
  - `backend/app/modules/quality_acceptances/service.py`：`submit_result`（第 158 行）
  - `backend/app/modules/operation_exceptions/service.py`：`create_comment`（第 661–675 行）
  - `backend/app/modules/rfqs/service.py`：`create_quote`（第 178–198 行）
- **证据与触发条件：**
  1. **供应商质量文件内部不可读：** 供应商在 `create_quality_document`（第 421–425 行）上传 COA/MSDS 时，仅写入 `SysFileAttachment(resource_type="SUPPLIER_QUALITY_DOCUMENT", resource_id=record.id)`。而在 `files/service.py:49, 242-247` 中，`SUPPLIER_QUALITY_DOCUMENT` 要求当前用户拥有 `supplier.portal.quality.read` 权限且在 `SupplierPortalAccount` 中绑定了该 `supplier_id`。导致内部质检员（`QUALITY`）、采购员（`PURCHASER`）、仓管员（`WAREHOUSE`）调用 `GET /api/v1/files/{file_id}/download` 下载供应商上传的 COA/MSDS 时全部返回 404。
  2. **质检报告、评论附件、报价源文件未写入 `SysFileAttachment` 且漏校验文件访问权：**
     - `quality_acceptances/service.py:158` 直接赋值 `acceptance.report_file_id = data.report_file_id`，既未检查文件是否存在（传入不存在的 `report_file_id` 会在 `commit` 时抛出未捕获的外键 `IntegrityError` 导致 HTTP 500），也未校验当前用户对该文件的访问权，更未写入 `SysFileAttachment(resource_type="QUALITY_ACCEPTANCE")`。
     - `operation_exceptions/service.py:667-670`（`create_comment`）仅检查 `db.get(SysFile, data.attachment_file_id) is None`，未校验当前用户是否有权引用该 `attachment_file_id`，也未写入 `SysFileAttachment`。
     - 由于 `files/service.py:_check_file_access`（第 290–313 行）对非上传者本人要求必须存在匹配的 `SysFileAttachment` 记录（第 311 行：`if linked_resources or (value.access_level == "INTERNAL" and value.uploader_id != user.id): raise ResourceNotFoundError`），导致其他有权查看该质检单、报价单或异常任务的同事/主管在下载这些文件时均收到 404。
- **根因分析：**
  - 业务模块通过外键列（`report_file_id`、`source_file_id`、`attachment_file_id`）关联文件，而文件下载鉴权统一依赖 `sys_file_attachments` 多态关联表及 `RESOURCE_READ_PERMISSIONS`，两边未形成闭环。
- **影响范围：**
  - 供应商质量文件下载、质检报告下载、询价报价单源文件下载、异常任务评论附件下载及提交。
- **修复方案：**
  - 在 `files/service.py:_can_access_resource_instance` 中，允许对 `SUPPLIER_QUALITY_DOCUMENT` 关联的 `po_id`（采购订单可读）或 `delivery_id`（到货单/质检单可读）有访问权的内部角色读取；

### 2. Top 3 优先修复问题

1. **[严重] 修复 `deliveries` 与 `supplier_portal` 在 MySQL `REPEATABLE READ` 下 `with_for_update()` + `selectinload()` 的子表旧快照并发漏洞（问题 1）**：防止并发确认收货/发货导致超额入库与订单已收数量丢失更新。
2. **[严重] 修复财务付款对已复核发票金额的累计校验漏洞（问题 2）**：在 `create_payment` 与 `approve_payment` 中校验“累计有效付款总额 <= 已复核发票总额”，堵住拆单超额无票付款风险。
3. **[严重/高] 修复站内通知跨部门/仓库越权广播（问题 3）、停用供应商门户访问绕过（问题 4）及文件附件权限闭环断裂（问题 5）**：收口多角色数据隔离与文件访问控制边界。

### 3. 主要技术债务与改进建议

1. **统一 MySQL `REPEATABLE READ` 下的主子表加锁范式**：将 `inventory/crud.py:_locked_request`（第 196–205 行）与 `purchase_orders/followup_service.py:_lock_order_items`（第 40–44 行）的“主表 `FOR UPDATE` + 子表显式 `FOR UPDATE` + `populate_existing=True` + `set_committed_value`”沉淀为 `app/core/db.py` 的通用辅助函数，禁止在 `for_update=True` 路径下依赖 `selectinload` 读取可变子表。
2. **统一单据编号生成与终态唯一键释放机制**：用 `f"TEMP-{prefix}-{uuid4().hex[:12]}"` 替换全部残留的 `"TEMP"` 与秒级时间戳占位符；对含业务终态（`CANCELLED`、`VOIDED`）的唯一约束统一采用虚拟生成列（仅对活跃状态非 NULL）。
3. **清理 `async def` 中的同步阻塞 I/O 与长事务**：遵循“短事务读取 → `commit()` 释放连接 → `await` 外部 LLM/解析服务 → 开启新短事务重验权限并落库”的三段式模式，避免慢外部 I/O 拖垮连接池与事件循环。
4. **前后端枚举与工具字典单一事实来源**：将 Agent 的 12 个工具元数据与 11 类 Action Proposal 元数据集中维护并建立契约测试，避免后端新增工具后前端回退显示异常文案。
