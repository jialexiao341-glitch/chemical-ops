# ChemicalOps 数据库字段设计

版本：v0.3  
适用数据库：MySQL 8.0+

本文是 `database/schema.sql` 的字段字典和关系说明。SQL 中的 `COMMENT` 是最终的数据库级字段说明；本文补充可空规则、索引意图和跨表约束，供后端 ORM、接口 Schema 和 Alembic migration 对照使用。

## 1. 统一约定

| 约定 | 规则 |
|---|---|
| 主键 | 业务表使用 `BIGINT UNSIGNED AUTO_INCREMENT`；纯关联表使用双方外键组成联合主键 |
| 时间 | `DATETIME(3)`；所有核心表有 `created_at`、`updated_at`，事件/日志表只有 `created_at` |
| 金额/数量 | `DECIMAL(18,6)`，金额必须同时有 `currency_code`，数量必须同时有 `unit_id` |
| 编号 | `*_no` 是对外业务编号，唯一；不可用自增 ID 代替业务编号 |
| 状态 | 使用 `VARCHAR(20/32)` 保存状态码，状态流转由服务层枚举校验；保留数据库 CHECK 保护数值和日期 |
| 可空 | `NULL` 表示“尚未提供/尚未确认/对该业务不适用”；空字符串不作为缺省值 |
| 快照 | 订单、报价、询价等单据中的 `*_snapshot`/名称字段保留当时文本，防止主数据变化改写历史 |
| 文件 | 文件内容放 MinIO，`sys_files` 只保存元数据和对象键；业务表只保存文件外键 |
| JSON | 只用于不稳定的扩展数据、AI 快照和检测结果；需要筛选/排序/统计的字段必须拆成普通列 |
| 删除 | 业务历史表不做物理删除；主数据通过 `status` 停用。若要删除，只允许删除没有业务引用的数据 |

### 1.1 可空规则总览

- 非空字段是创建该记录所需的最小业务事实，例如名称、数量、单位、状态、操作者和父单 ID。
- 可空字段主要有四类：待确认信息（`product_id`、`approver_id`）、流程后置时间（`approved_at`、`received_at`）、业务可选资料（电话、地址、备注、附件）和外部来源不一定存在的关联（公开行情的 `supplier_id`）。
- `UNIQUE` 字段允许 `NULL` 重复，这是 MySQL 的标准语义；因此 CAS、邮箱、统一信用代码等“有值时唯一、无值时允许缺失”的字段均使用可空唯一列。
- 对于“数值和单位必须成对出现”的字段，服务层必须同步校验。例如 `moq_quantity` 有值时必须有 `moq_unit_id`；SQL 已约束数值非负，但未用跨字段 CHECK 替代服务层的单位一致性校验。

## 2. 系统、文件和基础字典

### `sys_departments` 部门表

| 字段 | 类型 | 可空 | 说明 |
|---|---|---:|---|
| `id` | BIGINT UNSIGNED | 否 | 部门主键 |
| `parent_id` | BIGINT UNSIGNED | 是 | 上级部门；根部门为空，自关联 |

| `ai_tool_calls` | `(tool_name,status,created_at)` | 工具成功率和失败分析 |
| `sys_audit_logs` | `(resource_type,resource_id,created_at)` | 资源变更审计 |

不建议为所有外键机械加索引：MySQL 会为外键检查创建所需索引，但列表页、时间范围和状态组合才是本系统的主要查询路径，联合索引按左前缀设计。

## 10. 必须由服务层保证的跨表约束

数据库 FK 能保证“引用存在”，但以下规则需要在事务服务中校验：

1. `rfq_items.source_request_item_id` 必须属于 `rfqs.source_request_id` 对应的采购申请。
2. `supplier_quotes.supplier_id` 必须是 `rfq_suppliers` 中被邀请的供应商；报价明细的 `rfq_item_id` 必须属于该报价的询价单。
3. `quote_comparisons.selected_quote_id` 必须属于当前比较的 `rfq_id`；选定报价供应商必须与订单供应商一致。
4. `purchase_orders.source_quote_id/source_comparison_id/source_request_id` 的来源链路必须一致，且只有审批通过的报价/比较结果可生成正式订单。
5. `purchase_order_items.source_quote_item_id` 必须属于订单来源报价，订单行的产品、单位、供应商必须匹配来源明细。
6. `deliveries.supplier_id` 必须与 `purchase_orders.supplier_id` 一致；到货明细的 `po_item_id` 必须属于该订单。
7. `operation_exceptions` 至少填写一个具体业务外键，并使其与 `source_type/source_id` 一致。
8. `moq_quantity` 与 `moq_unit_id`、数量与单位必须成对出现；不同量纲不能直接比较。
9. 每个供应商最多一个 `supplier_contacts.is_primary=1`；每个订单/申请只能有一个当前审批节点。
10. 订单、申请、报价和 AI 动作的状态变化必须与对应事件、审批和 `sys_audit_logs` 在同一业务事务中写入。

## 11. 建议的 migration 拆分顺序

1. 系统基础：部门、用户、角色、权限、关联表。
2. 文件与字典：`sys_files`、`md_units`。
3. 主数据：分类、化学品、产品、参数、替代关系。
4. 供应商：供应商、联系人、资质、供应商产品、评价。
5. 采购前置：采购申请及审批、询价及供应商邀请、报价及报价明细、报价比较。
6. 订单执行：采购订单及审批/事件、到货及验收、异常任务。
7. 知识与分析：知识文档、片段、历史价格、预测。
8. AI 与审计：会话、消息、运行、步骤、工具调用、动作审批、审计日志。

生产环境不要直接执行 SQL 文件中的 `DROP TABLE` 段；该文件定位为全新环境初始化脚本，生产结构变更必须拆成 Alembic migration 并先备份数据。
