# ChemicalOps：化工采购运营与智能协同平台

> 项目周期：2026.09—至今｜职责：全栈开发｜整理日期：2026-10-09
> 定位：全栈业务平台 + 场景化 Agent。目标是面向中小型化工企业的采购履约与运营协同平台，以确定性的业务服务为核心，融合 AI Agent、RAG 和自动化工作流。以下区分当前成果与后续规划；个人职责按实际参与范围表述。

## 项目简介

面向化工企业采购履约与运营协同场景，基于 **FastAPI + Vue 3** 构建覆盖采购申请、询价报价、订单履约、质量验收、库存及财务对账的全栈业务平台，融合 **Agent 工作流与 RAG 知识检索**，支持经营数据查询、化学品资料检索、采购辅助分析及草稿预览确认。

**技术栈：** Python、FastAPI、SQLAlchemy、Vue 3、TypeScript、MySQL、RabbitMQ、LangGraph、Qdrant、MinIO、Docker。

本次整理依据截至 2026-10-09 的工作区实现与专项验证记录，指标的日期、范围及来源见下方 Result。当前成果来自开发环境、模拟业务和专项验证；完整异常闭环、生产交付和真实角色试点仍属于建设目标。详细能力现状、目标架构和实施任务分别见 [企业级改造方案](ChemicalOps-企业级改造方案.md) 与 [改造任务清单](ChemicalOps-改造任务清单.md)。

## 核心贡献

- **全栈业务开发：** 针对采购、仓储、质检及财务流程割裂、跨岗位权限复杂的问题，基于 **FastAPI、SQLAlchemy、MySQL 与 Vue 3** 实现核心业务模块，结合状态机、RBAC 与资源级权限校验约束业务流转，支持多角色协同与操作追溯。
- **异步任务与可靠性：** 针对文档处理与 Agent 长任务耗时较长、异常退出易造成重复执行的问题，基于 **RabbitMQ + MySQL Outbox** 构建异步任务链路，结合幂等控制、任务租约与 Checkpoint 实现消息补发、有限重试及异常恢复；通过固定规模故障测试验证重复投递、Worker 异常退出后的任务恢复及重复执行防护机制。
- **Agent 工作流：** 针对跨模块查询、业务对象定位歧义及结果缺乏证据的问题，基于 **LangGraph + Pydantic** 编排产品定位、询价定位、库存查询及报价比较工具，结合条件路由、候选状态保存与证据校验支持多轮澄清及任务续答，并通过草稿预览与人工确认约束采购写入；2026-10-03 固定任务用例严格检查通过率达 **93.75%（15/16）**。
- **知识库与检索优化：** 针对化学品 CAS、商品别名及技术资料结构复杂的问题，基于 **MinIO + MySQL + Qdrant** 实现资料解析、章节级索引与向量检索，结合实体归一化、内容 Hash 与文档版本控制避免重复索引及旧内容覆盖，通过字段匹配排序与多来源证据保留优化检索效果；2026-10-09 固定题集评测 **Recall@6 达 95.00%、MRR@6 达 0.9500、nDCG@6 达 0.9500**。
- **业务一致性与质量保障：** 针对发票匹配、额度占用及审批中的并发一致性问题，通过 **Decimal、MySQL 行锁与版本化审计**保障金额计算、并发操作与历史追溯；基于 **pytest + Docker Compose** 完成集成测试与故障演练，覆盖 Agent 工作流、只读工具及异步任务队列等核心场景，2026-10-09 专项关联回归 **311 项测试通过**。

## 项目整体 STAR

### S — Situation：业务背景与问题

化工采购同时涉及产品纯度、规格、计量单位、供应商报价、交期和质量资料，需要采购、供应商、仓库、质量与财务多岗位协作。部分到货、短交、质量不合格、退货和批次冻结会改变可用库存与结算依据；不能把收货完成直接视为质量通过或财务结清。不同岗位只能操作职责范围内的数据，对账与开票需要保留计算口径和历史来源。引入大模型后，还需解决同名化学品识别、查询对象歧义、证据缺失、权限越界、重复执行和长任务中断等工程问题。这是项目面对的业务复杂性，不是对某家企业生产现状的调查结论。

### T — Task：项目目标

建立采购申请 → 审批 → 询价报价 → 订单 → 收货 → 质量验收 → 批次入库 → 发票匹配 → 财务对账的业务闭环；由服务端执行状态、权限、数量和金额约束。以模块化单体 + 独立异步 Worker 支撑可靠执行，以受控 Agent 和技术资料检索辅助查询与建议。当前实现保留其既有顺序：先形成并确认对账依据，再提交及核验发票；目标中的发票匹配与对账是相互校核关系，不擅自颠倒已实现流程。后续补齐行级放行、预留归属、异常结算和交付验收。

### A — Action：技术方案与实施

1. **业务领域建模与状态一致性。** 针对多岗位状态与数量、金额依据不一致的问题，用 FastAPI / SQLAlchemy 建模单据、明细、批次和事件；收货锁定到货单与订单，核验累计数量，财务使用 Decimal、ROUND_HALF_UP、来源 SHA-256 和行锁保护额度，匹配按版本追加。保留现有服务结构，避免一次性重写；通过采购状态、并发、库存与财务回归验证。当前订单 `COMPLETED` 表示收货数量完成，质量和财务分别判断，行级部分放行结算尚待补齐。
2. **模块化后端与可靠异步任务。** 针对进程内任务中断与迟到执行问题，保留按模块组织的单体，将任务、outbox 和资源锁同事务提交，由独立投递器发布、资料/Agent Worker 执行。租约、fencing token、有限重试、checkpoint 和 Windows Job Object / Linux 进程组约束恢复；无法证明旧进程停止时隔离并保留资源锁。以真实 Broker、隔离 MySQL 和 CLI 故障注入验证；默认仍为 `in_process`，不将消息 ACK 等同于业务提交，不承诺 Exactly Once。
3. **Agent Runtime、工具调用与 HITL。** 针对工具选择、对象歧义和证据不明，用 LangGraph 的 `plan` / `execute` 条件循环及 Pydantic 动作 Schema 开放四个授权只读工具；MySQL 快照、revision、结构化记忆与执行 checkpoint 支持追问、续跑和取消。服务端核对来源与数值，采购草稿使用专用预览确认。选择先收敛只读场景，再扩展写入确认；通过来源/数值矩阵和固定真实模型样本验证，通用写工具、统一 Token 预算与任意节点恢复仍是目标能力。
4. **RAG 知识处理与证据追溯。** 针对名称定位与技术资料依据问题，采用 MinIO 原件、MySQL 章节和 Qdrant 检索，结合 CAS / 名称 / 别名解析、源 hash、稳定章节 ID 与文档代次条件更新。保留现有解析链路，逐步建设 MinerU 优先和必要时 VL 补识、发布复核及索引生命周期；不将全部解析分支一概称为已完成。用固定合成题集区分目标识别、检索与事实代理指标，以临时 Qdrant 集合验证重跑幂等和旧写隔离。
5. **权限安全、自动化测试与可观测性。** 针对跨角色访问与交付风险，服务端执行 RBAC、归属和供应商绑定校验，前端复用现有模板呈现操作与来源。已有幂等中间件、生产配置门禁、文件扫描、请求/Trace ID、结构化日志、指标及健康接口，CI 配置包含迁移、测试和安全扫描；这些基础不等于完整生产交付。使用接口拒绝探测、专项测试与代表性浏览器流程验证，后续补全全角色 E2E、告警、链路追踪和备份恢复演练。

## 目标架构与企业级改造路线（后续建设规划）

目标采用 FastAPI / SQLAlchemy / MySQL 模块化单体，明确业务域的服务入口与事务边界；API → MySQL Task + Outbox → Dispatcher → RabbitMQ → Worker → Checkpoint / Result。AI 经授权工具调用领域服务，业务状态不由模型决定。MinIO / MySQL / Qdrant 保持既有分工，Docker / Compose 优先。Redis 只在明确需要缓存或限流时评估，不替代持久状态；暂不引入微服务、Kubernetes 或 Service Mesh。
