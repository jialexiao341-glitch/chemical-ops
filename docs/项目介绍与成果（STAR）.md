## 项目介绍（简历展示版）

**2026.09—至今　ChemicalOps：化工采购运营平台与场景化 Agent　｜　全栈 / 大模型应用**

**【项目简介】** 面向化工采购、质量、仓储与财务协同，开发贯通采购申请至结算的全栈运营平台；集成业务查询、化学品 RAG、采购草稿及报告核对，以岗位权限、人工确认和来源快照衔接 AI 输出与业务处理。

**【技术栈】** Python、FastAPI、SQLAlchemy、MySQL、Vue 3、TypeScript、LangGraph、Pydantic、Qdrant、SSE、ECharts。

**【核心能力】**

- **全栈架构与业务闭环：** 基于 FastAPI / SQLAlchemy 与 Vue 3 / TypeScript 实现采购、质量、库存及财务协同，串联申请、询价、订单、到货、验收、库存与结算；前端按 RBAC 读取权限码过滤侧边业务分组、页面、表格行操作、主数据写入口及批量菜单的导入/删除项，并按当前账号可见记录隐藏无数据且无写入/审批权限的仓储只读入口；一级分组现由可见子页面推导，无可见子页时隐藏分组标题，保留授权的详情跳转路由。运营看板读取权限授予全部 12 类内置角色，包含供应商门户；AI 工作台改用独立的 `ai.workspace.read`，仅对内部角色开放。看板向各角色返回相同的公司级汇总，包括已付款金额、供应商采购金额和库存成本，不开放业务明细或写操作。供应商门户按绑定供应商隔离受邀询价、报价、正式订单、交期更新、发货通知、质量资料和对账协同；报价提交/修订校验邀请关系、明细归属、询价状态及截止日期，交期变更追加履历，发货通知复用到货单/收货流程并检查未交数量，质量文件下载复用附件资源权限校验，对账支持双方追加留言及供应商确认/争议。各操作由独立权限码控制，六个供应商列表复用产品规格页的 Vben / Vxe Grid 与筛选适配层，统一筛选、工具栏、勾选、状态、更多操作和分页样式；批量菜单支持当前页所选记录 CSV 导出及清除勾选。通过 SQLAlchemy 跨功能区核查开发样本空字段，以幂等脚本补齐关联规格、纯度、包装及演示订单/到货日期，并修正样本生成源；保留正常流程空值和需要真实资料的字段。供应商 API 使用精简响应，不返回其他供应商报价、内部比较、审批或事件轨迹。后端批量导出和草稿删除复用对应详情服务的数据范围校验；采购员可读产品规格但不能维护主数据，运营异常详情按读写权限分别呈现。结合报告结构化提取、Decimal 规则核对和证据快照，将检测差异、批次核查与异常处置落到明细、负责人及复核流程。迁移 038、039、040 已在 development 数据库应用；供应商及角色定向回归 20 项、相关财务回归 17 项共 37 项通过，覆盖询价报价、订单归属/确认、交期、发货数量、质量文件、对账协同及分页边界；修复双方纯空白留言校验，并将供应商分页选项限制在 API 的 100 条上限内；前端类型检查与生产构建通过。尚未在浏览器逐页面复验，也未执行本地演示账号质量文件上传、发货及对账写操作；生产环境及真实业务验收未覆盖。
- **Agent 编排与确认交互：** 使用 LangGraph 编排理解、槽位校验、计划构建、SQL 校验和执行 **5 个节点**，以 Pydantic QueryPlan 与受限 ORM 覆盖 **12 类数据集**；使用 Pydantic 动作与 RBAC 白名单封装 **4 个只读工具**，新增 LangGraph 条件循环实现模型选工具、多候选追问与证据汇总；会话级 JSON 记忆保存当前目标、产品焦点、查询槽位、待补充项、最近 8 条聊天上下文和任务轨迹引用，新 Agent 任务可读取本人会话中刚完成的普通问答以解析产品指代，历史产品/库存事实不作为本轮证据；MySQL 任务快照和版本条件更新支持补充续跑及取消。Vue 3 在现有聊天消息中集成只读任务、候选单选、追问与取消，以编号正文和加粗呈现确定性业务结果，Ant Design Popover 展示段落来源、对应记录预览与切换，使用会话任务引用恢复历史，读取摘要时重新鉴权，FastAPI BackgroundTasks 独立会话执行并通过 202 接口与轮询显示进度；专用采购草稿已有预览确认，任务循环的确认写入仍待实施。Agent 运行时回归 26 项通过，包含 MySQL 认证任务 API；本次普通问答指代上下文改动尚未验证，真实模型及浏览器记忆行为仍待验证。
- **化学品 RAG 与检索优化：** 结合 Qdrant 向量检索、MySQL 章节桥接与 CAS / 别名解析，在 200 条合成混合题的 149 道可回答题上测得 **Recall@6=86.24%、MRR@6=0.6842、nDCG@6=0.7290**，无证据拒答 **39/39**；通过名称规范化、英文词边界与歧义检查，修复 **17 道**目标定位失败题，后续名称识别专项回归 **149/149**。
- **财务一致性与审计追溯：** 通过 Decimal / ROUND_HALF_UP、来源 SHA-256、MySQL 事务锁及追加式版本实现对账行计算、发票行匹配和独立双人核验；支持税差说明、驳回释放额度及来源变化重开核查，以 **6 组场景、8 张模拟发票**验证流程，金额支持 **0～6 位精度**，历史依据按保存版本留存。
- **评估体系与工程验证：** 基于 pytest 事务回滚测试覆盖状态流转、权限隔离、额度及版本校验，2026-09-30 后端全量 **279 项通过**；2026-10-03 Agent 运行时、工具、评估器及任务相关回归 **88 项通过**，隔离样本来源/数值矩阵 **30/30**；工作台状态/来源与图表规划前端测试 **16 项通过**，ChemicalOps `vue-tsc` 类型检查及 Vite 生产构建通过，构建保留第三方 BigInt 目标兼容提示。聊天集成后真实模型固定合成题首跑 **15/16** 严格 outcome 通过；T14 独立复核 **1/1** 通过但状态波动。结果报告明确记录授权工具及业务写入检查，来源/数值检查由服务端规则完成，不代表人工回答准确率或生产效果。RAG 题集区分 **149 道可回答、39 道应拒答、12 道需追问**，以固定随机种子及语料 SHA-256 留存评估依据，分别统计检索结果与名称识别回归。

## 项目定位与 Agent 优化判断

**定位：全栈业务平台 + 场景化 Agent。** 全栈部分提供真实业务对象、权限、事务和处理流程；Agent 部分负责理解需求、检索证据、查询业务数据与生成候选操作。简历用五条突出全栈架构、Agent 编排、RAG、财务一致性及评估验证，避免按页面或接口逐项罗列。

### 当前实现与差距

已有查询图仍是固定五节点链路，聊天按意图分流到查询或资料问答，采购草稿、晨报及筛选解析保留专用接口。库存/询价请求在现有聊天中转入采购只读任务 API，模型通过严格 JSON 动作在四个工具之间决策，工具结果反馈到下一步；服务端约束对象定位、权限、证据和预算。

2026-10-03 已建立采购首场景规则与 20 条验收用例，后端实现产品/询价定位、库存/报价查询、多候选追问、保存轨迹、补充续跑和取消。C18/C19 控制流已通过回归，并新增 16 条固定真实模型任务评估及只读工作台；完整阶段矩阵和 C20 确认写入、幂等及故障恢复按 [Agent 升级方案](AI%20Agent升级方案与交付标准.md) 继续实施。

会话状态与查询轨迹已保存到 MySQL，模型请求已有超时和部分重试逻辑；查询图在调用内使用 MemorySaver。新增任务表保存每步公开证据与等待状态，可在补充条件后重新核验并续跑；但进程中断可能留下 RUNNING，工作台通过进程内 BackgroundTasks 启动/续跑并立即返回编号；尚无持久化队列、租约回收、后台恢复、人工确认写入及写操作防重复机制。

工作台负责自然语言探索，业务页面负责围绕具体单据核对，通知与任务负责需要跟进的事项。模型处理语义与文档，确定性服务计算金额、数量和状态，两者通过来源记录及人工确认衔接。

| 批次影响与演练 | 可见库位/流水 → 数量、来源和调拨两端核对 → 核查清单 → 报告确认 | 待核查对象、处理记录、保存时证据和演练结论 | 确定性服务承接核查；无系统外客户去向时不推断覆盖范围 |
| 异常处置 | 异常证据与建议 → 人工采纳/驳回 → 已有运营任务 | 原因、负责人、任务及完成说明 | 采纳去重，未完成任务限制关闭；不自动执行库存或采购操作 |
| 财务差异 | 收货/退货/对账保存版 → 票行人工匹配 → 校验 → 核查复核 | 行级金额差异、版本、处理说明与独立复核记录 | 金额由业务规则计算；付款仍按单据管理，未接税务验真与银行支付 |

这些能力的共同约束是：结果必须说明依据与范围，能回到对应业务对象；涉及正式写入时，通过专用确认入口与原业务服务执行。批次、财务、异常等分析中的数值和状态主要来自规则服务，不能将它们包装成模型独立决策。

## 项目整体 STAR

### S｜Situation：业务背景

化工采购运营需要同时核对采购单据、报告与标准、库存批次和财务金额。仅展示单据列表难以回答“这批物料来自哪里”“报告与系统记录是否一致”“某一产品行为什么存在财务差额”等跨环节问题。自然语言查询和报告提取还需要满足不同岗位的数据权限，以及质量放行、库存操作与财务确认的流程要求。

ChemicalOps 以这些业务需求为开发背景，目前使用本地开发库、合成业务数据和模拟材料验证流程，实际岗位使用效果尚未量化。

### T｜Task：建设目标

构建可追溯的采购运营平台，并将 AI 能力嵌入用户正在处理的业务对象：让用户能够查询数据、核对原文证据、定位差异、指定处理人员并记录复核结果。对数量、金额、权限和状态采用确定性服务校验，模型承担意图理解、文档整理和解释，业务决定由相应岗位确认。

## 关键技术场景 STAR（面试展开）

### 采购 Agent：模型决策与服务端证据约束

- **S｜问题：** 原固定查询链路无法根据库存/报价结果选择下一步，同名规格与多个询价明细不能由模型猜 ID。
- **T｜目标：** 先建立权限内可追问、可追溯的只读任务，再实施确认写入闭环。
- **A｜技术与实现：** 使用 LangGraph 条件边循环、Pydantic 三种动作与四工具 Schema，SQLAlchemy 按业务范围查证；多候选强制等待用户，续跑重新定位核验。MySQL JSON 快照保存公开证据，revision 条件更新保护续跑/取消；Vue 3 将 202 启动/续跑、轮询、候选及来源集成进原聊天消息，通过 URL 会话编号与 AIMessage 任务引用恢复历史，聊天摘要重新检查任务授权，库存来源提交表单同步显示条件与查询范围；迟到响应不能覆盖取消/新任务状态。模型完成动作仅引用本轮成功业务证据，由后端生成数值摘要；固定合成评估保留 Schema、模型配置与回放。
- **R｜结果：** 2026-10-03 工具/运行时/相关回归 84 项通过，覆盖追问、四工具串联、范围变化、预算及取消；MySQL 认证 API 与模型 HTTP 协议有开发验证。后续增加 Vue 3 只读工作台与 FastAPI 202 后台启动/续跑，曾完成相关后端 90 项、前端状态/图表 9 项及类型/构建验证；聊天集成后，会话恢复、候选选择与底部输入补充有交互证据。本轮后端相关回归 88 项、来源/数值 30/30、前端 16 项及类型/构建通过；deepseek-flash 固定合成题首跑 15/16 严格通过，T14 单例复核通过但状态波动，来源/数值由规则核验，不代表人工回答准确率或生产收益。浏览器确认管理员既有成功/取消态及采购员会话隔离；采购员任务状态、其他岗位、完整浏览器矩阵、确认写入与故障恢复仍待验收。


### 界面一致性补充：共享规则与例外页面收敛

- **S｜问题：** 筛选控件存在整列拉伸、固定宽度禁止换行和表格字体差异，供应商退货页的标题、行距、筛选及分页与其他业务列表不同。
- **T｜目标：** 在既有 Vben / Ant Design 风格内统一正文、标题、控件密度和筛选布局，使桌面与窄屏保持可读、可操作。
- **A｜技术与实现：** 在 Vue 3 / TypeScript 列表适配层统一筛选规则，用 CSS 与 Ant Design 主题统一 14px 正文、16px 列表标题和 32px 常规控件；文本及对象筛选组默认 300px、普通枚举组 230px，空间不足换行。供应商退货页复用 Vxe 分页、筛选、工具栏和状态字典；弹窗/抽屉约束最大宽度，表单窄屏切换单列；有效期预警使用批次、仓库及库位组合行标识，预警窗口移入标准筛选栏，通过搜索应用条件、重置恢复 30 天，列宽均衡分配并保留窄屏内部滚动。
- **R｜结果：** 2026-10-04 供应商六个列表改为直接复用产品规格页的 Grid：继承全局 Segoe UI / Microsoft YaHei 字体、14px 正文、16px 标题、32px 控件、主题色和浅色表头，沿用筛选栏换行、表格内部滚动及原生按钮交互状态；取消询价物料双行与单据编号加粗以保持行密度。代码对照完成布局、字体、主题及控件复用审查，类型检查和生产构建通过；此次未做浏览器视觉、焦点、窄屏或操作实测，不能计为像素一致或可访问性验收。2026-09-30 前端类型检查及生产构建通过，本地浏览器只读巡检 27 个页面无控制台错误；产品、库存流水、退货页在 1440 / 1024 / 768 / 390px、明暗主题下未发现页面和筛选栏横向溢出。保留后端既有 279 项回归记录，本轮未重新执行后端全量测试；未把界面巡检推算为业务效率提升。

### 1. 安全自然语言查询：约束模型输出与数据库执行

- **S｜问题：** 采购、库存与财务查询涉及不同权限和金额口径，模型直接生成的 SQL 难以保证访问范围和业务字段正确。
- **T｜目标：** 保留自然语言查询的便利，同时将执行权限收敛到服务端定义的目录，并能解释每轮查询过程。
- **A｜技术与实现：** 使用 LangGraph StateGraph 将流程划分为理解、槽位校验、计划构建、SQL 校验和执行；Pydantic QueryPlan 约束数据集、指标、条件及限制条数，SQLAlchemy 将合法计划映射为查询，再检查 SELECT-only 和允许表。将上一轮计划、权限快照和查询轨迹保存到 MySQL，SSE 返回回答，ECharts 呈现可用图表。LangGraph MemorySaver 用于执行时 checkpoint，会话状态另由业务表持久化。
- **R｜结果：** 开放 12 类普通汇总数据集及部分固定追溯查询，支持部分条件继承和来源定位；查询范围由服务端规则控制。相关查询、权限与追溯行为进入已有后端回归，不宣称任意 SQL 或通用长任务恢复。

### 2. 化学品 RAG：先定位对象，再评估检索与回答

- **S｜问题：** 原混合评估中，22 道可回答题失分，17 道在物质名称识别阶段未定位化学品，尚未进入检索；剩余 5 道未找齐指定证据。
- **T｜目标：** 修复名称阶段的检索入口问题，并分别衡量目标识别、证据召回和回答事实，避免把不同层次混为一个准确率。
- **A｜技术与实现：** 对主数据及已解析文档名称、别名进行全角规范化、空格/连接符处理、英文词边界和长名称优先匹配；歧义时要求 CAS 确认。结合 Qdrant 向量检索与 MySQL 文档章节桥接，把章节摘录及来源送入模型；用固定随机种子及输入 SHA-256 保存 200 条混合评估的可复现来源。
- **R｜结果：** 名称专项回放达到目标 CAS 集合匹配 149/149，旧 17 道定位失败题通过。2026-09-28 完整评估 Recall@6 为 86.24%，MRR@6 为 0.6842、nDCG@6 为 0.7290；拒答 39/39、追问 12/12。后续名称修复没有重新生成全套答案，因此不据此上调完整 RAG 指标。

### 3. 结构化生成：把采购描述转成可检查的草稿

- **S｜问题：** 自然语言需求可能缺少数量、单位或用途，生成模型也可能返回不存在的物料、单位和不合格式的日期。
- **T｜目标：** 生成用户可以编辑和确认的表单候选，最终写入仍满足原采购申请的格式与权限规则。
- **A｜技术与实现：** 将有效产品/单位目录作为上下文，要求模型 JSON 输出；以 Pydantic `_DraftProposal` 和 `_DraftItem` 约束字段及数值，再逐项校验目录 ID、必填字段和停用状态，最后复用 `PurchaseRequestCreate` 模型检查完整请求。预览返回候选与警告，前端确认后调用正式创建接口。
- **R｜结果：** 实现“描述 → 校验预览 → 确认创建 DRAFT → 原审批流程”的专用链路；对缺项、无效目录项和格式错误返回可处理提示，预览阶段不创建业务记录。尚无真实录入耗时对比，不填效率提升百分比。

### 4. 质量报告核对：分离模型提取与数值判断

- **S｜问题：** 报告和系统录入可能在批次、检测项、单位或数值上不一致，多份报告也可能互相冲突；多明细验收单不能把整单结果套到某一种产品。
- **T｜目标：** 定位报告对应的到货明细，把每个核对结论关联到可检查的原文和标准版本。
- **A｜技术与实现：** 使用本地文件解析或配置的 MinerU 取得文本，模型按 Schema 提取检测项及引句，Pydantic 检查结构；通过 `text.find` 验证原文引句并定位最近页/段落标记，以 Decimal 比较数值及单位，按产品、规格、批次定位结果后应用所选标准。用 JSON 快照保存报告、明细、标准版本和差异，结合角色权限及检测项处理状态记录修正与复核。
- **R｜结果：** 已接入明细级核对、多报告冲突汇总、标准选择、逐项处理和负责人复核；单位不同、对象信息不明或报告缺项保留待核查状态。当前报告样本主要用于开发验证，不能声称实测提取准确率或自动质量放行。

### 5. 批次影响与异常：将分析延伸到核查与任务

- **S｜问题：** 单个批次余额无法解释来源和历史流转，调拨出入库可能不完整；只有建议文本无法知道是否已有负责人处理。
- **T｜目标：** 在可见数据范围内核对数量和来源，保存当次证据，并把待核查对象关联到具体处理记录。
- **A｜技术与实现：** 用 SQLAlchemy 读取批次库位、流水及来源明细，按产品、批次、单位、库位唯一匹配来源，并核对调拨两端执行数量。以不可变 JSON 快照保存演练证据，状态机约束指派、提交和另一人复核，追加事件保留操作历史；异常采纳关联已有运营任务，创建前检查重复关联，并在异常关闭时检查任务完成状态。
- **R｜结果：** 批次分析已有核查清单与演练报告确认路径，来源缺失、多候选、跨权限范围和数量差异均明确标记；异常跟进形成任务关联与关闭约束。数量与状态由规则服务计算，模型不独立决定冻结、召回或库存调整。

### 6. 财务匹配：来源版本与并发额度一致性

- **S｜问题：** 退货、分次开票、多产品行、税额舍入及驳回重提会改变核查口径；并发匹配或沿用旧复核结论可能造成超额和依据不一致。
- **T｜目标：** 把发票匹配到保存版对账行，保持金额和来源可复核，并在每次提交、核验时检查当前额度。
- **A｜技术与实现：** 使用 Decimal/ROUND_HALF_UP 分别计算行不含税金额与税额，以 SHA-256 检测已保存版本的订单、到货和退货来源变化；对账与发票匹配追加版本。历史版本 0 单据明确标示未保存行级快照，不与当前来源比较后误报变化，也不按当前订单反推历史金额。通过 MySQL 事务、`SELECT FOR UPDATE` 锁定主单和相关记录，并用当前锁定读统计占用，避免等待锁后沿用旧事务快照。状态机限制修改时机，人员 ID 校验阻止自审；匹配或状态变化时追加事件并重开原核查结果。
- **R｜结果：** 已支持一票多行、同一行分次开票、税差说明、驳回/作废释放额度和历史版本保留；通过隔离接口测试验证行超额、重提超额、来源变化及同人复核拒绝。保留 6 组、8 张模拟发票供页面演示，相关用例纳入 279 项后端回归。

## 事实与使用边界

- 当前没有真实用户规模、上线收益、核对耗时下降比例或财务差错下降比例的验证数据，简历中不填写这类成果。
- 名称识别 149/149 与完整 RAG 评估是两个独立指标，不能将前者写成“问答准确率 100%”。
- 产品标准由用户配置；质量核对不自动放行，演练完成不代表执行实际召回，财务核验不代表税务平台验真或银行付款。
- 模型、解析、对象存储、向量检索及队列服务按部署配置启用；可选集成不代表全部环境已经运行。
- 项目角色和个人贡献范围需要按实际经历表述；本文不预设团队人数或全部功能均由单人完成。
