# Agent 与批次查询语义统一设计

## 目标

统一只读采购查询在 Agent 和多意图批次中的业务口径，避免同一库存/报价请求因路由不同而得到不同的澄清、候选选择或摘要行为。保留现有执行入口和业务工具，先共享产品查询的确定性规则，不重构整个 Agent Runtime。

## 当前行为与差异

- `Understanding` 已显式携带 `execution_mode`，Schema 校验其与任务结构一致；`route` 直接返回已校验模式。
- 批次产品任务在调用工具前，遇到 `date_from`、`date_to` 或 `unit` 会进入 `WAITING_INPUT` 并询问是否采用现有记录/原始单位口径。
- Agent 路径由规划器选择工具。工具参数目前没有日期筛选；单位槽位可能未参与工具调用，因而存在条件被忽略的风险。
- Agent 与批次各自实现产品候选处理和库存汇总。`candidate_resolution.validate_selection` 已共享候选 ID 与 revision 校验，但何时等待、何时可汇总仍分散在两个运行时。
- Agent `_summary` 与批次 `summarize` 分开生成回复，库存/报价明细和不同单位说明可能出现差异。
- analytics 与 document 目前由批次执行；此设计不改变其能力边界。

## 设计

新增一个只依赖数据结构和工具结果的共享查询策略模块，供 Agent 与批次产品查询调用；需要数据库核验的产品族身份留在候选解析层，再把核验结果传入纯策略。第一阶段限定为：

1. **槽位可执行性**：集中判断库存/报价工具当前支持的条件。日期或单位条件若无法由对应工具准确执行，两条路径都在工具调用前进入相同的澄清状态；不得静默丢弃条件。澄清应保留原问题与槽位，续答后再按服务端当前权限执行。
2. **产品候选策略**：集中判定唯一命中、多候选、截断和明确全选的处理。候选必须来自当前授权工具结果；选择仍绑定当前任务 revision，并由服务端重新查验候选范围。沿用现有同名或已登记为同一有效化学品的产品族汇总口径；数据库身份核验保留在候选解析层，共享纯策略只接收“同产品族”布尔结论。全选只对完整候选集合生效，不允许截断结果被称为全量。
3. **库存单位策略**：集中按单位 ID/名称分组汇总；不同单位不换算、不直接相加。Agent 与批次共用同一汇总函数和边界错误。
4. **产品查询摘要**：集中为库存与报价工具证据生成确定性摘要，保留无结果、截断、不同单位和报价可比组信息。多任务批次的整体进度/部分失败汇总仍由批次负责；Agent 的模型规划和完成条件仍由 Agent Runtime 负责。

工具执行依旧经 `agent_tools.execute_tool`，每次调用继续执行现有 RBAC 与资源范围校验。该模块不接收模型生成的 SQL、数据库 ID 或权限结论，不执行写操作，不改变 API 请求/响应或持久化格式。

## 方案选择

- **推荐：共享策略与摘要函数，保留双编排器。** 变更集中、风险可控，可以先收敛日期/单位和候选边界，再逐步扩展到更多只读查询。
- 将 Agent Runtime 与批次整体合并为一个执行器：重复最少，但会同时影响队列任务、进度、续跑、部分失败和持久化，超出当前阶段必要范围。
- 只在提示词中要求两路行为一致：改动小，但不能阻止工具调用前静默丢弃条件，也不能保证候选/汇总规则一致。

## 不在本阶段范围

- 将 analytics、document 纳入 Agent 工具。
- 改造 Tool Registry、队列/任务状态机、前端交互或 API 契约。
- 自动换算单位、推断用户未提供的业务口径，或增加写工具。
- 统一所有跨模块查询服务；后续需要按业务域单独评审。

## 验收标准

- 同一库存/报价请求分别进入 Agent 与批次时，对日期/单位不支持条件给出相同的执行前澄清，且没有业务工具调用。
- 两条路径对唯一候选、多候选、全选、截断候选和过期 revision 作出一致状态判定。
- 不同单位分别汇总；单位不一致时明确不直接比较/相加，数值与工具证据一致。
- 报价无结果、多个询价候选和截断结果不被摘要误报为唯一或完整结果。
- 既有权限、候选撤权/数据变化重验、历史证据访问和批次部分失败回归保持有效。

## 验证边界

使用现有 `tests/test_agent_runtime.py`、`tests/test_ai_multi_intent.py`、候选解析与权限隔离测试，并为两路共享策略增加对照回归。真实模型评测只在使用当前提示词、运行时和题集哈希留档后执行；单元/契约对照通过不能替代真实模型质量评测。
