# Agent 动作确认与采购闭环设计

## 目标与范围

实现蓝图 Sprint 2 的三个衔接能力：F-05 通用动作确认框架、F-06 采购申请草稿修改/检查/提交、F-07 询价草稿与比价建议。动作建议可以来自 Agent 或页面，但业务写入只能在用户确认当前预览版本后发生，并且只能通过已有领域服务完成。

本期包含：

- 将采购申请草稿创建从专用确认账本接入通用动作提案机制。
- 对已有采购申请草稿/驳回申请提供字段修改提案、提交前检查和显式提交动作。
- 从已审批采购申请创建询价草稿；现有报价比较能力继续作为只读建议使用。
- 前端复用现有 AI 草稿预览与业务表单样式，展示动作、字段差异、依据、风险、阻塞项和确认结果。

采购订单草稿、发送询价、确认中选、通知供应商、附件解析和事件触发写入不属于本期；它们在后续阶段复用本框架。F-07 的比较建议不自动选中供应商或产生写入。

## 现状与约束

- `AIPurchaseDraftConfirmation` 保存采购申请创建预览、版本、哈希、证据和执行结果；确认时锁定记录，校验用户、部门、产品及单位快照，再调用 `purchase_requests.service.create_request(commit=False)` 并在同一事务中提交。
- `patch_purchase_draft` 修改的是尚未写入业务库的创建预览，不是已有采购申请。
- 采购申请领域服务已有 `update_request` 和 `submit_request`，但目前内部提交事务；`create_request` 已支持 `commit=False`。
- 询价 `create_rfq` 校验来源申请范围、审批状态、产品、单位和供应商，但目前内部提交事务。
- 询价创建仅允许来源采购申请处于 `APPROVED`。订单草稿创建依赖已确认的比价结果及中选报价，因此留给 F-08。
- 所有 Agent 行为调整先检查并复用现有提示词、结构化 Schema、工具契约和页面模板；权限、数据范围、状态、版本与写入边界由服务端强制执行。

## 设计方案

### 1. 通用提案账本

新增 `ai_action_proposals` 表和对应 ORM/Alembic 迁移。每条记录保存：

- 所有者、`action_type`、资源类型/ID（新建动作资源 ID 为空）、当前提案版本。
- 规范化 payload、payload hash、执行前资源版本快照、字段差异、证据、风险级别和所需权限。
- 唯一确认 ID、幂等键、到期时间、状态、执行结果与执行时间。

动作类型必须在服务端注册表白名单中。首批注册：`purchase_request.create_draft`、`purchase_request.update_draft`、`purchase_request.submit`、`rfq.create_draft`。不允许模型或客户端指定任意 Python 服务、模块或 SQL。

提案状态为 `PENDING`、`EXECUTED`、`EXPIRED`、`CANCELLED`、`INVALIDATED`。修改提案会递增 `preview_version`、重算 payload hash 和 diff，旧版本确认一律拒绝。执行失败不写业务数据，也不返回成功结果；可修订的字段错误返回可读校验信息，过期或资源已变化则要求重新生成提案。

### 2. 服务端动作处理器

新增独立的动作提案服务和处理器注册表。每个处理器定义：

- 入参 Schema、所需权限和允许的用户/资源范围。
- 生成规范化提案、字段差异、证据、阻塞项和风险提示。
- 在确认阶段重验权限、用户有效状态、资源范围、资源版本及业务状态。
- 调用对应领域服务，并序列化稳定的业务结果。

确认服务先按用户与确认 ID 锁定提案，再验证 `confirm=true`、预览版本、哈希、状态及有效期。若同一已执行提案再次确认，返回已保存结果；不重复调用领域服务。领域数据和 `EXECUTED` 结果必须在同一数据库事务提交。所需领域服务提供 `commit=False` 路径，提案服务是该事务的唯一提交者。

权限要求：创建与修改申请草稿需要 `procurement.requests.write`；提交申请在现有领域权限规则下仍需 `procurement.requests.write`，审批权限不授予 Agent；创建询价草稿需要 `procurement.rfqs.write`。所有动作在提案时和确认时重新读取权限及资源范围。SYS_ADMIN 继续遵循现有权限绕过规则，但用户仍须为 ACTIVE。

### 3. 首批动作契约

**采购申请创建草稿**：复用当前自然语言提案与产品候选解析。缺少必填字段时只返回澄清，不创建可确认提案；字段齐备后保存 `create_draft` 提案。确认后通过采购申请服务创建 DRAFT。

**采购申请修改**：只接受 `PurchaseRequestUpdate` 允许的字段，目标状态必须为 DRAFT 或 REJECTED。提案快照包括申请与明细字段摘要、`updated_at`/规范化内容 hash、当前申请版本状态；diff 按字段和明细行展示。确认时重新检查状态、对象快照、用户数据范围及申请关联的产品和单位状态，再调用 `update_request(commit=False)`。

**采购申请提交前检查与提交**：检查复用采购申请领域服务的校验规则，返回阻塞项与需要注意的字段，不改变申请状态。仅当阻塞项为空时生成 `submit` 提案；确认时重新校验同一申请版本与提交资格，再调用 `submit_request(commit=False)`，由领域服务建立审批节点。没有显式确认不得进入 APPROVING。

**询价草稿**：来源采购申请必须对当前用户可见且已 APPROVED。提案包含来源申请版本/明细、询价截止与交期要求、询价行及已选供应商；供应商 ID 必须来自当前用户可访问的供应商候选，不能仅凭模型生成的 ID 写入。确认时重验来源状态/版本、产品、单位、供应商状态与权限，再通过 `create_rfq(commit=False)` 创建 DRAFT。现有报价比较工具可在报价数据存在时给出只读比较建议，回答中保留报价依据和限制，不选中报价、不发送询价。

### 4. API 与前端流程

增加通用提案创建/修订/取消/确认 API；请求和响应使用严格 Pydantic Schema，禁止额外字段。确认 API 要求显式字面值 `confirm: true` 与当前 `preview_version`。确认端点不由模型工具调用，只能由已登录用户在界面明确操作。

采购申请草稿现有预览面板改为渲染通用提案响应；已有草稿页面通过同类业务面板发起修改、预检查和提交提案。询价草稿在现有 AI 工作台和询价页面复用已有表单/弹窗样式。所有确认按钮显示动作名称和目标单据，并在提交中禁用；成功后展示领域服务返回的单号及状态，失败则保留可读错误并要求重新核对。

已有 `/purchase-request-draft/*` API 保留为兼容适配器：新预览写入通用提案表，但继续返回现有采购草稿预览响应；patch/confirm 先处理通用提案 ID，再兼容尚未过期的旧专用确认记录。新前端直接调用通用动作 API。部署后不再写入旧表；旧记录经过 10 分钟有效期及清理任务后，可在后续迁移中移除旧确认路径和模型。

### 5. 提示词、Schema 与 Agent 行为

先调整现有 purchase draft 阶段提示词和理解 Schema，使 Agent 将“创建草稿、修改已有申请、提交申请、创建询价草稿、查询/比较报价”区分为明确的动作意图和对象槽位。模型只能提出动作及字段候选，不能把自然语言请求解释成已确认，也不能调用确认端点。

服务端按动作类型校验槽位、工具/路由允许集合和唯一编号/资源 ID；只读查询与动作提案分开执行。确定性摘要如实呈现字段差异、阻塞项、影响对象和确认状态，不使用模型生成的最终写入结果。

### 6. 错误与安全处理

- 未登录、用户停用、权限撤回、资源超范围：拒绝动作并保持业务数据不变。
- 预览过期、预览版本不匹配、资源状态/内容变化：返回冲突错误，要求重新检查并展示新预览。
- schema 或领域校验未通过：返回字段级错误，不执行写入。
- 相同确认并发到达：行锁串行化；首次成功写入并保存结果，后续请求返回同一结果。
- 领域服务失败或数据库异常：事务回滚，提案不能标记为成功；不得留下部分业务记录或审计结果。
- 审计日志继续由领域服务写入；提案账本记录确认 ID、动作类型、预览版本与执行结果关联，不记录模型思维链。

## 验收标准

1. 创建、修改、提交采购申请和创建询价草稿均先返回可读提案；未确认时业务表和审批状态不变。
2. 确认当前预览版本后只通过领域服务执行，提案结果与业务写入同事务提交。
3. 重放确认、并发确认最多产生一次业务写入，并返回相同结果。
4. 过期/旧版本预览、权限撤回、部门或数据范围变化、申请/询价状态变化、产品/单位/供应商停用均被服务端拒绝。
5. 采购申请检查结果与提交时的领域校验一致；阻塞项存在时不能创建可执行提交提案。
6. 询价草稿只接受已审批且当前用户可见的申请来源、有效供应商和有效产品/单位；创建后状态为 DRAFT，发送与选中均未发生。
7. Agent 的代表性自然语言样本能区分只读查询、动作提案和需要澄清的请求；现有只读工具、权限、确认和财务/供应商回归不退化。
8. 复用既有前端模板；本期不做浏览器验收，待后续统一验收。

## 备选方案与取舍

- **继续扩展专用采购确认表**：改动较少，但 F-07 以及之后每个业务动作仍需复制版本、过期、权限和幂等逻辑，无法完成 F-05 的统一契约。
- **把提案仅保存在 Agent 任务 JSON**：不需要专用数据表，但任务清理、并发锁、重试与业务事务难以保证一次性执行，不用于写操作账本。
- **使用通用提案表 + 白名单处理器（推荐）**：新增一个明确的服务端写入边界，复用领域规则，并可让后续 F-08 订单草稿等动作逐步注册接入。
