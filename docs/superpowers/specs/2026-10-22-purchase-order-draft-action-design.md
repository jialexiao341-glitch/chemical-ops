# 中选报价生成采购订单草稿设计

## 目标与范围

在询价详情中，采购员可基于已经确认的比价结果准备采购订单草稿提案。提案预览需要展示订单明细及可核实的合同条款，用户显式确认后才调用采购订单领域服务创建 `DRAFT` 订单。新草稿保留中选报价逐行付款条件快照。

本设计只覆盖“确认中选报价 → 订单条款预览 → 创建订单草稿”。不自动提交订单审批、不审批、不正式下单、不生成催货动作，也不引入模型自动判断合同合规性。条款检查是确定性规则和原始业务数据的对照，不替代法务或采购审批。

## 已有能力与缺口

- `purchase_orders.service.create_order` 已要求比价结果为 `CONFIRMED`、报价为 `SELECTED`、来源申请已审批、报价完整覆盖询价明细、产品已关联、剩余可采购量足够，并限制同一比价结果重复生成订单。
- 该领域服务目前直接提交事务，尚不支持动作提案要求的 `commit=False` 原子执行。
- RFQ 页面已有直接创建订单草稿按钮；它调用订单接口，不经过版本化动作提案。
- 报价行保存 `payment_terms`，但采购订单明细没有该字段。若不建立订单侧快照，之后查看历史订单只能依赖来源报价关系。

## 方案

### 1. 订单付款条件快照

在 `purchase_order_items` 增加可空 `payment_terms_snapshot` 字段，采用新增迁移 `058`，不修改已发布迁移。使用逐行字段是因为付款条件目前存储在 `supplier_quote_items`，同一个报价中的不同明细可以有不同条件。

更新 SQLAlchemy 模型、订单创建/更新/读取 Schema、订单草稿服务和数据库结构说明。订单生成时把中选报价行的原始付款条件复制到对应订单明细。现存订单保持 `NULL`，表示历史付款条件未在订单侧保存；读取时不能从当前报价反向伪装成下单时的订单快照。

### 2. 订单提案

新增已注册动作 `purchase_order.create_draft`，入口为 `business_page`，所需权限至少包括 `procurement.orders.write` 和读取来源询价/报价所需权限。动作 payload 只接受比价 ID、报价 ID 和明确允许编辑的订单字段（收货地址、预计到货日、备注）；RFQ ID、供应商、产品、价格、税率、数量和付款条件全部从服务端重新读取，不接受客户端覆盖。

`prepare` 调用无写入的订单来源校验/预览逻辑，要求用户可访问来源申请和询价，并复用订单领域规则；检查该比价结果尚未创建订单。生成的提案关联已确认的比价结果和询价单，保存中选报价、询价、申请、行项目及主数据状态的资源快照。

`validate_current` 在打开提案、修订和确认时重新读取并比对快照，重新检查用户状态、权限、数据范围、比价/报价状态、申请审批状态、剩余采购量和重复订单。确认时调用 `create_order(..., commit=False)`，由通用提案框架在同一事务保存订单草稿与提案执行结果；旧 HTTP 接口保留原有调用行为。

提案 Inbox 加入新动作类型。仅提案所有者可读取；读取和确认都重新检查订单写权限、来源可见范围以及询价读取权限。资源不可访问时隐藏报价、申请、金额、条款及深链信息；深链返回询价详情，而不是暴露不可见订单。

### 3. 条款预览与检查

提案差异和证据逐行列出：产品、数量/单位、未税单价、税率、币种、报价交期、付款条件，以及适用的询价/申请要求。服务端生成可解释的检查结果：

- 报价来源、供应商和币种必须与已确认中选结果一致；报价行必须完整覆盖询价行。
- 已有订单服务验证数量不超过申请剩余量；预览同时展示数量来源。
- 有报价交期和要求到货日时比较两者；缺少任一侧数据时标为“无法核对”。
- 用户未提供收货地址或预计到货日期时作为待核实提示，不擅自从非权威来源补值。
- 每行付款条件原文写入订单快照；缺失时显示“报价未提供”，不生成推断条款。
- 报价来源和金额条件发生变化、申请未审批、订单已存在、数量超额、产品缺少主数据等阻止生成的条件由服务端校验并阻止确认。

预览不对付款条件、交期或质量做未经批准的货币化评分，不宣称法律合规。质量记录不是采购订单合同条款；如展示，只能作为链接到可见历史验收事实的独立提示，不作为订单生成阻塞或评分。

### 4. 前端交互

沿用询价详情抽屉、现有订单表单控件和 Agent 提案预览/确认组件。中选报价确认后显示“检查条款并准备订单草稿”入口；打开预览后展示差异、逐行条款、待核实提示和显式确认按钮。确认只创建 `DRAFT`，完成后显示订单编号并跳转订单详情或订单列表。当前订单创建按钮不再直接调用写接口。

如从 Agent Inbox 处理该提案，详情复用现有提案模板；用户只可修改收货地址、预计到货日期和备注，改动导致新预览版本，确认时以最新版本重验。

## 错误与并发处理

- 提案过期、权限撤销、来源资源变化和重复确认沿用通用提案错误语义。
- 同一比价结果的数据库唯一约束继续作为并发最终防线；发生唯一约束冲突时转换为明确的重复订单业务错误。
- 领域服务 flush 但不提交时，不得返回已创建成功的订单；只有提案结果和业务事务提交后才能向客户端确认完成。
- 新迁移只新增可空字段，不回填历史订单、不修改旧迁移 checksum。

## 验收

1. 未确认提案不创建订单或订单事件；显式确认后只产生一张 `DRAFT` 订单。
2. 订单行的数量、单价、税率、币种和逐行付款条件与确认的中选报价一致。
3. 申请未审批、来源不可访问、报价/比价状态变化、剩余量不足、产品无主数据、订单已存在和并发重复创建均被拒绝。
4. 缺收货地址、预计到货日、报价交期或付款条件时，预览准确提示待核实，不猜测补值。
5. 动作确认回滚时订单、事件和提案执行结果一起回滚；幂等重放返回既有执行结果。
6. 权限撤销或来源资源不可见后，Inbox 不泄露供应商、金额、付款条件和单据入口。
7. 订单详情读取付款条件快照；旧订单的空值明确表示历史无快照。
8. 相关后端/前端回归通过后，再按统一安排进行浏览器验收。

## 待用户审阅的关键决策

- 付款条件以订单明细级快照保存，以匹配报价数据粒度。
- 自动条款检查只做字段一致性、来源完整性和缺项提示；不制定付款/交期风险权重，不自动判断合规。
- 缺少地址、交期或付款条件默认允许先生成草稿但明确提示；阻塞项限于现有订单领域硬规则与来源/权限/状态校验。
