# 订单交期跟进与催办草稿

## 目标与边界

落实蓝图中采购链路收尾的交期跟进首期能力。从已下单/部分到货订单详情生成有业务事实依据、可补充说明、显式确认保存的催办草稿。复用当前动作提案账本和本人 Inbox，不增加外部消息通道，不改变交期、订单状态或收货记录，不预测交期。

事实取自服务端按当前账号范围重读的订单：真实订单号、供应商 ID、确认状态、预计到货日期，以及逐行产品快照、单位、订购/已收/待收数量和计划日期。日期使用上海业务日，数量不跨单位合计，未维护交期明确提示。仅处理尚有待收明细的 ORDERED/PARTIAL 订单。

## 实施选择

沿用既有确定性事实摘要和版本化提案，注册 `deliveries.followup_draft`，从业务页发起。通用 LLM 自由生成会增加未经证实的承诺和数字风险；直接发送需要新的供应商消息领域模型和通道，超出本次草稿范围。因此本次不引入这两条路径。此为根据现有架构作出的实施选择。

草稿正文由领域读服务生成，用户仅修改补充说明。确认保存前重验订单/明细/业务日快照，事实变化要求重新预览。确认结果仅保存于提案账本，重复确认复用结果。读取 Inbox 必须同时满足当前动作读写权限和订单范围；撤权后隐藏单号、正文和证据。

## 界面与验证

订单工具栏新增“交期跟进”，直接复用任务中心的 ActionProposalDetail 和现有 Modal 用法。展示正文、来源快照、未发送提示、补充说明编辑及取消/确认保存；已保存草稿可从本人 Inbox 回看。

验证覆盖非法标识/额外字段、无待收/终态拒绝、部分收货、逐行日期/单位、缺交期、上海日期、来源改变、权限撤销、资源越权、版本修订和确认幂等。开发阶段运行后端定向回归、前端针对性测试与类型检查；浏览器验收按既有统一策略收尾。不自动提交 Git，不更新 README/STAR。
