# Agent 查询证据衔接采购申请提案设计

状态：已实现服务端会话桥接、来源事实指纹与确认前重验；浏览器与真实模型验收未执行。

## 目标与范围

库存/报价查询后，用户说“按刚才的信息整理采购申请”，系统继承当前会话已确认的产品与用户需求，重新查询参考事实，缺少数量、单位或用途时追问，在既有草稿预览中展示并保存来源。显式确认当前版本后仍由现有领域服务创建 DRAFT。

本轮不扩展询价、订单、附件、主动通知或审批。不推算采购量，不用报价数量/MOQ 充当需求，不自动把报价填为用户预算。

## 现状

- agent_runtime.get_task 已有本人任务和轨迹访问校验，TaskRead 包含 revision、trace、conversation_id。
- 聊天批次另将任务与证据写入会话状态和消息引用，必须同时兼容。
- AIPurchaseDraftRequest 已有 conversation_id，但工作台 API 未传入；后端仅在可确认阶段校验会话，没有用它还原需求。
- drafts.py 会查询产品、库存和报价并返回 evidence，但创建处理器 prepare 返回空 evidence，来源未进入通用提案账本。
- revise_action 直接覆盖 evidence，需要处理修订后的来源更新。
- 已有草稿表单、来源展示、缺项与确认交互，继续复用。

## 方案

采用“现有会话/任务引用 + 服务端结构化上下文 + 新鲜证据”的增量方案。

仅拼接历史聊天文字不能可靠区分用户需求与助手建议，不采用；新建 Supervisor 或工作流没有必要，不采用。本设计将用户已选择的第一步具体化。

## 输入与上下文

继续使用 question/draft/conversation_id。客户端不上传可信证据快照。模型调用前校验本人会话；从最近适用的已完成查询消息定位 Agent 任务或批次，不能扫描全部个人任务。核验任务所属、会话绑定、完成状态、revision 和权限。多对象或待选择状态不得静默选定。

服务端分别提供：

1. 有消息 ID 的相关用户原文及本轮需求；采用有界窗口，当前要求优先，冲突时追问。
2. 从成功工具参数和结构化结果还原的已确认产品、规格及单位；不能从助手摘要推断 ID。
3. 重新执行受控工具得到的库存/报价，保留原仓库及询价明细范围，不自动换成别的询价或扩大仓库。
4. 会话/消息/任务 revision/step 或批次子任务引用，以及工具参数、观察时间、当前来源和结果指纹。

旧事实过期、对象停用或权限/范围变化时不能进入 Prompt 或预览。缺失对象重新查询或选择。无会话请求兼容原有行为。

## Prompt 与安全校验

优先调整现有提取 Prompt 与输出 Schema 说明，区分用户需求、已核验对象、参考事实。输入文本都是数据，不能改变权限或触发确认。

产品 ID 只能由服务端已核验候选绑定；拒绝模型任意 ID。多候选继续使用原有选择/缺项表单。数量、预算、用途须由用户提供，库存、报价量、MOQ 与模型建议不能补成这些字段。不增加单个问法关键词特例。

## 证据持久化与生命周期

复用 AIAgentActionProposal.evidence 和 expected_resource_snapshot JSON，预计不增加表或迁移。服务端专用上下文把已核验证据交给采购创建处理器；公共 payload 继续严格遵循采购业务 Schema，不接受客户端 evidence。

- 缺项：返回部分字段、来源和追问，不生成 token。续问及表单补齐携带原会话，恢复同一来源引用并重新校验。
- 生成：重新查证据，与动作 payload 和业务快照一起保存；预览与 Inbox 使用同一份持久化来源。
- 修订：对象改变后清除不相关证据，重新查询并递增 preview_version，必须确认新版。
- 读取：所有者、写权限与业务资源检查之外，核验证据读取权限，撤权后不泄漏原库存/报价。
- 确认：先检查证据新鲜度，再进入现有短事务重验提案及业务对象并执行。事实变化要求重新预览，不能静默刷新后执行。模型/长工具查询不放在写事务内。仅承诺确认前观察到的一致性，不承诺锁定库存/报价到提交瞬间；DRAFT 不占库存或承诺报价。
- 重放：已执行结果按现有所有者/写权限规则回放同一申请，不因后续库存变化重复创建；历史证据读取仍鉴权。
- 取消/过期：沿用现有机制。

## 前端

API 包装增加可选 conversation_id，自然语言预览及结构化补齐均传 activeConversationId。沿用草稿字段、来源区、缺项提示与确认按钮。检查并复用 chatEpoch 机制，防止旧请求覆盖新会话。刷新后提案仍能读取来源。

## 实施顺序与测试

1. 先补失败测试：Agent/批次到草稿的上下文、撤权/跨会话、多候选与缺项、参考事实不冒充采购需求。
2. 实现统一服务端证据上下文解析，接入原 Prompt/预览。
3. 保存来源，补读取、修订、确认和重放校验。
4. 前端接入会话参数与请求隔离，复用原模板。
5. 后端相关回归、前端测试与类型检查；服务可用时做浏览器验收，未做时明确说明。

代表案例：单产品查询后申请 50 升；批次库存/报价后申请；缺数量/用途后补齐；多规格不选第一项；跨用户/跨会话/撤权拒绝；换产品清理旧来源；预览与账本证据一致；确认前事实变化拒绝旧预览；重复确认仅一份 DRAFT；无会话及旧确认兼容。

## 交付边界

设计不代表实现或验收完成。实施仅更新直接相关运行说明和蓝图，不更新 STAR/README，不自动提交或推送。真实模型与浏览器覆盖按实际执行记录。

## 实施默认值（独立检查重点）

- 缺项需求及来源锚点保存在现有会话状态的独立 purchase_draft_bridge 命名空间，包含原始用户消息引用、已确认对象、查询锚点与状态版本；不覆盖 query_plan、batch_tasks 或 Agent 运行状态。写入沿用会话版本并发控制，不在模型调用期间持有行锁。
- 会话状态尚不可用时，不静默使用前端缓存恢复来源；按现有无会话模式整理本轮明确需求，提示重新明确对象。来源上下文不可用不能生成“继承了历史证据”的可确认提案。
- Agent/批次来源按会话消息顺序选最近一次相关查询，不能固定 Agent 优先；无明确相关对象或发生话题切换时追问，不回退到更旧的不相关成功任务。保存选定消息/任务版本，避免另一轮查询静默替换当前缺项草稿的锚点。
- 来源指纹排除 observed_at 等每次查询必变的元数据，保留实际影响参考判断的结果、来源身份、完整性/截断及范围信息。否则正常重查也会使预览永远无法确认。
- 确认前证据核验完成后，短事务再次检查提案仍为同一版本且 payload/hash 未变化；并发修订或取消不能沿用先前核验结果。已执行重放优先走现有结果回放分支，不重跑参考事实校验。
- 独立检查补充：purchase_request.create_draft 当前未列入 INBOX_ACTION_TYPES，且读取逻辑对没有既存 resource_id 的提案会隐藏差异和证据。本轮将该动作纳入本人提案列表，增加“尚未创建业务资源”的读取规则：先重验创建权限、部门与产品/单位引用、来源读取权限，再展示本人待确认草稿；不能依赖一个尚不存在的申请 ID 判断可见性。
- purchase_draft_bridge 缺项状态保存部分结构化字段、来源锚点、用户原文引用、并发版本及过期时间；默认有效期与预览一致为 10 分钟。过期需重新整理。成功转为提案或用户取消时清理对应版本，不能清掉其他请求新写入的状态。表单编辑生成新提案也保留选定来源锚点。
