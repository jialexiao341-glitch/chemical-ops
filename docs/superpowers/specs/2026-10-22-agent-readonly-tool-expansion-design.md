# Agent 跨业务只读工具扩展设计

## 目标

在不开放模型写业务数据的前提下，将采购 Agent 从库存/报价查询扩展到采购申请读取与采购订单跨模块追溯，为蓝图阶段 0 的跨业务只读能力建立首个可验证切片。

## 当前实现与约束

- `agent_tools.TOOLS` 是静态白名单注册表；`execute_tool` 集中校验 Agent 总开关、当前权限、输入 Schema 和输出 Schema。
- `capabilities.build_capability_manifest` 从同一组 ToolSpec 生成按权限裁剪的路由能力目录。
- 当前 Agent `Task`、能力预检、任务启动条件和完成证据校验围绕 `inventory`、`quotes` 设计。
- 采购申请已有 `service.list_requests` / `service.get_request`，后者重验当前用户的数据范围。
- 订单已有 `order_trace.trace_purchase_order`，先验证订单范围，再按环节权限读取申请、询价、到货、质量、库存、财务等证据；无权限环节返回不可见标记。
- 所有工具继续保持只读；写操作、模型生成 SQL、动态导入工具和由模型提供的身份/权限条件均不在范围内。

## 方案

保留静态 `ToolSpec` 注册与 `execute_tool` 执行入口，不引入动态插件平台。将目前由 `list_tools` 和能力清单硬编码的 `version`、`risk` 元数据收敛到 ToolSpec；现有四个工具的对外元数据保持 `version=1.0`、`risk=READ_ONLY`。

新增两个只读工具：

1. `purchase_requests.get_by_no`
   - 输入只接受精确 `request_no`。
   - 读取时复用采购申请领域服务的数据范围校验。
   - 输出不超过一条申请记录；无匹配或不可见时不泄露记录是否存在。
   - 暴露申请编号、用途、状态、优先级、预算金额/币种、期望日期、明细和审批节点状态；不输出审批意见或内部身份字段。
   - 权限为 `procurement.requests.read`，来源指向实际返回的申请及明细记录。
2. `purchase_orders.trace_by_no`
   - 输入只接受精确 `po_no`。
   - 复用 `order_trace.trace_purchase_order`，不得复制或简化其按环节权限和订单数据范围检查。
   - 输出保持分环节状态、可见来源、结论和不可见环节；来源只包含当前用户有权读取的记录。
   - 基础权限为 `procurement.orders.read`；每个关联业务环节仍按追溯服务当前规则独立授权。

扩展 Agent 路由任务类别 `purchase_request` 与 `order_trace`，并分别绑定上面的工具。能力 manifest 只向当前有权用户展示工具。任务启动权限门禁按账号可执行的 Agent 任务类型判断：库存/报价继续要求产品定位及相应业务读取工具；申请/订单追溯任务不要求产品目录权限。执行入口仍在每次调用时重验权限和数据范围。

规划器对新增任务只能使用对应只读工具，不能自行拼接记录 ID。完成校验要求每个请求任务都有成功的对应工具证据；明确无匹配结果是有效完成，缺少证据或调用不匹配时拒绝完成。申请与订单追溯的最终摘要使用服务端结构化结果生成；模型不改写金额、状态、日期或来源。继续保留当前单一任务目标约束，首批不支持一个任务同时混合多业务域查询。

现有针对真实订单号的专用路由与答案格式保持兼容；订单追溯工具复用同一服务，两个入口结果遵循相同权限、数据范围和证据口径。

## 错误与隐私边界

- 未登记工具、额外参数、无权限调用和无效输入按现有统一工具错误契约拒绝。
- 对申请编号或订单号无匹配、已撤权或超出当前数据范围的记录，不返回业务字段或可枚举的资源存在性信息。
- 订单各阶段无权限时，按追溯服务既有语义保留 `NO_PERMISSION` 阶段摘要，不查询受限模块记录。
- 来源与业务结果一起保存到任务轨迹；任务读取和导出继续使用既有当前权限重验。

## 验收条件

1. 已授权用户能按准确申请编号读取本人/本部门或管理范围内的申请、有限明细、审批状态及来源；无权用户不能枚举记录。
2. 已授权用户能调用订单追溯并获得与现有专用路径一致的阶段和来源；缺少关联环节权限时不泄露其数据。
3. 能力 manifest、启动门禁、模型可见工具、运行时校验和完成证据契约对两个新任务保持一致。
4. 现有库存/报价工具、产品消歧、Agent 与批次共享查询语义、真实 PO 号专用路由和任务权限回归不退化。
5. 未增加写操作，不改变数据库 Schema 或公开 HTTP API。
6. 浏览器验收按用户安排并入后续统一验收；本设计的完成不声称已完成浏览器验收或真实模型质量评测。

## 明确不做

- 泛化的动态 Tool Registry、工具自动发现或任意 Python 函数执行。
- 到货、质量、财务、供应商、异常等后续工具域。
- 模型重试、幂等写入、工具配额计费、附件、多模态、长期记忆、Agent Inbox。
- 跨业务域复合任务并行和自然语言范围搜索；本批申请与订单工具仅支持准确业务编号。

## 设计自检

- **范围覆盖**：静态工具元数据、两个新增只读工具、路由、启动权限、结果摘要、来源、完成契约与回归条件均在上述章节明确；其他工具域被列为后续事项。
- **权限一致性**：工具目录过滤只提供路由提示；执行时仍复查 RBAC 和业务数据范围；订单追溯沿用逐环节授权。
- **输出边界**：工具输入禁止额外字段；采购申请不返回审批意见或内部身份字段；编号无匹配与不可见资源不允许被枚举。
- **兼容性**：不改变现有工具元数据、订单专用路由、API、Schema 或数据库结构。
- **验证限制**：合成回归不能证明真实模型表现；浏览器验收留待统一执行。
