# 交期催办门户发送与回复设计

## 目标与已确认选择

用户选择“门户内发送与回复”。采购从已保存的催办草稿主动发送，供应商在现有门户查看并回复，采购在订单详情查看回复，形成可追踪的站内协同闭环。

以下具体行为是本次建议的实现选择，供设计确认；不代表用户已逐项确认。

## 方案比较

- **门户内发送与回复（用户已选）**：复用供应商绑定、订单权限、交期更新和站内通知；增加持久催办记录与两端入口，可跟踪发送和回复。
- 只发通知并跳转交期更新：改动较少，但不能确定某条催办是否已回复，不满足完整闭环。
- 邮件/IM：需要渠道配置、联系人核验、投递回执和外部重试边界，留待后续外部集成。

## 现有基础与约束

- `purchase_orders/followup.py` 根据当前授权订单事实生成正文和快照，只接受订单 ID 与补充说明。
- `deliveries.followup_draft` 已接入提案预览、修改、取消和确认；执行结果保存在提案账本，状态为 DRAFT、sent=false。
- `supplier_portal/service.py` 的 `_supplier_id` 要求纯供应商门户角色及有效绑定；`_require_order` 按绑定供应商隔离订单。
- 现有 `update_expected_delivery` 会校验订单状态、保存交期历史、更新未收明细并写订单事件和审计，但内部直接提交事务。
- 站内通知 `notify_users` 可参与调用方事务，不单独提交。
- 前端沿用订单详情、催办提案弹窗、供应商交期更新列表及其业务弹窗，不新增视觉模板。
- 不修改当前工作区已有的采购订单报价加载修改及其测试，不自动提交 Git；不自动更新 README 或 STAR 文档。

## 用户流程

1. 采购在订单详情准备、修改并确认保存催办草稿，既有行为不变。
2. 保存后展示“发送至供应商门户”，确认弹窗展示已保存正文及接收供应商。用户显式确认才发送；服务端校验后创建 SENT 催办记录和通知。
3. 订单详情增加催办历史入口，复用现有业务弹窗和表格，展示正文、发送时间、待回复/已回复、回复说明和回复交期；只读用户可看授权订单历史。
4. 供应商在现有“交期更新”列表行操作中查看该订单催办记录。待回复记录展示“回复催办”，复用已有 Modal、DatePicker、Input.TextArea。
5. 回复要求非空说明；预计到货日期可选。提供日期时明确提示“同时更新订单预计交期”；不提供则仅记录回复，不更改订单日期。回复成功通知发送人及订单经办人，去重。
6. 每条催办首期只接受一次正式回复；回复后只读。采购需要再次跟进时重新生成、核对并发送新草稿。无需增加关闭、撤回或多轮聊天状态。

## 持久化与状态

新增迁移 `059_delivery_followups.sql`（实施前再次确认编号未占用）及相应 ORM 模型，表置于采购订单领域。

每条记录保存：主键、订单 ID、发送时供应商 ID、来源提案 ID（唯一）、发送人、发送时间、不可修改的发送正文、发送事实快照，以及可空的回复人、回复时间、回复说明、回复预计日期、回复请求键和回复 payload hash。与现有统一时间协议一致使用 UTC 存储。

状态只包含 SENT 和 REPLIED，以回复字段和统一服务维护；数据库约束保证同一来源提案只发送一次，服务校验保证回复字段成组写入。按订单/供应商及发送时间建立查询索引。外键、字段长度和时间列风格复用现有迁移。

提案账本的执行结果仍表示“草稿已保存”，不回写 sent=true，也不把提案确认等同发送；真实发送状态以新领域记录为准。

## 接口与权限

- 采购订单下新增催办历史查询及发送接口。历史要求 `procurement.orders.read` 并调用订单范围服务；发送额外要求 `procurement.orders.write` 和 `ai.workspace.read`。
- 发送只接受本人已执行的 `deliveries.followup_draft` 提案引用、已核对预览版本及显式 confirm=true；不能提交自定义正文、供应商或收货事实。提案必须指向 URL 中的订单。
- 供应商门户订单下新增催办历史及回复接口。历史要求 `supplier.portal.delivery.read`；回复额外要求 `supplier.portal.delivery.update`，再次校验纯供应商角色、有效绑定及订单归属。
- 列表统一使用项目分页契约，页大小上限 100。返回值使用专用 Schema，供应商响应只含协同所需正文、时间、状态及回复，不返回内部提案、快照、采购审批或内部用户详情。
- `can_reply` 由服务端根据当前订单状态、待收数量、权限和催办状态计算；前端控件不是授权边界。
- 历史记录始终绑定发送时供应商；订单供应商变化后，旧供应商与新供应商都不能通过该订单读取不属于自己当前关系的记录。

## 发送、回复和并发边界

**发送**：重新检查用户权限、本人提案及订单范围后，按统一顺序锁订单再锁关联记录。仅 ORDERED/PARTIAL 且仍有待收量可首次发送。重算当前草稿事实，与保存提案的事实快照和正文核对；事实或业务日变化时拒绝，要求重新生成预览。有效门户接收人必须是当前绑定供应商、ACTIVE 用户、纯供应商角色且具备交期读取权限；无有效接收人时整笔拒绝。首次发送在同一事务保存催办、通知和审计。

同一提案的发送重试在重新鉴权后返回同一记录，不重建通知；已发送记录不会因后来日期变化而再次生成。唯一约束兜底竞争，发生竞争后回滚并按授权重新读取结果。

**回复**：同样按订单再催办的顺序加锁。订单必须仍为 ORDERED/PARTIAL、有待收量、供应商绑定未变且催办为 SENT。回复说明去空白后非空、最多 1000 字；日期如填写，使用业务日期验证并不得早于当天。将现有交期更新服务扩展为默认保持现状的 `commit=True`，回复调用 `commit=False`；交期更新、回复记录、订单事件、审计和通知在同一事务提交。

回复携带请求键；同记录、同键、同 payload 的重试在重新鉴权后返回已有结果，同键不同内容或其他再次回复返回冲突。幂等重放先于可变订单状态校验，但仍必须满足当前用户权限和供应商绑定。中途失败全部回滚，保留原 SENT 状态和原交期。

通知只放通用提示及记录引用，不含催办正文、订单金额或内部快照，避免撤权后从通知正文读取历史事实。点击通知后经当前权限重新读取：供应商跳交期更新页定位订单，员工跳订单详情定位催办；失败时给出不可访问提示，不暴露记录详情。无跳转权限的用户不接收新通知。

## 前端实现范围

- 订单详情保留“交期跟进”及提案组件；补保存后发送动作、发送确认、催办历史和回复展示。Inbox 首期仍用于保存草稿，发送从订单详情完成；返回已执行草稿时可跳转订单详情继续发送。
- 供应商交期更新页沿用 `SupplierRecordList.vue`、现有行操作、业务 Modal、日期及文本输入控件。通知携带的订单引用只能作为定位提示，列表和详情仍请求后端授权结果。
- 接口错误、重复点击、已回复或订单已结束时刷新状态；不沿用失败操作前的可执行预览。列表不展示固定演示记录。

## 验收与实现者可自行决定的事项

- 保持原草稿确认仍不发送的回归；发送必须显式确认，伪造正文/提案归属/版本或来源变化均拒绝。
- 覆盖跨供应商、失效绑定、混合角色、员工越权、未授权列表数量与详情裁剪；通知跳转也要复核权限。
- 覆盖重复发送/回复、同键不同内容、并发发送/回复、无接收人、订单终态与待收量变化、回滚后无孤立通知或部分交期更新。
- 覆盖只回复文字与同时更新交期两条成功路径，核对 UTC 时间、日期边界、订单历史与审计。
- 前端验证保存/发送边界、刷新和错误状态、无权限控件、供应商回复入口及模板一致性；执行类型检查、相关前端测试和后端回归。
- 按蓝图统一策略，浏览器验收留到功能开发结束统一进行；本轮交付说明实际运行的检查与未验证项，不能将收集成功或环境跳过算通过。
- 实现者可决定 Schema/函数命名、表格列宽、通知定位参数、内部 helper 拆分及锁冲突到现有异常类型的映射，遵守已有项目模板与事务契约。
- 本期不发送邮件/IM，不自动下单、不预测交期，不因催办或回复修改订单正式业务状态。
