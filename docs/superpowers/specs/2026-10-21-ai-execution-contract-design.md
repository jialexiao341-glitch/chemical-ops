# AI 路由与执行契约设计

> 状态：待用户审阅。本文只定义第一项架构子项目，不代表已实现或验收。

## 1. 背景与目标

专项排查报告发现，同一类采购查询可能因 `sub_tasks` 的数量和结构进入 Agent 或多意图批次；两条执行路径对日期、单位、候选选择和结果汇总的处理不同。路由理解器当前不接收按用户权限过滤后的能力清单。需要澄清时，会话状态没有持久化待回答字段，后续只能依赖有限消息历史重新推断。

本子项目建立一个服务端可验证的执行契约，使语义理解结果能够稳定映射到已授权执行器；将当前用户可用能力提供给路由模型作为上下文；并把澄清问题及待回答条件持久化，以便安全、可恢复地续接会话。

成功标准：

1. 同一份已签发的理解结果在路由、聊天和 Agent 入口中得到相同的执行策略；相互矛盾或不支持的组合在执行前被拒绝，不静默降级。
2. 路由只能选择当前用户可访问的工具和查询数据集；执行层继续逐次强制检查权限与资源范围。
3. 澄清状态跨请求持久化，有明确生命周期；用户回答被绑定到原问题和待回答槽位，过期、切换话题或答案不匹配时不会执行旧计划。
4. 现有只读护栏、证据校验、权限重验、候选选择、批次部分成功续跑和草稿确认边界保持有效。

## 2. 当前结构与约束

- `/ai/route` 调用 `routing.understand`，返回 `Understanding` 和短期 `route_token`。路由凭据绑定用户、原问题摘要和会话，但不授予工具权限。
- `Understanding.route` 当前根据 `purpose`、`tasks` 和 `sub_tasks` 数量推导执行器；`normalize` 只校验子任务类别集合与任务类别集合相等，未表达稳定的执行策略。
- 聊天服务消费路由凭据后分派 `batch`、Agent 指引、Text2SQL、文档等路径。Agent 任务可通过 `/ai/agent/tasks` 启动，并在 Runtime 内再次理解请求。
- Agent 的 `PendingChoice` 和多意图批次的 `BatchChoice` 已持久化，并已有候选版本校验及部分成功续跑；第一阶段不得替换或破坏这些既有流程。
- `AIConversationState` 已有 JSON `memory_state`、查询计划、查询轨迹、权限快照和状态版本。可以先评估在现有结构化状态中保存澄清生命周期，避免仅为一个字段引入不必要的数据库迁移；若并发写入或检索需求无法由现有结构满足，实施计划再提出最小迁移。
- 本工作区已有未提交修改：订单号解析、聚合结构化槽位、Text2SQL 权限错误优先级及相关测试。实施时应保留这些改动，并在新方案中检查兼容性。
- 项目已有工作记录将任务中心、批次续跑和部分测试门禁标记为已实现。实现前需对照当前代码验证，不重复建设。

## 3. 方案比较

### 方案 A：只调整路由提示词

通过提示词要求模型稳定选择 Agent 或批次，并将权限目录作为文本附加上下文。

优点是改动范围小；缺点是执行策略仍依赖模型输出，权限状态和澄清生命周期仍未形成可强制校验的服务端契约。不能单独满足成功标准。

### 方案 B：结构化执行策略 + 服务端能力清单 + 持久化澄清状态（推荐）

在严格理解 Schema 中显式表示执行策略及必要条件，构造按当前用户权限过滤的 `CapabilityManifest`，由服务端验证输出是否能交给目标执行器；对需要澄清的会话保存版本化状态，并在下一轮先处理待回答项。

优点是边界可测试、能与现有 route token 和会话状态衔接；风险是契约变化涉及路由、聊天、Agent、批次和前端入口，需要分阶段迁移及回归。

### 方案 C：统一重写为共享采购查询工作流

将 Agent 和批次的查询计划、候选、权限和摘要全部抽到共享流程，并由路由层只提交工作流输入。

长期一致性最好，但改动面最大，会同时触及多个已稳定的执行器和恢复状态，不适合作为第一步。可在方案 B 的行为矩阵确定后，针对重复业务逻辑逐项提取共享服务。

## 4. 推荐设计

### 4.1 执行策略成为理解契约的一部分

增加明确的 `execution_mode`，枚举为 `agent`、`batch`、`query`、`document`、`none`；非查询类目的模式必须为 `none`。`Understanding.route` 对 `purpose=query` 直接返回该模式，不再以子任务数量隐式决定 Agent 或批次。`Understanding` 校验器负责检查：

- `purpose`、`tasks`、`sub_tasks`、`execution_mode` 之间是否一致；
- 目标执行器是否支持该任务组合和槽位；
- 用户请求是否能在该模式下完整执行，不能执行的部分不得被静默丢弃。

模式约束如下：`agent` 只接受库存/报价任务且不带 `sub_tasks`，同一产品的组合库存与报价以一个 Agent 目标表达；`batch` 必须带 2–6 个原子 `sub_tasks`，由每项 `kind` 汇总得到 `tasks`；`query` 必须是单个 analytics 子任务；`document` 必须是单个 document 子任务。不能满足这些约束的模型输出在结构校验阶段重新生成一次，仍不满足则澄清且不执行。多产品独立查询采用 `batch`，避免 Agent 把多个对象折叠为一个目标。

模型输出的执行策略只用于选择流程，不作为权限凭据。目标入口必须消费同一份已签发理解结果；没有有效 route token 的直接 Agent 入口可以运行理解器，但仍通过同一 Schema 和服务端验证。

实施计划需提供一张完整的意图/执行模式矩阵，覆盖库存、报价、组合库存与报价、多产品、多条同类子任务、analytics、document、clarify、unsupported、purchase draft、取消及其混合请求。对现有 Agent 或批次无法完整执行的组合，明确拒绝或澄清，不静默切换。

### 4.2 CapabilityManifest 按用户构造

新增服务端构造器，从已存在的静态 Agent 工具注册、Text2SQL 数据集权限和用户可访问资源范围生成本轮 manifest。字段只保留模型路由所需的信息，例如能力名称、允许任务、必要权限/范围说明、可用筛选字段和是否启用；不包含数据库 ID、业务记录、密钥或完整权限主体详情。

Manifest 作为 `routing.understand` 的受信上下文传入，并在路由评测中记录其版本或稳定摘要。运行时和工具服务仍逐次重新校验权限、资源范围及业务状态。能力不存在、能力存在但无权限、输入不完整三种结果应映射为不同的拒绝或澄清语义。

### 4.3 持久化澄清状态

会话状态增加版本化 `pending_clarification`，至少保存：状态 ID、原问题摘要、待回答字段、澄清问题、有限选项（如适用）、创建与过期时间、理解契约版本。用户文本不重复复制到新增记录中；原问题继续由已有消息存储管理。

实际聊天或任务请求消费澄清回答时，服务端必须校验会话归属、当前用户权限、状态版本、有效期和回答字段。答案有效时将字段合并到新一轮理解，再生成新的执行计划；答案无效时仍停留在澄清状态。用户明确切换话题、取消或状态过期时清除 pending 状态，不恢复旧计划。

同一会话的并发澄清由状态版本控制，迟到请求不得覆盖较新的状态。Agent 候选选择和批次候选选择继续使用它们现有的任务级状态与候选版本校验；是否抽象为统一 `PendingInteraction` 留待后续子项目，第一阶段不强行合并不同生命周期。

### 4.4 兼容与迁移

- route token 继续短期有效并绑定用户、问题和会话；契约字段变更后，旧 token 按版本校验失败并要求重新识别，不尝试猜测转换。
- 旧会话没有澄清状态时视为无 pending；旧批次和 Agent 任务 payload 继续通过现有模型和版本化兼容逻辑读取。
- 只读工具、权限复验、证据来源、候选版本和草稿确认流程保持原有服务端边界。
- 本子项目不开放新的写工具，也不要求真实模型调用作为每次 CI 测试的条件。

## 5. 错误处理与安全边界

- Schema 无法解析、执行策略冲突或 Manifest 不允许目标能力：记录受控错误类别，不调用业务工具；向用户返回可操作的澄清或不支持说明。
- 执行期权限变化：以执行层当前权限为准，拒绝执行并清理不可再访问的会话记忆；不得信任路由时的权限快照。
- 澄清状态缺失、过期、版本冲突或跨会话使用：拒绝旧答案的绑定，重新识别或请用户重新发起。
- 不把用户输入、工具结果或路由模型输出提升为系统提示词或服务端授权条件。
- 结构化日志只记录策略、能力摘要、状态版本、错误类别、模型与提示词版本等必要信息，不记录业务问题和业务结果明文作为新增审计字段。

## 6. 验收与测试设计

1. 纯函数契约测试：所有意图和模式组合通过矩阵验证；非法组合被拒绝；相同 `Understanding` 始终给出相同模式。
2. 入口一致性测试：路由 token 在聊天和 Agent 启动入口复用后保持相同策略；失效、错用户、错问题、错会话 token 均不执行。
3. Manifest 测试：不同角色、权限和仓库范围得到不同能力；缺权限时路由上下文不暴露能力；撤权后执行仍被拒绝。
4. 澄清生命周期测试：跨请求续答、正确槽位绑定、无效回答、话题切换、取消、过期、并发版本冲突及会话隔离。
5. 兼容回归：现有 Agent `PendingChoice`、批次 `BatchChoice`、失败项重试/成功项保留、Text2SQL 查询计划、文档问答和草稿确认均有回归覆盖。
6. 质量门禁：离线单测和冻结数据集在 CI 可运行；真实模型评测作为发布前独立门禁，记录模型、提示词、代码和题集版本。若本机数据库测试持续挂起，先定位测试夹具或数据库可用性，不把挂起用例标记为通过。
7. 浏览器验收：检查澄清选项、继续/取消后的任务状态与现有前端模板一致；未完成浏览器验收时明确记录未验收。

## 7. 非目标与后续子项目

本子项目不实现 Tool Registry 全平台、工具重试/配额/成本治理、真实数据反馈闭环、知识库和别名、附件上传、草稿与查询证据自动衔接、价格趋势、Supervisor–Specialist、多租户、数据分级或新的写操作。这些保留在后续阶段，各自形成独立设计和验收范围。

工具结果 `planner_view` 与字符预算、错误码恢复提示、业务时区统一是紧邻的 Runtime 可靠性子项目；是否与本项目并行开发，应在本设计获批后、实施计划中安排，避免把本次 Schema/路由改动扩大成一次全平台重构。

## 8. 已知风险与待实施阶段验证项

- 现有模型是否稳定填充执行模式和能力约束，需要在当前冻结路由题集及代表性真实模型样本上验证；不能以旧 hash 报告代替。
- 当前前端 `/ai/route`、聊天和 Agent 入口的 token 传递细节需在编写计划时逐条确认，避免仅后端支持而前端绕过。
- `AIConversationState.memory_state` 是 JSON 状态；需确认数据库 JSON 大小、并发更新和会话删除清理语义适用于 pending 生命周期。
- 专项报告测试所用隔离数据库在本工作区出现挂起/跳过现象；需确认测试数据库配置后再定义完整回归命令。
- 不把专项报告中所有企业级建议视作当前必须落地能力；后续项目仍按代码证据、业务需要和风险逐项审阅。
