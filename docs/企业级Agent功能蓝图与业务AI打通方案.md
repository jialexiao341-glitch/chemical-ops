## 0. 结论

ChemicalOps 的业务 API 已经很全：采购申请、询价、报价、订单、到货、质量、库存、财务、供应商门户、异常、通知都有实际服务。**真正缺的不是业务功能，而是把业务能力安全地暴露给 AI 的“最后一公里”**：

1. Agent 当前有 10 个静态只读工具，覆盖产品、询价明细、库存、报价比较、采购申请查询、订单追溯、质量验收、到货、财务对账和供应商主数据；更深入的跨域分析与操作协同仍待扩展。
2. AI 入口包含工作台和全局可拖动的化工助手；采购申请、采购订单、到货、库存、质量验收、财务对账明细及供应商编辑抽屉已接入对象上下文。更多业务对象、列表上下文和来源跳转仍待扩展。
3. 通用“动作提案 → 用户确认 → 领域服务执行”框架已用于采购申请草稿创建/修改/提交、询价草稿创建、询价发送及中选；订单、异常处置等动作仍待开放。
4. 业务事件没有接入 AI，AI 只能被动等用户提问，不能主动发现逾期、报价过期、库存不足、发票差异。
5. 文档、质量报告、报价单、合同、发票的抽取和比对能力没有形成统一“文档智能中心”。
6. 评测、审计、成本、反馈没有形成运营闭环，无法证明“企业级可用”。

因此，建议把目标形态定为：

```text
                    ┌────────────────────────────────────┐
                    │  入口层                             │
                    │  全局化工助手 / 当前页面上下文 /    │
                    │  Agent Inbox / 通知 / 邮件与 IM      │
                    └──────────────────┬─────────────────┘
                                       │
                    ┌──────────────────▼─────────────────┐
                    │  AI 编排层                          │
                    │  上下文解析 · 能力路由 · 计划执行 ·   │
                    │  动作提案 · 人工确认 · 审计          │
                    └──────────────────┬─────────────────┘
                                       │
        ┌──────────────────────────────┼──────────────────────────────┐
        │                              │                              │
┌───────▼────────┐          ┌──────────▼─────────┐          ┌─────────▼────────┐
│ 业务工具层      │          │ 业务事件层          │          │ 知识与文档层      │
│ 只读查询/分析   │          │ 状态变化/定时扫描    │          │ SOP/合同/COA/    │
│ 动作提案/确认   │          │ 触发 Agent/待办     │          │ 报价单/发票/MSDS │
└───────┬────────┘          └──────────┬─────────┘          └─────────┬────────┘
        │                              │                              │
        └──────────────────────────────┼──────────────────────────────┘
                                       │
                    ┌──────────────────▼─────────────────┐
                    │  领域服务与权威数据                 │
                    │  采购/履约/质量/库存/财务/供应商     │
                    │  事务、状态机、权限、幂等、审计      │
                    └────────────────────────────────────┘
```

**一条原则不变**：模型负责理解、检索、归纳、准备参数和提出建议；权限、状态、金额、审批、幂等、事务和写边界由领域服务强制校验。

## 1. 现状与差距

### 1.1 业务侧已经不缺“可被 AI 调用”的能力

| 业务域 | 现有主要能力（代码可确认） | 当前 AI 暴露情况 |
| --- | --- | --- |
| 主数据/产品 | 产品、化学品、单位、供应商资料查询与维护 | 仅 `catalog.search_products` |
| 采购申请 | 创建、修改、提交、审批、驳回、取消 | 已有自然语言草稿预览、精确单号查询，以及草稿修改/提交提案；确认后调用采购领域服务 |
| 询价/报价 | 创建、发送、录入报价、生成比较、确认中选 | 已有询价明细定位、报价比较只读工具，以及从已审批申请创建询价草稿提案；发送和中选已接入确认提案与 Inbox；报价 PDF/Excel 候选解析和人工复核首期已接入报价录入弹窗 |
| 采购订单 | 创建、修改、提交、审批、下单、取消 | 已有按真实 PO 编号逐环节追溯；询价详情可通过版本化提案预览中选报价条款并显式确认创建 DRAFT 订单；订单审批、交期跟进动作与全链路验收仍待补 |
| 到货 | 到货计划、收货 | 按准确到货单号读取收货状态、预计/实际日期、短交和单证状态 |
| 质量验收 | 验收、报告上传、明细核对、人工复核、修正记录 | 已有按准确验收编号读取状态、检测记录及证书/报告状态的只读 Agent 工具；质量验收报告核对抽屉也已接入页面对象上下文问答，文档问答仍是独立能力 |
| 库存 | 余额、流水、冻结、领用、调拨、盘点、退货 | 仅按产品查可用库存 |
| 财务 | 对账、发票、票行匹配、付款、结算 | Agent 可按准确对账单号读取行级对账/匹配、发票占用与核验、来源变化及付款前置摘要；付款提交/审批仍由财务领域服务负责，Text2SQL 可查部分汇总 |
| 供应商门户 | 订单确认、交期更新、发货通知、质量资料、对账协同 | 供应商主数据支持按准确编码只读查询；门户订单、交期、质量与对账协同尚无专用 Agent 工具 |
| 运营异常 | 异常登记、任务、评论、通知 | 无 Agent 工具 |
| 补货/退货 | 补货申请、退货申请 | 无 Agent 工具 |
| Dashboard | 概览、统计报表 | Text2SQL/晨报部分覆盖 |

> 本列指 Agent/工具暴露情况；Text2SQL、文档问答、自然语言筛选、晨报等独立 AI 能力不计入本列。

### 1.2 核心差距不是“模型能力”，是产品化能力

| 差距 | 表现 | 后果 |
| --- | --- | --- |
| 工具面仍有限 | 业务服务覆盖采购履约、财务和供应商等多域，Agent 当前有 10 个只读工具 | 已能按准确编号读取部分跨模块事实，但三单匹配、供应商绩效、异常处置和完整流程协同仍未覆盖 |
| 页面上下文覆盖有限 | 全局化工助手已在采购申请、采购订单、到货、库存、质量验收、财务对账明细及供应商编辑抽屉读取当前对象 | 首批跨业务只读上下文已接入；其他业务对象、列表上下文、更多来源跳转及统一浏览器验收仍待补 |
| 动作覆盖仍有限 | 通用提案框架和首批采购动作已落地 | 当前覆盖采购申请、询价草稿、询价发送和中选；订单、异常及跨域协同动作仍待开发 |
| 没有事件驱动 | AI 只能被动回答 | 逾期、报价过期、库存不足不能主动处理 |
| 文档能力未产品化 | 有文件解析、质量报告核对、文档 RAG，但未形成统一入口 | 报价单、合同、COA、发票仍靠人工看 |
| 评测/审计不足 | 主要靠离线/合成样本，缺少线上质量和操作审计 | 无法证明企业级可靠性 |

> 上一份专项报告已经列出具体缺陷（路由、澄清、上下文、取消、真实订单号等）。本文不重复缺陷清单，只回答“功能上还要加什么”。

## 2. 功能全景：三层 Agent + 五个底座

### 2.1 三层 Agent

| 层 | 面向谁 | 典型形态 | 关键要求 |
| --- | --- | --- | --- |
| 业务副驾 | 采购员、仓库、质量、财务、供应商管理员 | 全局可拖动化工助手；在已接入的采购申请、订单、到货单及库存余额上下文读取当前对象；列表自然语言筛选 | 懂已接入对象和当前账号权限，并逐步扩展到其他页面 |
| 流程 Agent | 跨岗位的完整业务链路 | 申请→询价→比价→订单→到货→验收→对账 | 多步工具、跨模块证据、人工确认节点 |
| 主动 Agent | 管理者、业务负责人 | Agent Inbox、预警、晨报、待办 | 事件触发、去重、可解释、可关闭 |

### 2.2 五个底座

1. **业务上下文协议**：页面/单据/筛选条件/用户偏好进入 AI，但由服务端重新鉴权。
2. **统一工具与动作层**：只读工具、分析工具、动作提案、确认后写操作统一注册和治理。
3. **文档智能中心**：报价单、合同、COA/质检报告、发票、MSDS 的抽取、比对、引用。
4. **事件与主动任务**：复用 `task_queue`、`jobs`、`notifications`，把业务事件变成 Agent 待办。
5. **评测、审计与反馈**：按业务场景评估，记录模型/提示词/工具/确认/结果，形成改进闭环。

| 编号 | 功能 | 解决的问题 | 形态 | 优先级 | 当前进度 |
| --- | --- | --- | --- | --- | --- |
| F-01 | 全局化工助手与页面上下文 | 用户不想重复输入单号、条件 | 全局可拖动机器人 + 详情对话面板 | P0 | 页面上下文已接入采购申请、采购订单、到货、库存、质量验收、财务对账明细和供应商编辑抽屉；更多业务对象及统一浏览器验收待完成 |
| F-02 | 业务对象上下文协议 | AI 不知道“当前这单”是什么 | 后端 `context_refs` + 权限重验 | P0 | 对象引用协议、服务端重读和权限校验已覆盖当前已接入对象；更多业务类型和来源跳转待补 |
| F-03 | 跨模块只读工具集 | AI 只能查库存/报价 | Tool Registry | P0 | 首批基础工具已覆盖：10 个静态只读工具支持产品、询价/报价、库存、采购申请、订单追溯、质量验收、到货、财务对账和供应商主数据查询；更深入的跨域分析仍待扩展，浏览器验收待统一进行 |

| F-05 | 通用动作确认框架 | 除草稿外不能安全写业务 | 动作提案 → 确认 → 领域服务 | P1 | 首期已落地：通用提案账本、版本化预览、撤销/修改、过期与权限重验、白名单处理器、幂等重放和领域服务事务边界；支持采购申请草稿创建/修改/提交、询价草稿创建、询价发送及询价中选。草稿创建提案可承接本人已完成的库存/报价查询：服务端按会话/消息/任务引用还原产品，按当前权限重查来源事实并保存结果指纹；确认前重验事实，变化时要求重新预览；Inbox 读取按当前权限隐藏库存/报价来源。提案 Inbox 已支持这些动作的查询和处理；订单、异常等动作仍未开放；统一浏览器验收待进行 |
| F-06 | 采购申请 AI 助手 | 申请填写、体检、修改、提交 | 全局化工助手 + 确认后动作 | P1 | 首期已落地：草稿创建接入通用提案；用户完成库存/报价查询后说“按刚才的信息整理采购申请”时，服务端从本人会话的已完成任务或批次还原已核验产品，重新查询库存/报价并展示来源；缺数量、单位或用途时保留来源锚点追问，补齐后仍需显式确认。Agent 可按精确申请单号准备草稿修改和提交提案，服务端重验部门范围、状态及产品/单位引用，预览显示差异或提交阻塞项。提案 Inbox 已支持查看、修改、确认和取消修改/提交及创建提案；申请体检、附件完整性等能力及统一浏览器验收待补 |

## 4. 按业务链路的功能设计

### 4.1 采购申请：从“填单”到“AI 整理 + 人确认”

**现有基础**：`purchase_requests` 创建/修改/提交/审批/驳回/取消；`purchase_draft` 字段预览；`AIPurchaseDraftConfirmation` 一次性确认。

**建议功能**：

| 功能 | AI 形态 | 写边界 | 优先级 |
| --- | --- | --- | --- |
| 自然语言/附件生成申请草稿 | 抽取物料、数量、单位、用途、预算、期望日期、技术要求 | 只生成草稿，不提交 | P1 |
| 申请单体检 | 缺项、规格歧义、重复申请、预算超限、历史价格异常 | 只读建议 | P1 |
| 产品匹配 | 名称/别名/CAS/编码；多候选让用户选 | 不自动选 ID | P1 |
| 草稿增量修改 | 基于 `preview_version` 做字段级 patch | 重新确认 | P1 |
| 提交前检查 | 审批路径、必填字段、关联项目、附件完整性 | 用户确认后提交 | P1 |
| 申请转询价建议 | 聚合已审批未询价申请，建议询价包 | 只生成建议/草稿 | P2 |
| 申请单问答 | 在详情页问“这单还差什么/为什么被驳回” | 只读 + 来源 | P0 |

**验收要点**：未确认不提交；多候选不自动选；修改后 hash/版本失效；提交前重新鉴权；所有字段可追溯到用户输入或报价/合同来源。

### 4.2 询价与比价：从“人工组包”到“AI 组包 + 总成本比较”

**现有基础**：`rfqs` 创建/修改/发送/录入报价/生成比较/确认中选；`compare_quotes` 按可比组排名。

**建议功能**：

| 功能 | AI 形态 | 写边界 | 优先级 |
| --- | --- | --- | --- |
| 询价包生成 | 按产品、规格、供应商历史、资质、交期组包 | 生成草稿 | P1 |
| 供应商推荐 | 历史履约、质量、价格、响应速度 | 只给建议和理由 | P2 |
| 报价单解析 | 从 PDF/Excel 抽取单价、币种、单位、税率、MOQ、交期、有效期 | 生成结构化候选，人工复核 | P1 |
| 报价标准化 | 单位/币种/税率/规格差异提示 | 不强行换算 | P1 |
| 总成本比较 | 价格 + 运费 + 税率 + 账期 + MOQ + 交期 + 质量风险 | 只读比较，不自动定标 | P1 |
| 中选建议 | 推荐理由、风险点、需确认差异 | 用户确认后调用 `select-quote` | P1 |
| 询价跟进 | 截止提醒、未报价催办、报价过期 | 生成提醒/草稿 | P1 |
| 报价历史 | 同产品/供应商历史报价趋势 | 只读，注明口径 | P2 |

**验收要点**：不可比报价不排序；报价单字段抽取有引用；中选前重新校验报价有效期/状态；发送、定标都需要确认。

### 4.3 采购订单：从“生成订单”到“订单全生命周期助手”

**现有基础**：`purchase_orders` 创建/修改/提交/审批/下单/取消；`order_trace` 跨模块追溯。

**建议功能**：

| 功能 | AI 形态 | 写边界 | 优先级 |
| --- | --- | --- | --- |
| 从比价结果生成订单草稿 | 带入中选报价、供应商、数量、价格、交期 | 生成草稿 | P1 |
| 条款检查 | 价格、税率、币种、交期、收货地址、付款条件 | 只读差异提示 | P1 |
| 订单风险 | 供应商延期史、质量异常、价格偏离、重复订单 | 只读建议 | P1 |
| 订单追溯 | “卡在哪/为什么没结算/还差什么单据” | 只读，带来源 | P0 |
| 订单跟进 | 供应商确认、预计交期、发货通知 | 生成催办草稿 | P1 |
| 变更/取消建议 | 数量、交期、供应商变更影响 | 用户确认后走领域服务 | P2 |
| 审批辅助 | 生成审批摘要、风险点、关联证据 | 不代审批 | P2 |

**验收要点**：真实 PO 编号格式可用；订单追溯逐环节鉴权；提交/下单/取消不由模型直接执行。

### 4.4 到货与质量：从“事后登记”到“提前预警 + 报告核对”

**现有基础**：`deliveries` 到货计划/收货；`quality_acceptances` 验收、报告上传、只读核对、人工复核、修正记录。

**建议功能**：

| 功能 | AI 形态 | 写边界 | 优先级 |
| --- | --- | --- | --- |
| 交期预测 | 供应商交期更新 + 历史履约 + 当前状态 | 只读预警 | P1 |
| 催货草稿 | 针对逾期/风险订单生成沟通草稿 | 用户确认后发送 | P1 |
| 到货异常分诊 | 短交、逾期、单证缺失、质量异常 | 建议异常类型/任务 | P1 |
| COA/质检报告核对 | 抽取检测项、标准、结果、批次；与规格比对 | 只读 + 人工复核 | P1 |
| 验收建议 | 合格/部分合格/不合格及依据 | 人工确认结果 | P1 |
| 退货/补货建议 | 不合格数量、库存、供应商历史 | 生成草稿 | P2 |
| 质量趋势 | 按供应商/产品/检测项分析 | 只读 | P2 |

**验收要点**：报告核对有页码/章节引用；低置信字段高亮；验收结果不由模型直接提交；复检和改判走现有流程。

### 4.5 库存与补货：从“查库存”到“补货/调拨/盘点建议”

**现有基础**：`inventory` 余额、流水、冻结、领用、调拨、盘点；`replenishments` 补货；`inventory_returns` 退货。

**建议功能**：

| 功能 | AI 形态 | 写边界 | 优先级 |
| --- | --- | --- | --- |
| 补货建议 | 安全库存、在途、消耗、交期、MOQ | 生成补货草稿 | P1 |
| 缺货/积压/临期预警 | 按仓库、产品、批次 | 通知 + 待办 | P1 |
| 调拨建议 | 跨仓库存、需求、运输成本 | 生成调拨草稿 | P2 |
| 盘点差异解释 | 对比流水、冻结、退货、调拨 | 只读分析，不调账 | P2 |
| 批次追溯 | 批次→到货→验收→订单→供应商→发票 | 只读 | P1 |
| 领用合规检查 | 状态、效期、批次、权限、用途 | 只读 + 草稿 | P2 |

**验收要点**：不同计量单位不合计；建议引用当前库存/在途/历史消耗；执行调拨/盘点/领用必须确认。

### 4.6 财务：从“查报表”到“三单匹配 + 差异解释”

**现有基础**：`finance` 对账、发票、发票行匹配、付款、结算；供应商门户对账协同。

**建议功能**：

| 功能 | AI 形态 | 写边界 | 优先级 |
| --- | --- | --- | --- |
| 三单匹配 | PO/到货/发票逐行匹配数量、单价、金额、税额 | 只读差异 | P1 |
| 差异解释 | 短交、退货、价格变更、税率、运费、扣款 | 只读建议 | P1 |

## 5. 平台能力：把“功能”变成“可运营的产品”

### 5.1 业务上下文协议

前端只传引用，不传可信业务快照：

```json
{
  "object_type": "purchase_order",
  "object_id": 123,
  "page": "purchase-order-detail",
  "visible_filters": {"status": "PARTIAL"}
}
```

服务端负责：读取对象、重新鉴权、裁剪字段、生成 AI 上下文。这样避免前端状态过期和越权。

**已落地切片（F-01/F-02，采购申请、订单、到货、库存、质量验收、财务对账及供应商主数据）**：`POST /ai/context/ask` 只接受 `question` 与 `{object_type, object_id}`，不接受客户端业务快照。服务端按当前用户重新读取已接入对象；订单复用跨模块追溯，申请可追溯审批节点、询价/报价、采购订单及订单后续环节。到货单上下文检查 `warehouse.deliveries.read` 并复用到货服务的订单范围校验，只汇报收货日期、数量、短交及单证状态，不推断质检或库存入库状态。库存余额上下文检查 `warehouse.inventory.read` 并复用库存服务的仓库数据范围校验，回答余额、锁定量、按既有库存查询口径计算的可用量、批次和有效期。质量验收上下文检查 `quality.acceptances.read` 并复用验收服务的数据范围校验，只复述已保存的验收状态、证书和检测结果，不根据报告内容或检测标准重新判定。财务对账上下文复用财务只读行级读模型，并按当前账号重新检查对账、发票和付款读取权限；供应商编辑抽屉上下文按供应商主数据读取权限复读合作主数据。所有已接入对象均由服务端按权限重新读取，不接受客户端业务快照。前端全局可拖动化工助手按当前页面登记的对象引用打开可拖动调宽的对话面板；已接入采购申请、采购订单、到货单详情、库存余额状态变更记录抽屉、质量验收报告核对抽屉、财务对账明细抽屉及供应商编辑抽屉。没有当前对象上下文时，助手入口导航到 AI 工作台；更多业务对象和列表上下文仍待扩展，`page`、`visible_filters` 等前端提示字段不作为可信业务事实。浏览器验收统一留待需求开发完成后进行。

### 5.2 统一工具与动作层

建议在现有 `ToolSpec` 基础上扩展元数据：

```text
name / version / description
kind: read | analyze | propose | write
risk: READ_ONLY | LOW | MEDIUM | HIGH
permission / resource_scope
input_schema / output_schema
timeout / retry / idempotency / rate_limit
requires_confirmation
audit_fields
```

只读工具直接执行；`propose` 只生成动作提案；`write` 必须经过确认快照和领域服务。

### 5.3 通用动作确认框架

复用 `AIPurchaseDraftConfirmation` 的模式，抽象为通用表：

```text
action_type, resource_type, resource_id, expected_version,
payload, payload_hash, diff, risk_level, required_permission,
confirmation_id, preview_version, expires_at, idempotency_key,
status, result, executed_at
```

流程：

```text
AI 生成动作提案
→ 展示“做什么、改什么、依据、风险、影响”
→ 用户确认
→ 服务端重新鉴权/校验版本/状态
→ 调用领域服务
→ 保存审计结果
```

**首期实现说明**：当前通用账本保存 payload/hash、预览版本、业务引用快照、差异、证据、阻塞项、权限、幂等键及执行结果。用户确认必须携带当前版本和显式 `confirm=true`；服务端按白名单解析处理器，重新校验用户状态、权限、数据范围、业务状态及引用快照，再通过支持 `commit=False` 的采购申请/询价领域服务执行，并在同一事务保存结果。Agent 路由只准备提案，确认仅由前端用户操作触发。首期动作支持采购申请草稿创建/修改/提交、基于已审批申请创建询价草稿，以及询价发送和中选。`/ai/tasks` 的提案 Inbox 已增加本人提案列表/详情读取，覆盖采购申请修改/提交、询价草稿、询价发送和中选；详情展示差异、证据、阻塞项、有效期与可用性，并沿用现有修订、确认、取消接口和预览版本。中选理由可在 Inbox 修改；资源不可访问时隐藏单号、证据和入口，读取时识别过期、资源变化和权限失效。采购申请创建提案还可承接本人已完成的库存/报价查询：服务端按会话消息中的任务或批次引用还原已核验产品，不使用客户端证据快照；缺项时在会话状态保存来源锚点与已收集需求，补齐后重新查询并保存来源事实及结果指纹，确认前再次按当前权限核验，事实变化要求重新预览。Inbox 对创建提案按“待创建采购申请”展示，缺少来源读取权限时隐藏库存/报价证据。询价录入弹窗已接入报价文件解析候选，复用现有 PDF/Excel 文本解析和 MinerU OCR 回退；仅保留可由原文引句定位的候选字段，报价来源文件记录在报价单，用户必须复核并主动提交。总成本分析、订单及异常等动作仍待开发。浏览器验收统一留待需求开发后进行。

首批适用：修改采购申请草稿、提交采购申请、创建询价草稿、发送询价、确认中选、创建订单草稿、提交订单审批、创建异常任务、生成催货/对账留言草稿。

### 5.4 事件与主动任务

复用 `task_queue`、`jobs`、调度器、`notifications`，新增“AI 触发规则”：

| 事件 | 触发 | AI 输出 |
| --- | --- | --- |
| `purchase_order.overdue` | 预计到货日超过今天 | 逾期清单、催办草稿、异常建议 |
| `quote.expiring` | 报价有效期临近 | 提醒、替代供应商建议 |
| `inventory.below_safety` | 低于安全库存 | 补货建议、紧急度 |
| `inventory.expiring` | 批次临期 | 处理建议 |
| `invoice.mismatch` | 票行/三单差异 | 差异解释、待确认项 |
| `reconciliation.disputed` | 对账争议 | 争议摘要、回复草稿 |
| `quality.failed` | 验收不合格 | 异常任务、退货/补货建议 |
| `delivery.updated` | 供应商更新交期 | 影响分析、通知相关人 |

要求：幂等键去重、可关闭、可转人工、通知可配置、不在事件中自动执行高风险写操作。

### 5.5 语义层与实体解析

- 指标口径：采购金额、逾期、合格率、库存可用量、对账完成、付款账龄。
- 业务术语：状态、角色、权限、单据关系。
- 实体别名：产品俗名/英文名/CAS/编码、供应商简称、仓库简称、真实订单号格式。
- 时间口径：统一使用业务时区（Asia/Shanghai），不要用服务器本地 `date.today()`。

### 5.6 文档智能

- 解析：PDF/Excel/Word/扫描件；MinerU 优先，失败回退。
- 抽取：字段 + 值 + 单位 + 条件 + 页码/章节。
- 比对：与业务记录逐字段/逐行比对。
- 复核：低置信高亮、人工修正、版本留痕。
- 引用：回答中显示文档、版本、章节/页码。

### 5.7 记忆与个性化

- 会话摘要：长对话不只看最近 8 条。
- 用户偏好：常用仓库、单位、供应商、关注指标。
- 任务记忆：最近任务、待确认、已忽略建议。
- 数据边界：记忆按用户/部门隔离，可清除。

### 5.8 评测、可观测与审计

| 维度 | 指标 |
| --- | --- |
| 意图/路由 | 路由准确率、澄清率、拒绝率、转人工率 |
| 工具 | 工具选择正确率、参数正确率、成功率、超时率 |
| 业务 | 字段抽取准确率、对象匹配率、动作正确率、人工修改率 |
| 回答 | 事实正确性、引用有效率、拒答率、无依据输出率 |
| 运营 | 任务完成率、平均耗时、Token 成本、队列等待、失败率 |
| 安全 | 越权拒绝、确认绕过、重复执行、敏感数据泄露 |

审计记录：用户、角色、任务、上下文、模型/提示词版本、工具调用、动作提案、确认人、执行结果、业务单号。

### 5.9 安全与治理

- 权限链：身份 → 功能权限 → 组织/部门 → 供应商绑定 → 资源 → 状态。
- 写操作分级：只读 → 草稿 → 提交审批 → 正式下单/付款。
- 敏感字段按角色脱敏；文档/工具结果视为不可信数据。
- 保留期、法务保留、导出审计、模型供应商风险。
- 不允许模型直接写 ORM、执行任意 SQL、自动审批/付款。

### 5.10 外部集成

- 邮件/企业微信/钉钉：接收需求、发送提醒、审批通知。
- 供应商门户：供应商侧助手、询价回复、交期更新、质量资料、对账协同。
- ERP/财务系统：通过受控适配器，不在 Agent 内直连数据库。
- Webhook/API：业务事件推送给 AI 编排层。

### 5.11 化工助手入口与页面上下文

“打通”不仅是工具数量，还包括用户在哪里遇到 AI。建议统一为四类入口，复用项目现有页面、弹窗和抽屉模板：

| 入口 | 使用场景 | 交互 |
| --- | --- | --- |
| 详情页上下文 | 采购申请/订单/询价/库存/财务详情页 | 全局化工助手自动绑定当前单据，回答“解释这单、还差什么、相关单据” |
| 列表助手 | 各业务列表页 | 自然语言筛选（复用 `nl_filters`）、批量摘要、异常提示 |
| 全局助手 | 工作台或全局悬浮入口 | 跨模块问答、任务发起、任务中心入口 |
| Agent Inbox | 通知中心/独立页面 | AI 发现的待办、待确认动作、异常处置；接受/忽略/转人工 |

产品入口统一称为“化工助手”，不再把 Copilot 作为单独功能区：全局可拖动机器人是唯一常驻入口；位于已接入业务对象页面时按登记的对象类型和 ID 请求服务端重新授权并读取上下文、附带来源，目前已接入采购申请、采购订单、到货单、库存余额、质量验收、财务对账明细和供应商编辑抽屉。其他业务对象及列表上下文仍是后续能力，不因显示全局入口而视为已经实现。`/ai/tasks` 已提供任务与提案入口；提案详情复用现有 Modal、表格及控件模板，支持查看、状态刷新和按权限处理。界面沿用项目既有模板并支持面板拖动调宽。

**建议的页面级快捷动作**：

- 采购申请详情：`检查缺项`、`匹配产品`、`生成询价建议`、`提交前检查`。
- 询价详情：`解析报价单`、`总成本比较`、`生成中选建议`、`催办未报价`。
- 订单详情：`解释卡点`、`检查条款`、`生成催办`、`追溯关联单据`。
- 到货/质量：`核对 COA`、`分诊异常`、`生成处理任务`。
- 库存：`补货建议`、`临期处理`、`批次追溯`、`调拨建议`。
- 财务：`三单匹配`、`解释差异`、`生成对账草稿`、`付款前置检查`。

## 7. 分阶段路线

### 阶段 0：2–4 周，先把“能看见业务”做好

**目标**：AI 从工作台走进业务页面，能回答“当前这单/这个列表”的问题。

**当前状态**：首批页面上下文、跨业务只读工具、任务操作及任务/提案 Inbox 已落地，提案 Inbox 覆盖采购申请修改/提交、询价草稿、询价发送及中选；列表上下文、通知和跨用户待办仍待补，统一浏览器验收按需求完成后进行。

1. 已完成采购申请、采购订单、到货单、库存余额、质量验收、财务对账明细及供应商编辑抽屉的对象上下文接入；其他业务对象、列表上下文和更多来源跳转待补。
2. 已有 10 个静态只读工具，覆盖产品、询价/报价、采购申请、订单追溯、到货、质量、库存、财务和供应商主数据；更深入的异常和跨域分析工具待扩展。
3. 任务中心已支持查看、导出、等待补充后继续、运行中取消、失败后以首次查询新建任务。Inbox 已汇总本人等待补充/失败任务及采购申请修改/提交、询价草稿、询价发送和中选提案；通知推送、跨用户待办和异常处置入口待补。
4. 真实订单号识别、聚合全选、上下文溢出及取消/续跑相关问题已有代码修复和专项回归；仍需完成统一浏览器验收。
5. 已有离线评测、运行轨迹、工具护栏和专项回归基线；当前提示词/运行时完整基线重跑、在线质量/成本指标和真实模型评测仍待完善。

**验收**：在业务页面问“这单为什么没结算/还差什么/这家供应商延期多少”，能返回带来源的答案，并能跳转对应单据；不出现越权。

### 阶段 1：1–2 个月，让 AI 开始“能办事”

**目标**：采购核心链路（申请→询价→订单）有 AI 参与，但每一步可确认、可撤销。

**当前状态**：通用动作框架及采购申请草稿创建/修改/提交、询价草稿创建、询价发送、中选和从中选报价生成订单草稿已接入版本化提案；提案 Inbox 支持这些提案查看与处理。报价解析已接入报价录入弹窗并提供原文依据和人工复核；总成本拆解与有明确条件的成本候选/中选建议已落地。订单草稿条款预览包含逐行付款条件快照、剩余量与缺项提示；订单审批、交期跟进、申请到询价到订单的全链路业务验收及统一浏览器验收仍待完成；报价解析还需专项验收。

1. 通用动作确认框架。
2. 采购申请：自然语言/附件生成草稿、字段级修改、提交前检查、确认后提交。
3. 询价：生成询价草稿、报价单解析、总成本比较、确认后发送/中选。
4. 订单：从比价结果生成订单草稿、条款检查、确认后提交审批。
5. 文档智能：报价单、COA/质检报告、发票。
6. 主动预警：逾期、报价过期、库存、发票差异；接入通知。

**验收**：用户从“我需要采购 50 升乙醇”到“申请草稿→询价草稿→比价建议→订单草稿”可走通；每一步有证据、可修改、需确认；未确认不写入。

### 阶段 2：一个季度，做“跨模块闭环”

**当前状态**：财务只读三单匹配和付款前置摘要首期已落地；供应商绩效/风险、协同助手、异常主动处置、补货调拨建议及完整版事件驱动 Inbox 仍待开发。

1. 财务三单匹配、对账草稿、争议留言、付款前置检查。
2. 供应商绩效/风险、供应商门户助手。
3. 到货/质量异常主动处置、根因链。
4. 补货/调拨/盘点建议。
5. 管理驾驶舱问答、角色化晨报。
6. 事件驱动 Agent + Agent Inbox 完整版。

**验收**：从订单到付款的跨模块问题能一次追溯；财务差异有解释；异常能生成任务；供应商侧可自助查询/协同。

### 阶段 3：按需扩展

- 多 Agent/Supervisor–Specialist：只在独立数据域、并行长任务、独立权限边界出现时拆。
- 多组织/多租户、数据分级、法务保留、外部 ERP/IM 集成。
- 行情/价格趋势、供应商风险模型等高级分析，先只读、可追溯、后预测。

## 8. 衡量“打通”的指标

不要用“聊天次数”衡量价值。建议从业务流程取指标：

| 类别 | 指标示例 | 说明 |
| --- | --- | --- |
| 效率 | 申请到询价、询价到订单、异常响应、对账处理时长 | 需与改造前基线对比 |
| 质量 | 字段抽取准确率、对象匹配率、动作参数正确率、人工修改率 | 按业务场景分层 |
| 采纳 | 建议采纳率、草稿采纳率、AI 任务完成率、转人工率 | 不用点击量代替 |
| 风险 | 越权拒绝、确认绕过、重复执行、无依据输出 | 高风险门禁零放行 |
| 成本 | 单任务 Token/费用、平均耗时、队列等待 | 按模型/场景统计 |
| 体验 | 化工助手使用率、任务中心处理率、用户反馈 | 需真实用户样本 |

所有指标注明样本范围、时间窗口、环境、模型/提示词版本；不能把合成样本或聊天次数写成业务收益。

## 9. 边界与不建议做的事

1. **不让模型直接写业务库/ORM**：所有写操作走领域服务，统一权限、状态机、幂等、审计。
2. **不自动审批、不自动下单、不自动付款**：AI 可以准备材料、给建议、生成草稿；最终动作由有权限的人确认。
3. **不为“多 Agent”而多 Agent**：先把确定性工作流、工具层、上下文、确认框架做好；独立专家 Agent 按真实边界拆。
4. **不把聊天框当唯一入口**：全局化工助手、通知、Agent Inbox 更贴近业务。
5. **不用关键词分支堆意图**：能力目录、结构化上下文、工具契约优先。
6. **不让模型生成无来源的数字/结论**：库存、价格、金额、状态、日期必须有业务证据。
7. **不把 AI 建议等同于业务决定**：推荐、评分、风险提示都需标注依据和限制。
