# 运行、部署与构建手册

启动与测试、部署与数据库恢复、任务队列、前端构建的合并说明；按“本地运行 → 部署 → 队列 → 前端构建”顺序阅读。

## 运行、体验与测试指南

### 1. 运行前准备

#### 必需组件

- Windows PowerShell（下文按仓库现有脚本写法）；
- Python 运行环境及项目依赖（仓库配置使用 `uv`，亦可按 `backend/requirements.txt` 安装）；
- MySQL 8.0 或兼容版本；
- Node.js 与 Corepack/pnpm（pnpm 版本要求见前端构建说明）；
- 若使用对象存储、AI 或文档解析功能，另需 MinIO、模型 API 或 MinerU 服务及对应配置。

#### 获取配置

在仓库根目录执行：

```powershell
Copy-Item .env.example .env
```

按 `.env.example` 的字段填写数据库连接、JWT 密钥、前端环境、文件存储以及需要的外部服务凭据。不要把 `.env` 或真实凭据提交到版本库。默认后端端口为 `8888`；前端 Vite 代理将 `/api` 与 `/health` 转发到该后端地址。若本机端口或服务地址不同，应同时调整环境配置与前端代理配置。

### 2. 数据库初始化或升级

#### 全新空数据库

先在 MySQL 创建空数据库并按脚本要求准备 `.env` 中的数据库与管理账号配置，然后：

```powershell
uv run python scripts/init_database.py
```

初始化脚本会拒绝对已有表的数据库重建。`database/schema.sql` 本身含有 `DROP TABLE`，不得直接对含数据环境执行。

#### 已存在数据库

先查看版本状态，再升级：

```powershell
uv run python scripts/migrate_database.py status
uv run python scripts/migrate_database.py upgrade
```

升级默认先运行 `mysqldump` 备份。Windows 未安装或 PATH 找不到时，安装 MySQL 客户端工具，或在 `.env` 中配置 `MYSQLDUMP_PATH` 指向 `mysqldump.exe`。备份失败时迁移不会继续；仅对可丢弃的本地数据库，才考虑脚本支持的 `--no-backup`。迁移发布后不应修改旧迁移文件，应新增迁移。

### 3. 准备演示数据与账号

以下脚本会向当前 `.env` 指向的数据库写入数据。仅在本地/隔离开发库运行。为脚本导入后端模块，PowerShell 中先设置后端模块路径：

```powershell
$env:PYTHONPATH = "$PWD\backend"
uv run python scripts/seed_admin.py
uv run python scripts/seed_demo_accounts.py
uv run python scripts/seed_demo_master_data.py
```

先在 `.env` 设置 `ADMIN_PASSWORD` 与 `DEMO_DEFAULT_PASSWORD`。管理员用户名来自 `ADMIN_USERNAME`，演示账号使用 `DEMO_DEFAULT_PASSWORD`；脚本会输出实际创建的用户名。账号已存在时，演示账号脚本不会重置其密码。管理员脚本会创建/补齐管理员角色和权限。完成后使用管理员或演示账号登录，建议立即更改口令。

### 4. 启动依赖服务（可选）

MinIO 配置文件：

```powershell
docker compose -f deploy/docker-compose.minio.yml up -d
```

依照 `.env` 中的 endpoint、bucket 和凭据配置使用；对象存储模式启用时需确保所需桶可用。AI 与 MinerU 服务使用时，按 `.env.example` 填写对应 URL/API key；项目不会在未配置时自动提供第三方服务。

停止 MinIO：

```powershell
docker compose -f deploy/docker-compose.minio.yml down
```

### 5. 启动后端

在仓库根目录：

```powershell
uv run main.py run --env=dev
```

开发配置默认监听 `127.0.0.1:8888` 并启用热重载，同时启动资料与 Agent 独立 Worker，默认从 MySQL 持久队列领取任务；退出开发入口时 Worker 一并停止。直接运行 Uvicorn 或生产入口时，需单独托管两类 Worker，见 [队列运行说明](运行、部署与构建手册.md)。生产配置监听地址与是否重载不同，部署使用前需核对配置和安全设置。

启动后可验证：

- API 文档：`http://127.0.0.1:8888/docs`
- OpenAPI JSON：`http://127.0.0.1:8888/openapi.json`
- 健康检查：`http://127.0.0.1:8888/health/live`、`/health/ready`

就绪检查需要的依赖可能与存活检查不同；以返回状态和服务日志判断。

### 6. 启动前端

首次安装依赖：

```powershell
corepack prepare pnpm@11.16.0 --activate
corepack pnpm --dir frontend-design install
```

启动 ChemicalOps 前端：

```powershell
corepack pnpm --dir frontend-design dev:chemicalops
```

浏览器打开 `http://localhost:3000`。前后端应同时运行，Vite 代理负责将 API 请求转给本机 8888 端口。依赖安装、构建环境问题另见 [运行、部署与构建手册](运行、部署与构建手册.md)。

### 7. 建议体验顺序

1. 登录后确认首页 Dashboard 能加载；若无数据，按需装载演示主数据。
2. 查看/维护化学品、产品规格和供应商主数据；初始开发库可运行 `seed_demo_master_data.py` 创建演示单位、供应商、化学品、产品和仓库库位。
3. 创建采购申请并提交审批；使用询价、报价录入、报价比较和定标接口/页面（仅在相应功能和权限可用时）。
4. 建立或查看采购订单，按状态执行审批、下单或取消。
5. 登记到货并确认收货；在质量验收单上传报告、选择到货明细执行报告核对，查看产品检测标准、原文依据和人工复核历史，再由检验员提交正式验收结果。标准需由有产品维护权限的人员先行配置，不应把演示报告当作正式标准。
6. 对合格数量执行库存入库；查看批次、余额及交易流水。
7. 在测试数据上体验领料、调拨、盘点、退货、效期预警与 FIFO 出库。执行性操作会改变库存，应使用隔离数据库。
8. 体验财务对账、发票人工审核、付款审批/人工已付款登记和结算确认；这些是系统业务记录，不代表真实支付。
9. 体验异常任务、通知与 AI 工作台：提问业务数据或化学品资料，查看来源和图表；用斜杠菜单试自然语言筛选、运营晨报和采购申请草稿预览。草稿仅在再次确认后创建，随后仍需在采购申请模块提交审批。
10. 在库存、订单、异常、化学品、供应商、询价与盘点等页面打开“业务分析”入口，核查证据、建议和数据限制。MSDS 入口只比较已解析章节文字，不代表合规审查；工作台尚不能直接选择附件提问。

### 8. 测试与构建

后端测试（数据库配置满足测试要求后）：

```powershell
uv run pytest --strict-config --strict-markers -q -rs
```

AI 离线护栏可单独运行 `uv run python scripts/evaluate_ai.py`；RAG 合成题评估的范围和结果见 [RAG 混合评估报告](evaluation/评测原始证据-20261009.zip)。离线测试与合成题不能代替真实检验报告、业务单据、角色权限和外部模型服务的现场验证。

前端生产构建：

```powershell
corepack pnpm --dir frontend-design build:chemicalops
```

测试可能连接 MySQL 并创建/清理测试数据；先核对 `.env` 与 `tests/conftest.py` 的数据库目标，避免指向个人或生产数据。若 DB 不可用，有些测试会跳过；仅看到命令成功不能说明所有数据库测试均执行。

### 9. 从启动到停止的完整闭环

```text
配置 .env
  → 启动/连接 MySQL
  → 空库初始化或现有库迁移
  → 按需准备演示数据与 MinIO/AI 服务
  → 启动后端并检查健康端点
  → 启动前端并登录
  → 按采购 → 到货 → 质量 → 库存 → 财务/运营顺序体验
  → 运行测试或前端构建
  → 保存需要的数据/日志
  → Ctrl+C 停止前端和后端；按需停止 MinIO
```

数据库备份恢复属于运维操作。`scripts/restore_mysql.py` 的恢复命令会覆盖目标数据库风险范围内的数据，必须指定隔离库、确认目标并遵循脚本的确认参数；不要对正在使用的生产库做试恢复。

### 10. 常见故障排查

| 现象 | 检查方向 |
|---|---|
| 数据库连接失败 | `.env` 的主机、端口、库名和账号；MySQL 服务状态；当前环境实际加载的 env 文件。 |
| 迁移因备份失败停止 | 确认 `mysqldump.exe` 安装及 `MYSQLDUMP_PATH`；脚本明确会在失败时停止迁移。 |
| 前端 API 请求失败 | 后端是否监听 8888、Vite `/api` 代理目标、CORS/环境配置。 |
| 登录失败 | 账号是否存在/启用、口令是否正确、失败锁定策略以及数据库是否完成所需迁移。 |
| 文件上传或下载失败 | 文件存储 backend、MinIO endpoint/凭据/bucket、文件大小和类型限制及对象权限。 |
| AI/解析不可用 | API key、模型/MinerU URL、网络连通性、服务端配置和日志。 |
| 首页没有业务数据 | 当前连接的数据库、演示数据是否已加载、请求筛选条件和用户权限。 |


### 开发数据边界与维护

本地 `chemicalops` 数据库中的采购、到货、质检、库存和财务记录用于走通产品流程。化学品身份资料来自独立导入；采购订单、验收、库存、发票和付款等业务事件是**合成记录**，不能作为真实交易、检测、库存或资金划转的凭证。应用整体的开发环境提示应保留。

### 页面文案

业务列表和详情按记录本身的状态写明处理结果。验收结论分别说明已验收、短交待补交、随货证明待补齐；备注描述采购用途、到货核对、库存流转和财务核对。单据号使用各业务模块的编号格式，避免把数据生成脚本的 `SCN`、`SIM` 标记直接显示在业务页面。

文案只依据已有字段写作。没有检验报告或银行回单时，不补造检测数值、票据图片、银行流水或供应商承诺。与这些记录有关的历史 AI 会话保持原样，作为当时查询的历史内容。

#### 数据维护

存量修订脚本：`scripts/refine_development_records.py`。它只接受本机 development 环境的 `chemicalops` 数据库，并要求一小时内完成的完整备份。先用 `scripts/backup_development_database.py` 保存快照，再传入备份路径；默认预览变更，带 `--apply` 才提交。

未来扩充业务记录由 `scripts/extend_curated_dataset.py` 和 `scripts/expand_curated_dataset.py` 生成，文案与编号统一由 `scripts/curated_record_copy.py` 提供。重新生成数据时仍须保留本页和应用层的合成数据说明。

## ChemicalOps 部署与数据库恢复

本文说明如何使用完整 Compose 启动 API、前端、数据库、缓存、向量库、对象存储、病毒扫描器、后台 Worker 和 TLS 反向代理。真实运行前准备独立的生产环境文件、TLS 证书和持久数据目录；示例值不能代替生产密钥。

### 配置与启动

1. 从 `.env.example` 整理一份**独立且不入库**的生产变量文件。至少设置强随机 `JWT_SECRET_KEY`、MySQL 与 MinIO 凭据、正式 `APP_ENV=production`、模型服务凭据和存储桶名称。不得复用测试密码。
2. 准备内部 CA 文件、包含 `public.crt` 与 `private.key` 的 MinIO TLS 目录，以及反向代理使用的 `fullchain.pem` / `privkey.pem`。MinIO 证书 SAN 必须包含 Compose 服务名 `minio`。
3. 准备 `BACKUP_DIR` 主机目录；运行 API/迁移容器的 UID 10001 必须可写。首次部署前单独备份并验证 MySQL 数据目录。
4. 反向代理与 API 使用独立的 Docker 网络；Uvicorn 只信任代理固定地址。默认地址和网段为 `PROXY_API_IP=172.30.0.2`、`PROXY_API_SUBNET=172.30.0.0/24`、`PROXY_FRONTEND_SUBNET=172.31.0.0/24`。如果与主机或现有 Docker 网络冲突，请在独立环境文件中替换为两个互不重叠且未占用的网段，并将 `PROXY_API_IP` 设为第一个网段内的未占用地址。
5. 用环境变量 `CHEMICALOPS_ENV_FILE`、`INTERNAL_CA_FILE`、`MINIO_TLS_DIR`、`TLS_DIR` 和 `BACKUP_DIR` 指向上述绝对路径，然后从仓库根目录检查和启动：

   ```sh
   docker compose --env-file /secure/chemicalops-compose.env -f deploy/compose.full.yaml config --quiet
   docker compose --env-file /secure/chemicalops-compose.env -f deploy/compose.full.yaml up --build -d
   docker compose --env-file /secure/chemicalops-compose.env -f deploy/compose.full.yaml ps
   ```

   入口绑定在本机 `127.0.0.1:8443`（可用 `HTTPS_PORT` 调整）。生产入口应由主机防火墙或外层负载均衡按实际部署要求暴露；MySQL、Redis、Qdrant、MinIO 和 API 没有宿主机端口映射。
6. 通过 `https://127.0.0.1:8443/health/ready` 检查就绪状态，并在部署环境中验证登录、文件上传/下载、病毒扫描、队列 Worker、模型调用和前端深链刷新。若外部 CA 不受本机信任，使用部署签发的客户端信任配置；不要关闭 TLS 校验。

数据库迁移容器在 API 启动前运行，使用校验和台账并默认生成逻辑备份。备份持久写入 `BACKUP_DIR`；保管策略、异地副本、加密和恢复演练由部署环境负责。Compose 不会替代这些操作。

### 备份与隔离恢复

手动生成一份逻辑备份：

```sh
docker compose --env-file /secure/chemicalops-compose.env -f deploy/compose.full.yaml run --rm migrate python scripts/backup_mysql.py
```

恢复前先停止所有可能写数据库的 API、Worker 和调度任务。把待恢复数据库恢复至**预先创建且与当前配置库不同名**的隔离库，并人工确认备份来源与校验值：

```sh
docker compose --env-file /secure/chemicalops-compose.env -f deploy/compose.full.yaml run --rm migrate \
  python scripts/restore_mysql.py /app/backups/mysql/<备份文件>.sql \
  --database chemicalops_restore_test --confirm
```

恢复脚本会拒绝 SQL 中的 `USE`、数据库级 DDL 和点号限定标识符（包括库表名和 `table.column` 形式）。这是对常见直接重定向的检查，不是 SQL 沙箱；仅恢复可信的 ChemicalOps 逻辑备份。不可信来源应在独立 MySQL 实例和无生产权限的账户中人工核查。包含点号限定表达式的可信备份也需在隔离实例中检查恢复。隔离库恢复完成后，应在隔离配置下执行迁移状态检查、业务抽查和应用连通测试。恢复到正式库需单独备份、停写、审批并显式使用 `--allow-configured-target`；该选项不能用于常规验证。

### 已验证边界

自动化测试检查 Compose 服务与端口暴露、迁移重复执行、受保护的恢复目标以及数据库切换拒绝。它们没有证明本指南中的空环境 Compose 启动、TLS/对象存储信任链、病毒扫描连通性或完整备份恢复演练已在生产环境执行。首次部署和恢复均需在隔离环境完成演练后再安排上线。

## 数据库任务队列运行说明

2026-10-09：异步任务改用 MySQL 持久任务表和独立 Worker，移除 RabbitMQ 客户端、部署配置和投递器。API 同事务保存业务状态和执行记录，Worker 直接领取到期的 QUEUED/RETRYING 记录，无需 Redis 或其他消息服务。

### 启动

先备份数据库，再使用现有工具升级至当前最新迁移。迁移 042 增加队列领取索引，迁移 050 增加执行尝试起止时间及完成时间索引；不删除旧任务、checkpoint、资源锁或 task_outbox 投递历史；历史迁移保持原样，避免破坏校验台账。

```powershell
.venv/Scripts/python.exe scripts/migrate_database.py status
.venv/Scripts/python.exe scripts/migrate_database.py upgrade
```

默认两类执行模式均为 `database`。日常开发只需运行以下入口，它会启动 API 和对应的资料/Agent Worker；API 热重载不会重复创建 Worker，退出入口时停止 Worker。不要同时手动启动重复 Worker。

```powershell
.venv/Scripts/python.exe main.py run --env=dev
```

生产模式 `main.py run --env=prod` 或直接启动 Uvicorn 时，Worker 需由进程管理器单独运行。API 与 Worker 必须使用同一数据库，分别运行：

```powershell
.venv/Scripts/python.exe scripts/run_task_worker.py --queue documents
.venv/Scripts/python.exe scripts/run_task_worker.py --queue agent
```

后端 `.env` 默认配置如下；旧配置若显式设置为 `in_process`，需修改并重启开发入口：

```dotenv
TECHNICAL_DOCUMENT_EXECUTION_MODE=database
AGENT_EXECUTION_MODE=database
TASK_POLL_INTERVAL_SECONDS=1
TASK_DOCUMENT_CONCURRENCY=1
TASK_AGENT_CONCURRENCY=1
TASK_MAX_ATTEMPTS=3
TASK_LEASE_SECONDS=60
TASK_HEARTBEAT_SECONDS=10
```

两类模式默认均为 `database`，可独立显式回退为 `in_process`。未启动 Worker 时，database 模式接受的任务保存在数据库中等待执行。并发配置是每个 Worker 进程的上限，多个进程的并发相加。轮询间隔可设为 0.1–60 秒，空队列也会轮询。

排队任务超过 `max(30 秒, 2 × 租约秒数)` 仍未被任何 Worker 领取时，读取任务接口会把该执行标记为 `FAILED`、任务标记为 `WORKER_UNAVAILABLE` 并结束等待，提示检查 Worker 后重新发起；已领取或刚排队的任务不受影响，避免前端无限显示“正在查询”。

### 状态与恢复

- `async_task_executions` 保存执行状态和 `error_code`；新任务不再写入或消费 `task_outbox`，没有消息 ACK 或失败消息队列。
- Worker 使用事务行锁和 SKIP LOCKED 领取任务，完成后不会再领取。重试默认最多三次，退避 30/120 秒。
- 保留业务适配、权限检查、取消、租约、fencing token、checkpoint 和子进程监督。外部模型调用仍可能重复计费。
- 长期 Worker 定期检查过期租约，仅在能证明旧进程停止时恢复。无法证明时标记 RECOVERY_ISOLATION_REQUIRED 并保留资源锁，必须先核验旧进程，不可直接删锁重跑。

跨主机执行进入 `RECOVERY_ISOLATION_REQUIRED` 时，原主机失联不等于旧进程已停止。人工处置顺序：暂停对应业务重试/新建；通过云平台、虚拟化平台或主机管理面板关机/隔离旧主机网络与数据库访问；由主机管理员确认 Worker 与其监督子进程已退出，保存主机名、执行 ID、PID、时间和核验方式；恢复主机或数据库可达后复查租约、fencing token、业务状态和资源锁；确认旧执行不能再提交后，才由有权限人员按现有重试/恢复入口处置。保留锁期间不得手工删除锁或直接改 RUNNING 状态。若无法取得主机控制面证据，保持隔离并升级给基础设施负责人，不进行自动恢复。

#### 重试边界与副作用

任务状态、attempt 和 checkpoint 的 fencing 只保护 MySQL 执行记录与业务状态提交，不会撤销已经发给外部服务的请求，也不能提供 exactly-once。

| 任务 | 可安全重做的部分 | 重试仍可能重复的影响 |
| --- | --- | --- |
| `agent.run` | Agent 工具目前为只读查询；权限、对象和来源范围在续跑时重新核验。 | 模型规划/回答请求可能再次发送并重复计费；重试时读到的业务数据可能已变化。Agent 不应直接执行业务写入。 |
| `documents.fetch` | 同一 CAS 的文档对象使用确定性对象键，任务资源锁避免相同资源并发抓取。 | 爬虫会再次访问外部站点；源文档变化时同键对象内容可能更新。MinIO 对象与 MySQL 元数据不在一个事务中。 |
| `documents.ingest` | 解析结果按文档/章节 upsert；Qdrant 写入使用 generation、条件写入和旧代次清理，防止迟到执行覆盖新代次。 | Embedding 请求可能在 checkpoint 之前重发并重复计费；MySQL 与 Qdrant 的阶段性写入仍需依赖 generation 检查与重跑收敛。 |

新增带外部写副作用的任务前，必须先定义领域幂等键、外部 operation ID/请求 hash、未知结果查询或人工对账流程；不能仅依赖任务 attempt 或 fencing token 宣称副作用只发生一次。

查询积压和失败：

```sql
SELECT task_type, status, COUNT(*) AS task_count
FROM async_task_executions GROUP BY task_type, status;
SELECT id, task_type, business_id, error_code, attempt_count, updated_at
FROM async_task_executions WHERE status = 'FAILED' ORDER BY updated_at DESC;
```

单次领取或只检查恢复：

```powershell
.venv/Scripts/python.exe scripts/run_task_worker.py --queue agent --once
.venv/Scripts/python.exe scripts/run_task_worker.py --queue documents --recover-only
```

`--once` 最多执行一个可领取的任务，空队列立即退出。`--recover-only` 检查所有类型的过期执行，可能置为 RETRYING，后续由对应 Worker 领取。

### 从 RabbitMQ 迁移与回退

1. 暂停新提交，结束或正常取消旧进程内任务及 RabbitMQ 在途任务；停止旧 API、Dispatcher、两类 Worker 和任务子进程。
2. 核对遗留 RUNNING；证明旧进程停止后再运行恢复，无法确认的执行必须隔离处理。
3. 升级代码和迁移，将原 `rabbitmq` 配置改为 `database`，移除 RABBITMQ_* 配置。旧模式会被配置校验拒绝，不会静默切换。
4. 启动新 Worker 与 API，恢复提交。遗留 QUEUED/RETRYING 直接从执行表领取，与旧 outbox 是否 SENT、Broker 是否还有消息无关；禁止同时运行旧消费者。现有 Broker 和数据卷由部署负责人另行退役，升级不会删除它们。

回退 `in_process` 前暂停提交，排空、结束或隔离数据库任务并停止 Worker，再调整模式、重启 API。不要将遗留执行交给 BackgroundTasks 或直接重置状态重放。

### 三个必须知道的坑

#### 1. `@iconify/json` 装不上

这是 `packages/@core/base/design` 的依赖，压缩包 **102 MB**。
- npmmirror：请求超时（pnpm 反复重试后失败）
- registry.npmjs.org：传输中途 socket 重置（`UND_ERR_SOCKET`）
- 用 `curl` 下载同一地址却只要 16 秒

**处理**：已把该 scope 单独指向官方源，并把 tarball 预置进 pnpm store。

`.npmrc`（已提交在 `frontend-design/.npmrc`）：

```ini
registry=https://registry.npmmirror.com
@iconify:registry=https://registry.npmjs.org/
fetch-timeout=900000
fetch-retries=5
```

如果重装时仍然卡在这个包，用预下载的 tarball 喂给 store：

```powershell
cd C:\self_project\ChemicalOps\frontend-design
corepack pnpm store add "C:/self_project/ChemicalOps/.cache/vendor/iconify-json-2.2.520.tgz"
corepack pnpm install
```

`.cache/vendor/iconify-json-2.2.520.tgz` 就是预下载的包（102 MB），确认装好后可删除。

#### 2. 不要用 `node-linker=hoisted`

曾为绕开上面的网络问题试过 `node-linker=hoisted`，结果 pnpm 把 `vue-router`
解析成**两份实例**（因为树里同时存在 `@vue/compiler-sfc@3.5.41` 和 `3.5.43`
两个 peer 上下文）。后果是类型互不兼容，且运行时可能出现两个 vue-router 实例。
保持 pnpm 默认的 isolated linker 即可。

#### 3. `--ignore-scripts` 会跳过 stub，需要手工补

`internal/vite-config` 的 `exports` 指向 `./dist/index.mjs`，由 `stub` 脚本生成。
用 `pnpm install --ignore-scripts` 装完依赖后必须补跑：

```powershell
corepack pnpm -F @vben/node-utils stub
corepack pnpm -F @vben/vite-config stub
```

否则 `vite dev` / `vite build` 会因找不到 `@vben/vite-config` 而失败。

### 改了品牌配置（应用名 / logo）后看不到变化？

**这不是缓存没刷新的问题，普通刷新（F5）不会清 localStorage。**

vben 的偏好设置（`preferences`，含 `app.name` 与 `logo.source`）会持久化到
localStorage，并且加载时**缓存优先于代码里的默认值**：

```ts
// packages/@core/preferences/src/preferences.ts
const mergedPreference = mergeWithArrayOverride(
  {},
  cachedPreferences,      // 用户缓存的设置优先
  this.initialPreferences // 初始设置（含 overrides）仅补齐缺失字段
);
```

所以改完 `VITE_APP_TITLE` 或 logo，老用户浏览器里仍然是旧值。让旧缓存失效的正确做法是
**改 `VITE_APP_NAMESPACE`**（它会拼成缓存 key 前缀）：

```
VITE_APP_NAMESPACE=chemicalops-v2
```

命名空间变了 → 缓存 key 变了 → 旧缓存被忽略 → 走代码默认值。

**不要试图改 `VITE_APP_VERSION`**：它被 `internal/vite-config/src/plugins/inject-metadata.ts`
用 `package.json` 的 `version` 硬覆盖（`'import.meta.env.VITE_APP_VERSION': JSON.stringify(version)`），
写在 `.env` 里不生效，改了命名空间也不会变。

如果只是本地调试想立刻看到效果，也可以在浏览器 Console 执行 `localStorage.clear()` 后刷新。

### 与后端的约定差异（重要）

vben 默认假设后端返回 `{ code, data }` 包装，化学平台后端**不是**这样：

| 项 | vben 默认 | ChemicalOps 后端 |
|---|---|---|
| 成功响应 | `{code:0, data:{...}}` | 直接返回业务体 |
| 错误响应 | `{code, message, error}` | `{code, message, detail}`，HTTP 状态码非 2xx |
| 登录返回 | `{accessToken}` | `{access_token, token_type, expires_in}` |
| 刷新令牌 | 有 `/auth/refresh` | **没有**，401 直接重新登录 |
| 退出登录 | 有 `/auth/logout` | **没有**，前端清 token 即可 |
| 权限码 | 有 `/auth/codes` | 来自 `/auth/me` 的 `permission_codes` |
| 菜单 | 有 `/menu/all` | **没有**，前端路由 + `meta.authority` 匹配权限码 |
| 分页 | `page` / `pageSize` | `page` / `page_size`，响应 `{items,total,page,page_size}` |

因此 `src/api/request.ts` 用 `successCode: () => true` + `dataField: (body) => body`
改为「HTTP 2xx 即成功」，并单独处理 401 与中文错误提示。

另外 `RequestClient` **没有 `patch` 方法**，所有 PATCH 请求走
`requestClient.request(url, { method: 'PATCH', data })`。
