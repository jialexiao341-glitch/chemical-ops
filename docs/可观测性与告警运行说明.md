# 可观测性与告警运行说明

监控指标、追踪、告警通知与处置流程的合并说明。

## 后端可观测性运行说明

### 组件与数据

- FastAPI `/metrics` 暴露 Prometheus 文本格式指标；HTTP 请求计数和延迟、数据库连接池/查询数、Redis 缓存/限流、LLM Gateway 请求/耗时/Token/TTFT、Agent 步骤/工具调用及耗时沿用进程内注册表。
- 任务队列状态从 MySQL `async_task_executions` 汇总，避免只观察 API 进程而看不到独立 Worker 的持久化积压状态。积压按固定队列类型聚合，不包含用户、任务 ID 或业务参数标签。
- `deploy/docker-compose.observability.yml` 提供 Prometheus、Grafana、Jaeger、Alertmanager 及本地专用 webhook，不修改现有 Redis、Qdrant、MinIO 服务定义。Grafana 自动加载 ChemicalOps 概览看板；通知配置与处理步骤见 [告警处置说明](可观测性与告警运行说明.md)。
- 启用 `OTEL_ENABLED=true` 后，OpenTelemetry 自动采集 FastAPI、SQLAlchemy 和 HTTPX spans，并由 OTLP/HTTP 导出。API 接收请求时的 W3C trace context 写入持久任务 payload；Worker 子进程恢复父上下文并建立 `task.execute` span，Agent 执行、工具调用及模型请求作为子 span。请求日志 `trace_id` 与活动 OTel span 对齐。

### 本地启动

`/metrics` 始终需要独立 Bearer 凭据，未配置或凭据错误返回 401。先生成至少 32 位的随机值，写入后端 `.env` 的 `METRICS_ACCESS_TOKEN`，再将相同值保存到 `deploy/observability/secrets/metrics_token`（纯文本，无引号）。目录已忽略提交；限制该文件的本地读取权限。Prometheus 通过只读挂载的凭据文件抓取，不要把真实凭据写入 prometheus.yml。

配置后重启 API，使其监听 `127.0.0.1:8888`。然后在 PowerShell 中设置 Grafana 管理员密码并启动监控组件：

```powershell
$env:GRAFANA_ADMIN_PASSWORD = "设置一个本地密码"
docker compose -f deploy/docker-compose.observability.yml up -d
```

Prometheus 默认位于 `http://127.0.0.1:9090`，Grafana 位于 `http://127.0.0.1:3001`，避免与前端 Vite 的 3000 端口冲突。Grafana 用户名默认为 `admin`，密码读取 `GRAFANA_ADMIN_PASSWORD`。需要调整端口时可设置 `PROMETHEUS_PORT` 或 `GRAFANA_PORT`。

Alertmanager 位于 `http://127.0.0.1:9093`，本地接收器查询端口为 `http://127.0.0.1:19093/events`。默认通知仅投递到本地专用接收器；生产 webhook/邮件须使用受控配置及凭据，并单独验证外部送达。各管理与查询端口只绑定宿主回环地址。

Prometheus 每 15 秒抓取 `host.docker.internal:8888/metrics`。如果 API 使用其他端口或地址，请编辑 `deploy/observability/prometheus.yml` 中的目标地址。

同一 Compose 同时启动 Jaeger all-in-one，UI 地址为 `http://127.0.0.1:16686`，OTLP/HTTP 接收地址为 `http://127.0.0.1:4318`。将后端 `.env` 中的 `OTEL_ENABLED=true`、`OTEL_EXPORTER_OTLP_ENDPOINT=http://127.0.0.1:4318` 和 `OTEL_SERVICE_NAME=chemicalops-api` 配好后重启 API/Worker；此端点值使用信号基础 URL，SDK 自动补 `/v1/traces`。容器 UI 和 OTLP 端口仅绑定本机回环地址。

### 指标与解释

- API：`chemicalops_api_requests_count` 和 `chemicalops_api_request_duration_seconds_histogram_*`；可用 PromQL `histogram_quantile(0.95, sum by (le) (rate(chemicalops_api_request_duration_seconds_histogram_bucket[5m])))` 计算抓取样本的 P95。
- 队列：`chemicalops_task_queue_backlog`、`chemicalops_task_queue_oldest_ready_seconds`、`chemicalops_task_queue_executions` 和 `chemicalops_task_queue_attempts`。这些是每次 `/metrics` 抓取时对 MySQL 当前状态的快照，不是累计事件计数。
- Redis：`chemicalops_redis_cache_count`、`chemicalops_rate_limit_count`，按固定功能区和结果分类。
- LLM：`chemicalops_llm_gateway_duration_seconds_histogram_*`、`chemicalops_ai_first_token_seconds_histogram_*`、`chemicalops_llm_tokens_count` 及 Gateway 错误、重试、熔断和并发等待指标。Token 数只在上游实际返回 usage 时记录；流式模型需支持可选 usage 才能统计。首 Token 仅针对收到文本增量的流式调用。
- 数据库：`chemicalops_database_pool_connections{state=...}` 展示当前 API 进程的 configured/idle/in_use/overflow 连接数；`chemicalops_database_queries_count{operation=...}` 计数器可与压测前后快照对照。
- Agent：`chemicalops_agent_steps_count`、`chemicalops_agent_tool_calls_count`、`chemicalops_agent_tool_duration_seconds_histogram_*` 和 `chemicalops_agent_execution_duration_seconds_histogram_*`。默认 database Worker 通过独立子进程执行，其进程内指标不会出现在 API 的 `/metrics`；当前这些 Agent 运行时指标适用于 in_process 模式或 API 进程内调用，不可据此声称已观测独立 Worker。

当前 API/LLM/Agent 累计指标是进程内数据。多 API 进程部署时，应为每个进程设置独立 Prometheus 抓取目标，或接入明确配置的 multiprocess/exporter 聚合方案；不能把负载均衡地址当成完整的多进程累计数据。Gateway 的熔断器注册表、模型 semaphore 及每用户 semaphore 都是进程/事件循环内状态，因此每增加一个 API 实例，全局熔断和并发上限就会按实例数放大；当前建议保持单实例 API。只有在横向扩容且需要全局配额时再引入 Redis 共享限流/并发租约与熔断状态，并单独定义 Redis 不可用策略。

任务队列积压来自共享 MySQL，可跨 API/Worker 观察。迁移 050 为每次尝试持久化 `started_at`/`finished_at`；看板展示最近 15 分钟已完成尝试的按队列/状态平均耗时快照。API 从共享任务表采集，因此包含独立 Worker；这是窗口均值 gauge，不是 Prometheus 原生直方图或 P95。

当前任务按队列分别以 `created_at, id` FIFO 领取；资料和 Agent 是独立队列及并发池，不支持优先级或跨队列公平调度。现阶段保持 FIFO，只有出现可量化的高优先级 SLA 或持续饥饿证据后再设计调度变更。

### 可重复接口压测

```powershell
python scripts/run_load_test.py --url http://127.0.0.1:8888/health --requests 200 --concurrency 10
```

压测脚本通过环境变量 `METRICS_ACCESS_TOKEN` 或 `--metrics-token` 读取监控凭据（与业务 `--token` 分开）；凭据不写入报告。幂等缓存每小时自动清理，关注 `chemicalops_idempotency_cleanup_count{result="failed"}` 与 `chemicalops_idempotency_expired_deleted_count`。

脚本输出环境、请求数、并发数、错误数、RPS、P50/P95、状态码分布、测试区间 SQL 查询数增量，以及可用时的 Redis 缓存命中/未命中增量和命中率；使用 `--output report.json` 保存结果。脚本先后读取同一 API 实例的进程内 `/metrics`，因此必须保证测试期间没有其他流量；API 重启或切换实例会使增量不可用或不完整。报告结果时同时记录 API 实例数、数据库/Redis 状态、请求路径及模型是否参与；`/health` 仅验证服务端点，不代表业务接口或模型性能。

## 可观测性告警与处置

### 告警规则

Prometheus 规则位于 `deploy/observability/alerts.yml`，由 `deploy/observability/prometheus.yml` 加载：

| 告警 | 触发条件 | 优先处置 |
| --- | --- | --- |
| `ChemicalOpsAPITargetDown` / `ChemicalOpsAPITargetMissing` | API `/metrics` 连续不可抓取或 target 消失 | 检查 API 进程、主机网络、端口、目标配置和 `/health/ready` |
| `ChemicalOpsDatabaseMetricsUnavailable` | API 刷新任务队列快照时，5 分钟窗口出现 MySQL 错误 | 检查 MySQL 连通性、连接池、权限和迁移；恢复后确认该计数停止增长 |
| `ChemicalOpsQueueHasFailedTasks` | 持久化队列仍有 FAILED 任务 | 查看 task type、error code、attempt 和 checkpoint；按任务安全重跑边界决定人工核验或重试 |
| `ChemicalOpsQueueRecoveryIsolationRequired` | 旧 Worker 无法确认退出，执行处于隔离终态 | 保留资源锁，隔离旧主机和子进程并记录证据；确认旧执行不能提交后再恢复 |
| `ChemicalOpsQueueOldestReadyTaskDelayed` | 有可执行积压且最老等待超过 5 分钟，持续 5 分钟 | 检查对应 Worker、队列积压和 MySQL；勿用重置状态代替恢复流程 |

队列 FAILED 是持久化未处置快照，告警会保持到任务按支持的业务入口完成恢复或核实；不得为了消除告警直接删除执行记录或资源锁。跨主机 fencing 核验详见[任务队列运行说明](运行、部署与构建手册.md)。

数据库可用性以 API 的 `task_queue_metrics_collection{result="database_error"}` 计数作为补充探针：API target 仍可抓取时，该指标能区分“API 活着但 MySQL 快照失败”。API 实例完全不可达时由 target down 告警覆盖。

### 通知通道状态

本地 Compose 已接入 Alertmanager v0.28.1，Prometheus 向 `alertmanager:9093` 发送告警，默认投递到专用本地 `alert-webhook:8080/alerts`，并发送恢复通知。Alertmanager 管理端口及接收器查询端口只绑定宿主回环地址 `127.0.0.1:9093` / `127.0.0.1:19093`；接收事件先写入 Docker volume 的 `/data/events.jsonl`，再返回 HTTP 200。`GET http://127.0.0.1:19093/events` 可查看最近 1,000 条接收记录。

`deploy/observability/alertmanager.yml` 按告警名、队列及验收标识分组，等待 5 秒、组更新间隔 10 秒、重复提醒间隔 4 小时。该目标仅供本地验收，不是生产收件人。生产通知须使用不入库的配置覆盖文件指定受控 webhook/邮件及凭据来源，并重新验证外部送达。不要把个人令牌或实际收件地址写入仓库。路由及 webhook 配置依据 [Alertmanager 官方配置说明](https://prometheus.io/docs/alerting/latest/configuration/)。

本地重验：先使用现有 `.env` 启动 `docker compose --env-file .env -f deploy/docker-compose.observability.yml up -d`，再运行 `.venv/Scripts/python.exe scripts/verify_alert_notifications.py --output <新报告路径>`。脚本拒绝覆盖历史报告，会向现有规则文件临时追加一条带唯一标识的验收规则并重载 Prometheus，验证触发、三次重复提交的抑制及恢复；结束时移除自己的规则并再次重载。仅在开发环境运行，不停止 API、不修改业务队列状态。结果见[通知闭环原始证据](evidence/alert-notifications-2026-10-14.json)。

### 多实例指标策略

`prometheus.yml` 当前抓取单个 API：`host.docker.internal:8888`。每个 API 实例应使用独立的可达地址并作为独立 target 加入 `static_configs`；不要把多个进程复用同一 target。Prometheus 自动添加的 `instance` 标签保留进程身份。

- 进程累计 Counter 与 Histogram（API 请求、SQL、LLM/Agent 调用）用 `sum` 聚合；P95/P99 必须先按 `le` 聚合 bucket，再计算分位数。
- 数据库连接池是进程局部快照，Grafana 保留 `instance` 展示，不把它误认为数据库全局连接数。
- 任务队列积压、FAILED、隔离和执行时长来自同一 MySQL 持久化快照，多 API 抓取会重复看到相同数据；看板和告警按 `queue` 取 `max`，不能求和。
- Worker 进程没有独立 Prometheus scrape endpoint；任务跨进程状态用 MySQL 快照观测。单个 Worker 内的即时日志/跨度仍需由配置好的日志与 OTLP collector 收集。

Prometheus 规则与 dashboard 修改后，重新加载配置并检查 `/api/v1/rules`、`/api/v1/targets` 和 Grafana 面板；当前通知验收证明本地接收器送达，不证明生产外部送达。

### 管理员前端监控

系统管理员可从 ChemicalOps「系统管理 → 运行监控」查看当前 firing/pending 告警、已加载的 alerting rules 和 Prometheus scrape targets。接口为 `/api/v1/system/monitoring/overview`，后端以 `SYS_ADMIN` 角色二次鉴权并裁剪 Prometheus 响应；Vue 浏览器不直连 Prometheus。默认读取 `http://127.0.0.1:9090`，如果 API 运行在 Compose 网络内，应设置 `PROMETHEUS_URL=http://prometheus:9090`。页面每 30 秒刷新，也可手动刷新；Prometheus 不可用时显示服务状态提示，不隐藏最后一次成功数据及其更新时间。

权限边界：仅系统管理员可读取监控汇总；普通业务用户返回 403，未登录返回 401。普通用户不显示系统管理/运行监控菜单，直接访问该页面按未注册路由处理。当前界面按状态总览、当前告警、采集状态与规则明细组织，复用运营总览卡片和列表组件。原始验证记录见 [权限证据](evidence/monitoring-permissions-2026-10-14.json) 与 [通知载荷](evidence/alert-notifications-2026-10-14.json)。

### 分层验收证据

| 层 | 入口/证据 | 范围 |
| --- | --- | --- |
| 普通业务 API | `docs/evidence/api-load-test-2026-10-14.json` | 单 API、MySQL/Redis、200 次产品详情请求、并发 10，不调用模型 |
| 缓存冷/热 | `docs/evidence/product-detail-cache-cold-hot-2026-10-14.json` | 同一真实产品详情 API 冷热各 100 次，记录 SELECT、缓存事件和 P50/P95；串行样本，不作稳定性能承诺 |
| Redis/Cache Aside | `docs/evidence/redis-validation.json`、`tests/test_redis_features.py` | 真实 Redis + SQLite 数据访问样本与缓存/限流故障边界 |
| 任务队列 | `tests/test_task_queue_delivery.py`、`test_task_queue_supervision.py`、`test_task_queue_processes.py` | 独立 Worker、崩溃/租约/取消/fencing 和恢复隔离；不与 HTTP QPS 混算 |
| LLM Gateway / Agent Mock | `tests/test_llm_gateway.py`、`test_ai_llm_stream.py`、`test_ai_structured_output.py`、Agent runtime 测试 | Mock 错误、限流、schema、取消和工具权限；是行为验证，不是真实模型性能负载 |
| 受控真实模型 | `docs/evidence/real-model-integration-2026-10-14.json` | 临时双 profile、真实模型/usage、结构化输出和流取消 smoke；样本小，不代表压测 |
| 真实模型小批量并发 | `docs/evidence/real-model-load-2026-10-14.json` | 用户确认并发 2、8 请求、8,000 Token 上限；实际 732 Token、8/8 成功；不代表生产容量或业务质量 |

真实模型并发入口为 `scripts/run_real_model_load.py --token-budget 8000 --output <报告路径>`，使用现有配置模型和 Gateway，固定无业务数据短提示、每请求最多 512 输出 Token、关闭重试与 fallback，预留总计 6,400 Token 后才发起请求。预算不足时拒绝执行；本次选择 Token 上限而非金额上限，不作货币费用估计。输出包含逐请求 usage、耗时和 P50/P95/P99；8 请求的小样本中 P95/P99 均为最大观测值，不能推断稳定尾延迟。该脚本的进程内指标不进入运行中 API 的 Prometheus 指标，不能用此报告宣称 Grafana 已展示模型负载曲线。

并发 API 的成功样本见 `docs/evidence/api-load-test-2026-10-14.json`：200 请求、并发 10、全部 HTTP 200、23.91 QPS、P50/P95/P99 62.01/183.53/7065.76 ms、368 条 API 进程 SQL、190 个缓存 hit 事件（95% 请求有缓存事件）。独立复跑见 `docs/evidence/api-load-test-repeat-2026-10-14.json`：198/200 HTTP 200，另有 2 次连接中断，P50/P95/P99 51.97/93.48/7079.76 ms；该样本同样有约 7 秒长尾，缓存事件仅覆盖 84% 请求。两份结果均未调用模型；保留失败和长尾，不将其解释为优化结论。

同一产品详情 API 冷/热串行各 100 次见 `docs/evidence/product-detail-cache-cold-hot-2026-10-14.json`：冷阶段 40.20 QPS、P50/P95/P99 29.01/33.44/36.85 ms、304 SELECT；热阶段 50.05 QPS、P50/P95/P99 20.76/33.79/37.63 ms、204 SELECT；两阶段均 100/100 HTTP 200 且缓存事件覆盖率 100%。数据库 SELECT 计数覆盖整个 API 进程，含鉴权与权限检查；测试是单并发短样本。
