## 3. 后端问题

### 3.1 P0：业务数据正确性

#### B-P0-01 询价定标与采购下单存在并发竞态

- **落实状态**：部分完成：定标/下单按询价单、比价单固定顺序加行锁，重复请求返回 409；独立 MySQL 会话并发用例通过。已有比价单 383 的订单 325/326 存在重复来源且均已履约，保留原单；数据库唯一约束暂放在 [人工迁移目录](../database/manual-migrations/采购来源唯一约束前置核对.md)，不标为完全关闭。

- **位置**：[`rfqs/service.py`](../backend/app/modules/rfqs/service.py#L301-L332)、[`purchase_orders/service.py`](../backend/app/modules/purchase_orders/service.py#L101-L104)、[`purchase_orders/model.py`](../backend/app/modules/purchase_orders/model.py#L22)。
- **现象**：定标先读 `comparison.status == "DRAFT"`，再直接提交，没有对询价单/比价单加 `FOR UPDATE` 或条件更新；下单仅靠“先查再插”判断是否已生成订单，`source_quote_id` 没有唯一约束。
- **影响**：两个采购员并发定标不同报价时，后提交者可能覆盖前一次定标；在覆盖前后各自下单时，可能产生同一询价两张采购订单，后续审批、对账和库存履约难以发现。
- **建议**：定标时按固定顺序锁 RFQ 与比价单，或使用 `UPDATE ... WHERE status='DRAFT'` 并校验 `rowcount`；为 `source_comparison_id` 增加唯一约束（一张比价单只生成一张订单），冲突转 409；补并发测试。
- **验收**：两个并发定标只能有一个成功；同一比价单并发/重试下单只产生一张 PO；失败方收到明确的 409/业务提示。

#### B-P0-02 结算重复校验使用错误主键

- **落实状态**：已实现并通过回归：按 reconciliation_id 查询未取消结算，冲突转 409；用户已确认取消后允许重建。迁移 052 使用有效对账 ID 生成列唯一约束，保留取消历史；重复、取消、重建和确认路径已验证。

- **位置**：[`finance/service.py`](../backend/app/modules/finance/service.py#L423)、[`finance/crud.py`](../backend/app/modules/finance/crud.py#L75-L81)。
- **现象**：`create_settlement` 用 `reconciliation.id` 去调用 `get_settlement`，而该函数按结算单 ID 查询。
- **影响**：重复创建结算单时检测不到已有记录，最终撞上 `uk_finance_settlement_reconciliation` 唯一键返回 500；结算单取消后唯一键仍被占用，该对账单可能永久无法重新结算。
- **建议**：按 `reconciliation_id` 查询已有结算单并区分 `CANCELLED`；捕获 `IntegrityError` 转 409；明确“取消后是否允许新建”的业务规则并落到唯一约束设计。
- **验收**：重复创建返回 409 而非 500；取消后按既定规则可重建或明确拒绝；相关路径有测试。

#### B-P0-03 出库成本层未按批次扣减，盘点不调整成本层

- **落实状态**：已实现并通过回归：普通出库仅消耗自身批次；盘亏扣成本层、盘盈沿用本批次同库位加权成本，缺少依据/历史数量不一致时拒绝。新增 [数量对账 SQL](../database/checks/inventory_cost_quantities.sql)。本地三笔历史退货错配已备份、修正并审计，六处数量差异归零，见 [修正结果](./evidence/remediation/data-postcheck.json)。

- **位置**：[`inventory_cost/service.py`](../backend/app/modules/inventory_cost/service.py#L39-L66)、[`inventory/service.py`](../backend/app/modules/inventory/service.py#L502-L548)、[`inventory/service.py`](../backend/app/modules/inventory/service.py#L855)、[`inventory_returns/service.py`](../backend/app/modules/inventory_returns/service.py#L348)、[`inventory/service.py`](../backend/app/modules/inventory/service.py#L1103-L1165)。
- **现象**：`allocate_outbound_cost` 只按产品/仓库/库位/单位筛选成本层，没有过滤 `batch_id`；领用、调拨、退货都按指定批次扣减库存余额，但成本层仍跨批次 FIFO 消耗。盘点只调整余额和流水，盘盈不新增成本层、盘亏不冲减成本层。
- **影响**：A 批次出库可能消耗 B 批次成本而 B 数量未减，成本/毛利失真；盘点后 FIFO 可能报“成本层不足”或成本虚高。
- **建议**：成本分摊按 `batch_id` 过滤；盘点差异同步生成/冲减成本层；增加“批次数量—成本层数量”对账查询和回归测试。
- **验收**：任意批次出库只消耗本批次成本层；盘盈/盘亏后成本层与余额数量一致；后续 FIFO 不出现成本层不足。

### 3.2 P1：安全与可用性

#### B-P1-01 幂等中间件全量缓冲请求体，且没有清理机制

- **落实状态**：部分完成：multipart 跳过幂等缓冲，前端 FormData 不再自动加键；其余带键写请求分块计数，超过 1MB 返回 413（含无 Content-Length 的请求）。过期记录每小时清理并记录成功/失败指标。网关全局请求体上限及不带键请求仍需部署层补齐。

- **位置**：[`core/idempotency.py`](../backend/app/core/idempotency.py#L163-L172)、[`idempotency.py`](../backend/app/core/idempotency.py#L199-L242)、前端 [`request.ts`](../frontend-design/apps/web-chemicalops/src/api/request.ts#L138-L146)。
- **现象**：中间件在鉴权前执行 `await request.body()`；前端给所有写请求（含文件上传）自动加 `Idempotency-Key`。服务端和现有 Compose 没有请求体大小上限。过期记录只在“同键再次请求”时删除，没有定时清理。
- **影响**：上传 50MB 文件时请求体会被完整读入内存一次；未认证攻击者可带键向写接口发送超大包，造成内存压力。`sys_idempotency_records` 会随写操作无限增长，单条响应体最大 1MB。
- **建议**：跳过 multipart 或改为流式哈希；按 `Content-Length` 限制大小并在网关设置 `client_max_body_size`；在现有调度器中清理 `expires_at` 过期行；评估缩短保留期或只存结果摘要。
- **验收**：大文件上传不触发全量缓冲；超限请求返回 413；过期记录在 24 小时内被清理；清理任务有监控。

#### B-P1-02 公开注册无限流，认证/监控面加固不足

- **落实状态**：代码已实现并通过回归：注册在密码散列前按 IP/15 分钟限制 3 次；metrics 始终校验独立 Bearer 凭据；生产关闭 docs/redoc/openapi；统一安全头及生产 HSTS；生产强制 Redis 限流和对象存储 TLS。本地已配置 API 与 Prometheus 的匹配凭据，真实凭据均不入库；监控组件需重启后端及 Prometheus 后生效，尚未做生产部署验收。

- **位置**：[`system/controller.py`](../backend/app/modules/system/controller.py#L58-L61)、[`core/security.py`](../backend/app/core/security.py#L18-L30)、[`main.py`](../backend/app/main.py#L256-L262)、[`main.py`](../backend/app/main.py#L429-L440)、[`core/production.py`](../backend/app/core/production.py#L41-L122)。
- **现象**：`/auth/register` 无鉴权、无限流、无验证码，每次注册执行 310k 次 PBKDF2；`/metrics` 匿名且每次查库；`/docs`、`/openapi.json` 未关闭；除文件预览接口外没有全局安全响应头；生产校验未要求 Redis 限流和 `MINIO_SECURE=true`。
- **影响**：可被用于垃圾账号与 CPU 消耗；监控与文档暴露内部接口结构；生产部署如果未启用限流，AI 调用没有用户级配额保护；对象存储可能以明文 HTTP 通信。
- **建议**：注册加限流/验证码；网关限制 `/metrics`、生产关闭 docs；补 HSTS/CSP/X-Frame-Options 等安全头；生产强制 Redis 限流、要求 MinIO TLS；补登录锁测试。
- **验收**：注册接口有明确限速；匿名访问 `/metrics` 被拒绝；生产配置缺少限流/TLS 时启动失败；安全头在响应中可见。

#### B-P1-03 被委派“用户管理”权限的账号可以给自己加系统管理员

- **落实状态**：已实现并通过回归：非 SYS_ADMIN 不能授予 SYS_ADMIN 或管理授权角色，不能修改系统管理员；角色/权限定义仅 SYS_ADMIN 可修改。用户、角色、权限的创建/修改/停用/删除写入同事务审计，不记录密码值。

- **位置**：[`system/service.py`](../backend/app/modules/system/service.py#L248-L291)、[`system/service.py`](../backend/app/modules/system/service.py#L225-L245)、[`system/audit.py`](../backend/app/modules/system/audit.py#L28-L49)。
- **现象**：`system.users.write` 持有者可以提交任意 `role_ids`，包括 `SYS_ADMIN`；只阻止“移除自己的管理员角色”，没有阻止添加。`create_user` 同样可以创建管理员。用户更新/角色变更没有审计日志。
- **影响**：当前种子数据只把这权限给 `SYS_ADMIN`，不是现状可利用漏洞；但一旦按岗位拆分出“用户管理员”，就是明确的提权路径，且可无痕操作。
- **建议**：仅 `SYS_ADMIN` 可授予/撤销 `SYS_ADMIN` 及高权限角色；用户、角色、权限变更统一写审计；补“委派管理员不能自提权”的回归测试。
- **验收**：非 SYS_ADMIN 即使拥有用户管理权限，也无法给自己或他人加 SYS_ADMIN；所有用户/角色变更可追溯。

#### B-P1-04 数据范围与文件访问的局部缺口

- **落实状态**：部分完成：领用选项按 accessible_warehouse_ids 过滤；用户已确认无关联 INTERNAL 仅上传者/系统管理员可访问；下载采用 64KB 分块并确保关闭对象流。领用选项分页仍待完成。

- **位置**：[`inventory/controller.py`](../backend/app/modules/inventory/controller.py#L128-L132)、[`inventory/service.py`](../backend/app/modules/inventory/service.py#L374-L407)、[`files/service.py`](../backend/app/modules/files/service.py#L242-L264)、[`files/service.py`](../backend/app/modules/files/service.py#L336-L362)。
- **现象**：领用选项接口不接收用户，直接返回全部启用仓库的库存余额，不按 `accessible_warehouse_ids` 过滤，也不分页；未关联业务资源的 `INTERNAL` 文件，任何拥有 `system.files.download` 的账号都可通过顺序 ID 枚举下载；下载把整个对象读入内存后一次性返回。
- **影响**：拥有 `warehouse.inventory.issue.read` 的仓库角色能看到职责外仓库的库存数量；文件 ID 可枚举，存在信息暴露与内存峰值风险。
- **建议**：领用选项按仓库范围过滤并分页；明确 `INTERNAL` 文件语义（全公司可见 vs 仅关联资源可见），必要时默认 `PRIVATE`；下载改 `StreamingResponse`。
- **验收**：仓库角色只能看到职责内仓库的领用选项；无关联 `INTERNAL` 文件不可被无关账号枚举；大文件下载内存占用可控。

#### B-P1-05 登录锁依赖客户端 IP，代理/NAT 下行为需确认

- **位置**：[`system/controller.py`](../backend/app/modules/system/controller.py#L101-L107)、[`system/service.py`](../backend/app/modules/system/service.py#L472-L518)。
- **现象**：登录锁按 `request.client.host` 分“账号+IP”和“IP”两个维度；没有固定可信代理配置的说明，也没有登录锁测试。
- **影响**：反向代理/NAT 下客户端 IP 可能退化或共享，`ip` 维度会在 30 次失败后锁住全体；如果 XFF 配置不当，也可能被伪造绕过。
- **建议**：固定 `FORWARDED_ALLOW_IPS`/可信代理，按“账号+设备/会话”优先限速，IP 维度只做兜底；补登录锁回归测试。
- **验收**：代理环境下按真实客户端 IP 计数；单账号失败不影响其他账号；伪造 XFF 不能绕过。

### 3.3 P2：性能、时间与工程

#### B-P2-01 每个认证请求的固定开销偏大

- **位置**：[`core/auth.py`](../backend/app/core/auth.py#L19-L50)、[`system/model.py`](../backend/app/modules/system/model.py#L19-L32)。
- **现象**：`get_current_user` 加载完整 `User` 行，`avatar` 是最大 512KB 的 `MEDIUMBLOB`；`require_permission` 随后再查角色码和权限码，至少 3 次查询；不少 service 内部还会重复查角色。
- **影响**：高并发下数据库读放大；头像越大越明显。
- **建议**：头像改为 `deferred` 或独立表；权限按请求级缓存（或短 TTL + 角色变更失效）；对高频接口做 `EXPLAIN`。
- **验收**：单请求 RBAC 查询次数可量化下降；头像不参与普通鉴权查询；缓存失效路径有测试。

#### B-P2-02 同步 SQLAlchemy 跑在 async 端点中

- **位置**：[`core/db.py`](../backend/app/core/db.py#L18-L25)、[`ai/service.py`](../backend/app/modules/ai/service.py#L601-L787)。
- **现象**：使用同步引擎，AI 的 `async def` 接口在等待模型/向量服务前后仍执行同步数据库操作。
- **影响**：高并发 AI 请求下会阻塞事件循环，普通接口也可能变慢；`/health` 冒烟不能证明 AI 并发能力。
- **建议**：短期在 AI 端点把 DB 操作 `asyncio.to_thread`；长期评估异步驱动；补 AI 并发压测。
- **验收**：并发 AI 请求下普通接口 P95 不显著劣化；压测报告记录连接池与事件循环等待指标。

#### B-P2-03 N+1 与无上限列表

- “我的查询”任务中心：列表、状态筛选、续跑、取消、来源回看。
- 草稿字段级修改：基于 `preview_version` 做 patch，重新计算 hash 后再次确认。
- 同产品历史报价趋势：只读数据集，明确单位/币种/规格可比口径，不做预测。
- 供应商绩效视图：按时间窗、品类筛选，复用已有 `supplier_quote_delivery_profile`。
- 结果导出（CSV/XLSX）与短链分享（鉴权后签发）。
- 批量清单查询：粘贴产品清单，服务端逐项执行并汇总不可比项。

**不该让 LLM 做：** 权限判定、仓库/询价范围推断、库存预留/扣减、供应商定标、金额/单位换算、状态流转、确认判定、幂等决策。现有设计基本守住了这条线，应继续保持。

**评测：** 现有离线 30 例、真实模型 16 任务/120 场景、路由与 RAG 评测，评分器有独立 oracle 和冻结 SHA，质量意识不错。但 CI 只跑 pytest，不跑真实模型评测；批次、草稿、改写数值保真、NL 筛选仍是盲区。建议把“离线护栏 + 冻结题集校验 + 批次/草稿单测”设为 PR 门禁，把真实模型评测设为发布前门禁。STAR 引用 100 题合成集 Recall@6=95%，而 mixed200 更难样本为 86.2%，对外表述应注明样本范围。
