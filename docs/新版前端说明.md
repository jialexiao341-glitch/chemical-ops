## 一、概况

旧前端（React + react-antd-admin）已删除，新版基于 **Vben Admin 5.8** 重建。

| 项 | 说明 |
| --- | --- |
| 位置 | `frontend-design/apps/web-chemicalops`（workspace 应用） |
| 技术栈 | Vue 3.5 / TypeScript / Vite 8 / antdv-next / vxe-table / Pinia / Tailwind 4 |
| 工程形态 | pnpm workspace monorepo，`packages/` 与 `internal/` 为 Vben 原样复用 |
| 代码量 | 126 个源码文件（52 个页面组件、24 个 API 模块、7 个路由模块） |
| 后端 | FastAPI，`http://127.0.0.1:8888`，前端 dev 代理 `/api` 与 `/health` |

选择"在 Vben monorepo 内新建 app"而不是自己搭框架，是为了直接复用 Vben 的
表格 / 表单 / 布局 / 权限 / 主题体系，避免重造轮子。

## 二、做了什么

### 1. 与后端的接口契约适配（最关键的部分）

后端**不符合** Vben 的默认约定，请求层按真实协议重写：

| 项 | Vben 默认假设 | ChemicalOps 后端实际 | 处理方式 |
| --- | --- | --- | --- |
| 成功响应 | `{code:0, data:{...}}` | 直接返回业务体 | `successCode: () => true` + `dataField: (body) => body` |
| 错误响应 | `{code, message, error}` | `{code, message, detail}`，HTTP 非 2xx | 优先透传后端中文 `message`，422 时拼接 `detail` |
| 登录返回 | `{accessToken}` | `{access_token, token_type, expires_in}` | 字段适配 |
| 令牌刷新 | 有 `/auth/refresh` | **没有** | 关闭自动续期，401 直接重新登录 |
| 退出登录 | 有 `/auth/logout` | **没有** | 前端清 token（JWT 无状态） |
| 权限码 | 有 `/auth/codes` | 来自 `/auth/me.permission_codes` | 登录时一并拉取 |
| 菜单 | 有 `/menu/all` | **没有** | 前端静态路由 + `meta.authority` 匹配权限码 |
| 分页 | `page` / `pageSize` | `page` / `page_size`，响应 `{items,total,page,page_size}` | 表格代理层转换 |

另外 `RequestClient` 没有 `patch` 方法，所有 PATCH 统一走
`requestClient.request(url, { method: 'PATCH', data })`。

### 2. 权限体系

后端没有菜单接口，因此采用**前端路由 + 权限码**方案：

- 每个路由声明 `meta.authority: ['procurement.orders.read']` 这类后端权限码
- 路由守卫把用户的**角色码与权限码合并**后参与匹配（`router/guard.ts`）
- 按钮级权限用 `v-access:code` 或表格操作项的 `auth` 字段

实测有效：`procurement_manager` 访问 `/system/*` 会 404（路由被过滤），
`system_admin` 可正常访问。

### 写路径实测记录（2026-09-21）

以「化学品」跑通完整增删改查，并单独验证含明细行的采购申请，后端调用均有据可查：

| 环节 | 证据 |
| --- | --- |
| 必填校验 | 空表单提交被拦截，提示「请输入化学品名称」 |
| 唯一冲突 | `409` → 提示「CAS 号 64-17-5 已存在」、抽屉保持打开、可改正后重试 |
| 新增 | `201 POST /chemicals` |
| 编辑 | 表单正确回填 → `200 PATCH /chemicals/{id}` |
| 停用 | `200 DELETE /chemicals/{id}` → 状态变为「停用」 |
| 采购申请明细 | `201 POST /purchase-requests`，`items` 数组字段完整 |

实测中发现并已修复 3 个缺陷：

1. **写失败产生未捕获的 Promise 拒绝** —— 20 个表单弹窗的 `onConfirm` 只有
   `try/finally` 没有 `catch`，后端返回 4xx 时异常逃逸成全局
   `[pageerror]`。已统一补上 `catch`（错误提示由请求层负责，弹窗保持打开）。
2. **明细行编辑器的初始行填了值不生效** —— `ItemsEditor` 的 `rows` getter 里
   做了「补齐 `__rowId`」的转换，而该转换会创建新对象；getter 每次渲染都被调用，
   于是 `v-model` 的写入落在被丢弃的副本上。表现为采购申请/询价单/到货计划
   的初始行永远提示「缺少物料名称」。已改为就地补齐、不复制对象。
3. **错误提示丢失具体原因** —— 后端错误体是 `{code, message, detail}`，
   `message` 是笼统文案（「数据已存在」）、`detail` 才是具体原因
   （「CAS 号 64-17-5 已存在」）。原实现只取 `message`，已改为优先展示 `detail`。

用 `scripts/flow-test.mjs` 端到端跑通六大段状态机（36/36 通过），
后端写请求逐步留痕：申请 645→646、询价 RFQ380、订单 PO314、

全程 0 个未捕获 Promise 拒绝。覆盖的流转：

| 段 | 流转 | 证据 |
| --- | --- | --- |
| A 采购申请 | 新建→提交→驳回→重提→审批通过；另单取消 | 201 create + 200 submit/reject/approve/cancel |
| B 询价 | 关联已批申请→发送→录报价→生成比价→确认中选→生成订单 | 200 send/quotes/comparison/select-quote + 201 order |
| C 采购订单 | 提交审批→审批通过→正式下单 | 200 submit/approve/place，状态到 ORDERED |
| D 到货 | 登记计划→实收 9/计划 10 短交收货 | 201 delivery + 200 receive（页面出现短交预警） |
| E 质量 | 创建验收→录入「合格」 | 201 acceptance + 200 result(PASSED) |
| F 库存 | 入库→冻结→解冻 | 201 inbound + 200 freeze/unfreeze |

实测中又发现并修复 6 个缺陷：

4. **询价详情缺「录入报价」入口** —— `quote.vue` 组件写好了但从未被引用，
   详情抽屉只有发送/比价/生成订单按钮，询价流程在 UI 上根本走不通
   （后端 `create_quote` 要求 SENT/RESPONDING）。已在详情抽屉补按钮。
5. **状态流转按钮缺 `catch`**（缺陷 1 的漏网之鱼）—— 非弹窗的动作函数
   （`rfqs/detail.vue` 的发送/比价/生成订单、`purchase-orders/detail.vue` 的
   `runAction`、`quality/result.vue` 的 `onConfirm`）仍是 `try/finally`。
   已补齐。
6. **主数据下拉不过滤状态** —— 询价/申请表单的供应商、产品、单位下拉
   返回全部记录，会把 `SUSPENDED`/`INACTIVE` 的选项列出来，选中后后端必然
   400（实测「供应商 SUP-270119 当前不可询价」）。已改为只拉 ACTIVE。
7. **新建的质量验收单点不了「录入结果」** —— 后端创建时 `result="PENDING"`，
   但按钮显示条件是 `!row.result || row.result === 'REINSPECTION'`，
   `PENDING` 不匹配，新单永远没有入口。已放行 PENDING；
   字典补「待检验」项（原样显示原始码 PENDING），录入结果表单过滤掉
   PENDING 选项（它不是可提交的结果）。
