# ChemicalOps 当前实现进度与接口质量评估

更新时间：2026-09-22
评估范围：后端 API、MySQL 数据库、权限控制、通知、Dashboard 聚合和当前前端请求封装。  
运行地址：`http://127.0.0.1:8888`

## 一、总体结论

当前项目已经完成采购运营主链路的 MVP 后端：

```text
采购申请 → 询价报价 → 比价定标 → 采购订单 → 到货收货 → 质量验收 → 库存入库 → 库存领用出库 → 财务对账 → 发票 → 付款 → 结算 → 异常处理 → 站内通知
```

当前 OpenAPI 实际包含 131 个路径、180 个操作。项目已经可以用于本地开发和业务流程演示，但还不适合直接作为生产系统上线，主要原因是：

- 已建立 pytest 接口、事务、并发和故障回滚测试基线，并已添加 GitHub Actions CI 工作流；本地全量测试已通过，远程 CI 尚未在本轮实际执行。
- 已接入统一 `Idempotency-Key` 中间件，并修复过期记录无法复用的问题；默认仍兼容未携带请求头的历史写接口。收货已锁定到货单和采购订单，入库已锁定到货单和已有库存余额，首次创建库存余额的极端竞态仍需补数据库冲突重试。
- 库存已完成入库、领用出库、调拨、盘点和冻结解冻。
- 财务对账、发票、付款和结算已经完成 MVP 闭环，仍需补生产级外部银行和税务系统对接。
- 已提供逾期扫描服务、手工接口和可持续运行的调度脚本；每轮支持基础失败重试，但统一任务状态、失败指标、通知重试和任务监控仍待完善。
- Dashboard 已从硬编码示例指标切换为数据库聚合数据，增加每日采购金额折线图、订单状态饼图、订单状态/供应商采购额/库存出库成本条形图、待办任务和库存有效期预警；前端支持手动刷新。
- `/health` 已返回数据源和运行环境，前端明确显示“数据库实时聚合 · 演示环境/生产环境”；本地 `APP_ENV=development` 仍代表演示数据库，不代表已接入生产业务系统。
- 前端左侧导航已按采购履约顺序重组为“采购申请与订单 → 到货与收货 → 质量验收 → 库存入库”；到货计划、收货数量、仓库/库位选择和入库写入已改为真实表单，复用 `/deliveries`、`/quality-acceptances` 和 `/inventory/inbounds` 接口。
- 已提供文件上传、下载、附件关联以及 local/MinIO/S3 兼容对象存储适配；上传入口已增加大小、扩展名、MIME 和常见文件魔数基础校验，并提供可配置的 ClamAV/`clamdscan --stream` 上传前扫描闸门（本地默认关闭）；PRIVATE 文件的元数据、下载、附件关联和附件列表均按上传者/系统管理员校验。
- 已接入 AI 基础调用闭环：`.env` 默认配置 DeepSeek `deepseek-flash`（V4.1 Flash 的官方 API 标识），后端提供登录保护的 `/api/v1/ai/chat`，前端悬浮 AI 工作台已调用真实接口；AI 会话和消息已写入 `ai_conversations` / `ai_messages`，附件会先保存为当前用户的私有文件并解析，具备对应实时权限的用户还会获得当前数据库 Dashboard、订单、到货、库存、质量验收、异常、财务对账和供应商只读上下文。PDF/Office 附件在本地开启 `MINERU_ENABLED=true` 时会按 MinerU v4 的签名上传、异步轮询和 `full.md` 下载流程解析，远程失败会回退到现有本地解析器。
- 生产环境的结构化日志、链路追踪、监控告警和备份策略尚未完成。

## 二、完成度标记

| 标记 | 含义 |
|---|---|
| ✅ | 代码已经实现，并且已有检查或真实接口验证 |
| ⚠️ | 已有基础实现，但存在边界、并发、测试或生产化不足 |
| ⛔ | 当前尚未实现，或不能证明满足要求 |

下面的 12 项标准对应用户提出的接口检查要求：

1. 输入对不对？
2. 操作的数据存在吗？
3. 业务上允许这么做吗？
4. 这个用户有资格这么做吗？
5. 多个数据库操作会不会只成功一半？
6. 多个请求同时进来会不会出问题？
7. 同一个请求执行两次会不会出问题？
8. 返回结果规范吗？
9. 出错时前端看得懂吗？
10. 出问题以后后端查得到原因吗？
11. 数据量大了以后还能不能跑？
12. 怎么证明这个接口真的没问题？

### 3.1 登录和系统权限

已实现：

- 用户名密码登录，返回 JWT。
- 当前用户查询。
- 用户、部门、角色、权限的基础管理接口。
- 基于角色和权限编码的接口访问控制。
- 用户、角色和权限关联关系使用数据库外键和联合主键。

需要注意：JWT 本身是无状态令牌，当前请求会重新查询数据库权限，因此角色权限变更可以较快生效；但登录失败次数限制、账号锁定策略、刷新令牌和退出登录黑名单尚未完成。

### 3.2 化学品、产品和供应商主数据

已实现：

- 分页查询、详情查询、新增、部分更新和停用。
- CAS 号、产品编码、供应商编码等唯一性校验。
- 主数据状态使用软删除或停用，保留历史业务引用。
- 列表接口具备基础索引和分页。

当前不足：

- 部分关联数据主要依赖数据库外键，服务层没有统一转换所有外键错误。
- 主数据并发编辑没有版本号或乐观锁校验。
- 没有完整的变更历史和字段级差异记录。

### 3.3 采购申请、询价报价和比价定标

已实现：

- 采购申请草稿、提交、审批、驳回和取消。
- 询价单草稿、发送、供应商报价、比价快照和确认中选报价。
- 采购申请明细、询价明细、供应商和报价明细之间的关联校验。
- 报价快照保存历史价格，避免供应商后续修改影响已有比价结果。
- 多表写入在一个 SQLAlchemy 会话事务中完成。

当前不足：

- 审批和定标缺少数据库行锁或版本号，两个审批请求同时进入时仍需加强保护。
- 带 `Idempotency-Key` 的写请求已经由统一中间件处理；未带 header 的历史接口仍保持兼容模式。
- 供应商报价导入和报价文件解析尚未完成，供应商门户基础订单确认已完成。

### 3.4 采购订单、到货和收货

已实现：

- 从确认中选报价生成采购订单。
- 订单提交、审批、驳回、正式下单和取消。
- 到货计划登记和实际收货。
- 收货数量回写采购订单明细和订单状态。
- 短交收货自动生成运营异常并发送站内通知。
- 重复确认同一到货单会被状态机拦截。

当前不足：

- 收货会锁定到货主单和采购订单主单，串行化同一订单的并发收货；库存余额的并发入库也会锁定已有余额行。余额首次创建时仍需结合数据库唯一约束和重试策略覆盖极端竞态。
- 供应商门户基础订单确认已经完成；订单通知供应商和物流轨迹同步尚未完成。
- 已实现退货、补货申请和分批到货基础业务规则；退货退款、补货自动生成采购订单仍未完成。

### 3.5 质量验收

已实现：

- 只能为已收货到货单创建验收记录。
- 支持 `PASSED`、`PARTIAL`、`FAILED`、`REINSPECTION`。
- 验收结果会同步更新到货单质量状态。
- `PARTIAL` 和 `FAILED` 自动生成质量异常并发送通知。
- 已完成验收需要先发起复检，再提交新的最终结果。

当前不足：

- 检测指标目前以 JSON 保存，缺少指标字典、上下限和自动判定规则。
- 验收报告文件已可关联文件元数据；上传、下载和附件关联接口已完成，生产环境仍需启用并验证 ClamAV。
- 复检并发操作、质量记录版本和审批留痕需要继续加强。

### 3.6 库存

已实现：

- 仓库、库位、库存批次、库存余额和库存流水表。
- 质量验收通过后才能执行入库。
- 按产品、批次、仓库、库位和计量单位维护余额。
- `delivery_item_id` 唯一约束防止同一到货明细重复入库。
- 库存余额使用联合唯一约束。
- 支持库存领用申请、审批、驳回、取消和执行出库。
- 出库锁定领用申请和库存余额，按固定顺序锁定多个库存余额，重复执行不会再次扣减。
- 支持库存调拨申请、审批、驳回、取消和执行调拨；一次事务同时生成源库位出库和目标库位入库流水。
- 支持库存盘点申请、审批、驳回、取消和执行差异调整，并保存账面快照。
- 支持库存冻结、解冻和状态变更历史，冻结库存不会改变数量。

当前不足：

- 入库余额增加操作仍需要补充行级锁或原子 SQL，才能完整应对并发入库。
- 已实现库存成本层、FIFO 出库、普通领用/调拨/退货成本分摊和有效期预警接口；历史库存必须先完成成本层回填。

### 3.7 运营异常、任务和评论

已实现：

- 异常登记、查询、负责人指派和状态流转。
- 支持短交、质量、文件、逾期和其他异常类型。
- 支持异常处理任务、任务负责人、优先级、截止时间和完成说明。
- 支持任务处理评论和已有文件元数据关联。
- 关键写操作写入审计日志。

当前不足：

- 已提供逾期到货扫描服务、手工接口和可持续运行的调度脚本；每轮扫描支持最大尝试次数和重试等待时间，最后一次失败会记录并继续下一轮。
- 任务状态变更没有数据库版本号，重复并发更新仍需加强。
- 评论附件仍需补充预览和在线下载策略；已按附件关联的业务资源类型读取权限校验元数据、下载、关联和列表，部门/仓库级数据范围仍需继续细化。

### 3.8 站内通知

已实现：

- 通知表和接收人索引。
- 查询当前用户通知。
- 查询未读数量。
- 单条标记已读和全部标记已读。
- 自动异常事件向相关角色发送通知。

当前不足：

- 尚未实现通知模板、通知偏好和通知渠道配置。
- 已提供逾期到货扫描服务、手工接口、定时调度和基础失败重试；统一任务状态、失败指标、重试告警和多渠道消息仍未完成。
- 当前通知写入与业务事务在同一数据库内，未来接入短信、邮件或 WebSocket 时需要消息 outbox 机制。

### 3.9 财务对账、发票、付款和结算

已实现：

- 已完成收货且全部质量验收通过的采购订单才允许创建对账单；一张订单通过唯一约束只允许一张对账单。
- 发票录入、提交、核验和驳回；发票号码按供应商唯一，价税合计必须等于不含税金额加税额。
- 付款申请、审批、驳回和实际付款登记；累计付款不能超过对账金额，付款前必须有足额已核验发票；银行流水号同时由服务层检查和数据库唯一索引保护。
- 结算单创建和确认；只有足额付款后才能结算，确认结算与关闭对账单在同一事务中完成。
- 对账单、付款审批和结算确认使用行级锁；关键动作写入审计日志；接口测试覆盖完整闭环和财务查看者越权写入。

当前不足：

- 尚未对接银行流水、电子发票验真、税务系统和真实付款回执。
- 发票附件目前只保留文件 ID；通用文件上传和 MinIO/S3 适配已完成，生产环境仍需启用并验证 ClamAV。
- 财务单据还没有独立的分录、会计科目和多币种汇兑核算。

### 3.10 退货和补货

已实现：

- 退货申请草稿、提交、审批、驳回、取消和执行出库。
- 退货明细校验产品、仓库、库位、批次、单位和库存余额；退货执行使用库存行锁，禁止冻结库存退货和库存不足退货。
- 补货申请草稿、提交、审批、驳回、取消和完成；完成时必须关联同供应商且已经正式下单的采购订单。
- 退货和补货接口已加入独立 RBAC 权限和集成测试。

当前不足：

- 退货后供应商退款、换货和退款金额尚未接入财务模块。
- 补货目前需要人工创建采购订单后关联，尚未自动从补货申请生成订单。

### 3.11 供应商门户和供应商确认

已实现：

- 供应商门户账号绑定表，一个门户用户只能绑定一个供应商。
- 供应商订单列表和详情按绑定供应商过滤，草稿订单不会暴露给供应商。
- 供应商确认和拒绝订单，写入订单事件与审计日志；重复确认会被状态规则拒绝。
- 供应商门户权限独立于内部采购权限，内部采购员不能直接使用门户接口。

当前不足：

- 供应商账号创建、邀请邮件、密码重置和多联系人账号管理尚未做成后台页面。
- 供应商确认暂未接入邮件、短信和 Webhook 通知。

### 3.12 库存成本、FIFO 和有效期预警

已实现：

- 入库流水按采购订单含税单价自动生成库存成本层，历史入库可以通过回填脚本补建成本层。
- FIFO 出库按成本层创建时间和主键顺序分摊，生成出库流水和成本分摊记录。
- FIFO 出库使用 `request_no` 做请求级幂等，相同请求重试返回原结果，不重复扣库存。
- 有效期预警查询已覆盖已过期、7 天内紧急和阈值内预警三种等级。

当前不足：

- 普通领用、调拨、退货已经统一接入成本层分摊；独立的库存会计分录和跨币种核算仍未完成。
- 成本层批量重算、成本调整和多币种汇兑尚未完成。

## 四、12 项标准的统一检查结论

### 1. 输入对不对？

基础完成。接口使用 Pydantic 请求模型和 FastAPI Query 校验，已经覆盖必填、长度、正数、日期、枚举和分页范围。

仍需补充：

- 更完整的跨字段校验，例如日期区间、金额精度和业务条件组合。
- 统一的中文字段级校验消息。
- 批量导入格式和病毒扫描校验。

### 2. 操作的数据存在吗？

大多数核心流程已在服务层使用 `db.get`、查询和数据库外键校验；采购申请、报价、订单、到货和验收的主要关联记录均有检查。

仍需补充：

- 所有外键异常统一转换为可理解的 400 或 404，而不是依赖数据库异常。
- 统一校验“存在且启用”“存在但已停用”“存在但不属于当前业务单据”三种情况。

### 3. 业务上允许这么做吗？

核心状态机已经实现，例如采购申请审批、订单下单、到货收货、质量验收和异常处理均限制了状态流转。

尚未完整覆盖：

### 4. 这个用户有资格这么做吗？

基础 RBAC 已完成。接口通过权限编码校验，系统管理员、采购、仓库、质量、财务和管理层账号已经准备好演示角色。

仍需补充：

- 审批代理、临时授权和权限变更审批。
- 对导出、下载和敏感字段的单独权限控制。

### 5. 多个数据库操作会不会只成功一半？

大多数服务方法在一个 SQLAlchemy 会话中完成多次写入后再提交，采购申请、订单、收货、验收、入库和异常任务的主要数据库写操作具备事务边界；失败时未提交的数据不会持久化。

当前风险：

- 没有统一的事务装饰器或工作单元规范。
- 没有统一记录回滚原因。
- 数据库写入与未来的邮件、短信、对象存储等外部系统无法天然保持原子性。

### 6. 多个请求同时进来会不会出问题？

当前只能评估为部分完成。状态检查和唯一索引可以拦截部分重复操作，但很多“先查询、再修改”的逻辑没有行级锁或乐观锁。

重点风险：

- 两个请求同时收货，可能同时读取旧的累计收货数量。
- 两个请求同时入库，可能竞争库存余额。
- 两个请求同时创建相同业务异常，应用层的重复查询不能替代数据库级幂等约束。
- 两个管理员同时修改用户角色或业务草稿，后提交者可能覆盖先提交者。

### 7. 同一个请求执行两次会不会出问题？

部分完成。已经具备的保护包括：

- 数据库唯一约束。
- 订单状态、到货状态和验收状态检查。
- 入库流水按到货明细唯一。
- 同一来源未关闭同类自动异常不重复创建。

当前状态：

- 已有统一 `Idempotency-Key` 中间件和请求幂等记录表。
- 相同用户、路径、方法和请求体会回放首次成功或业务失败响应；不同请求复用 key 返回 409。
- 未带 header 的旧请求保持兼容，后续可通过配置逐步切换为强制幂等。

### 8. 返回结果规范吗？

基础完成：

- 成功响应使用明确的 Pydantic `response_model`。
- 分页响应统一包含 `items`、`total`、`page`、`page_size`。
- 成功响应保持原有数据结构，避免破坏当前前端。
- 失败响应统一包含 `code`、`message`、`detail`。

当前约定：

```json

  "code": 404,
  "message": "资源不存在",
  "detail": "采购订单 10086 不存在"
}
```

### 9. 出错时前端看得懂吗？

基础完成。当前统一处理 `400、401、403、404、405、409、415、422、500`，并为每个状态码提供中文 `message`。前端请求封装会优先展示具体业务 `detail`，没有具体 detail 时展示中文状态提示。

仍需改进：
