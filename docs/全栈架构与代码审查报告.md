### H-00 含税报价被重复加税并传递到对账和库存成本

- **处理状态：** 已修改订单税务口径快照、对账和入库成本计算，并新增迁移及定向单元测试；本机数据库已备份并应用 068 迁移，字段及台账校验通过。尚未完成隔离 MySQL 与端到端验收。历史订单税务口径保持未知，既有金额不会自动更正。
- **位置：** `backend/app/modules/purchase_orders/service.py:148` 的 `create_order`；`backend/app/modules/purchase_orders/model.py:59` 的订单明细；`backend/app/modules/finance/reconciliation_items.py:111` 的 `append_basis`；`backend/app/modules/inventory/service.py:302` 的 `create_inbound`；`backend/app/modules/rfqs/total_cost.py:90`。
- **证据与触发条件：** 报价明细有 `tax_included`，报价总成本计算区分含税与未税，但生成订单时始终以 `单价 × 数量 × (1 + 税率)` 计算金额，订单明细未保存该标记。对账和库存入库成本也将订单单价作为未税价再加税。例如含税单价 113、税率 13%、数量 1，订单及对账含税金额会按 127.69 计算，而不是 113。税率未知时还被当成零处理。
- **根因：** 报价到订单的字段契约丢失含税口径，下游各自假定单价未税。
- **影响：** 订单金额、对账应付金额和库存成本可能高估，实际付款、结算受错误依据影响；本发现不代表已发生真实付款。
- **修复：** 明确订单单价与税务快照的契约，保留来源含税标记，对含税、未税和未知口径分别处理；统一订单、对账和成本计算，并审慎核对历史记录。
- **验证：** 在隔离环境覆盖含税、未税和未知税率/含税标记，从中选报价追踪至订单、收货入库和对账，核对金额与舍入。
- **可信度：** 已确认代码计算行为和口径丢失；尚未运行跨模块集成复现。

### H-01 报价提交与定标并发可能重新打开已关闭询价

- **处理状态：** 报价公共入口在状态校验前锁定并刷新询价，供应商门户在截止时间和状态检查前锁定询价，报价版本以当前读取得。独立 MySQL 8.0 临时库验证了定标期间持有旧快照的迟到报价被拒绝，询价保持关闭；该并发测试替换了范围校验和审计函数，尚需完整门户与权限验收。
- **位置：** `backend/app/modules/supplier_portal/service.py:171` 的 `submit_rfq_quote`；`backend/app/modules/rfqs/service.py:202` 的 `create_quote_for_supplier`；同文件第 512 行的 `select_quote`。
- **证据与触发条件：** 报价入口无锁读取询价状态；定标时锁定询价并置为 `CLOSED`。报价请求先读取 `RESPONDING`，定标随后提交，迟到报价仍可能插入报价并把询价写回 `RESPONDING`。内部报价入口也调用同一创建函数。
- **根因：** 报价写入和定标没有共享询价锁及锁内状态重验。报价版本唯一约束不能阻止询价状态覆盖。
- **影响：** 已定标询价重新开放，产生定标快照之外的报价，后续比价和订单状态可能不一致。
- **修复：** 所有报价入口按定标的锁序锁定并刷新询价，在锁内重新检查状态、截止时间和报价版本。
- **验证：** 使用隔离 MySQL 的两个连接和同步屏障交错报价与定标，断言定标后询价保持关闭且迟到报价被拒绝。
- **可信度：** 高可信风险；未执行并发复现。

### H-01A 多张订单草稿可以重复使用采购申请剩余数量

- **处理状态：** 正式下单时已汇总来源申请明细数量，以当前读按明细主键顺序加锁并重新校验额度；单元测试覆盖剩余额度不足、拆分明细汇总及成功下单。独立 MySQL 8.0 临时库双连接并发验收通过：两个事务先建立旧快照后并发下单，一单成功、一单被拒绝，累计数量不超过申请额度。测试为聚焦并发替换了权限范围与审计函数，不能替代权限及完整业务流程验收。
- **位置：** `backend/app/modules/purchase_orders/service.py:49` 的 `_validate_request_item_quantities`、`:123` 的 `create_order` 和 `:303` 的 `place_order`；`backend/app/modules/rfqs/service.py:104` 的 `create_rfq`。
- **证据与触发条件：** 创建订单时用申请数量减已下单的 `fulfilled_quantity` 校验，但草稿不占用该数量。一个已审批申请可通过不同询价和比价生成多张草稿，草稿先后创建时都可能通过剩余量检查；正式下单时只锁各自订单，直接累加来源申请明细数量，不重新校验剩余量。例如申请 10，先创建两张各 10 的草稿，再分别下单。
- **根因：** 采购额度仅在草稿创建时检查，而正式下单时没有统一锁住来源申请明细并重新检查，草稿之间也没有占用机制。
- **影响：** 采购数量可能超过申请审批数量；并发下单还可能发生来源明细更新竞争。是否允许超额采购应以业务规则确认，但现有创建校验明确以剩余量为约束。
- **修复：** 确定额度在草稿或正式下单阶段占用；统一锁定申请及明细、按最新状态汇总并检查，处理草稿取消释放及并发锁序。
- **验证：** 在隔离库先后生成两张来源相同的订单草稿，再顺序及并发下单，断言已采购数量不超过申请数量，且失败事务不写订单事件。
- **可信度：** 高可信风险；尚未运行完整业务流程复现。

### H-02 并发付款申请可能超过对账总额

- **处理状态：** 有效付款及已付款金额统计改为按主键顺序的当前锁定读，配合既有对账单锁。独立 MySQL 8.0 可重复读临时库双连接测试通过：两个旧快照并发申请合计超额时仅一笔成功。测试替换了数据范围和审计函数，完整财务权限与业务流程尚需验收。
- **位置：** `backend/app/modules/finance/service.py:104` 的 `_sum_payments`，第 331 行的 `create_payment`。
- **证据与触发条件：** 付款申请锁定对账单后通过普通 `SUM` 统计有效付款；相邻发票统计使用锁定读。MySQL 可重复读下，第二个请求若在等待主单锁前已建立一致性快照，等待结束后的普通聚合可能看不到第一个请求刚提交的付款。
- **根因：** 主单锁串行化写入，但占用额度统计不保证读取最新已提交数据。
- **影响：** 合计超过对账金额的两个付款申请可能同时成功。这里讨论系统记录，不表示银行发生实际支付。
- **修复：** 在统一主单锁下以当前读统计有效付款，或维护受锁保护的占用金额；复核其他调用 `_sum_payments` 的流程。
- **验证：** 在隔离 MySQL 可重复读下让两个事务先建立快照，再并发申请合计超额，断言最多一个成功。
- **可信度：** 高可信风险；依赖实际隔离级别和事务时序，未运行并发测试。

### H-03 库存和补货申请状态流转存在竞态

- **处理状态：** 领用、调拨、盘点的编辑、提交、取消与审批共用主单锁，并对明细使用当前锁定读；补货提交和取消也锁定并刷新主单。独立 MySQL 8.0 可重复读临时库验证了四类申请的提交与取消竞态、领用迟到编辑及旧快照下最新明细读取。测试使用权限和审计替身，完整权限与库存执行流程仍需验收。
- **位置：** `backend/app/modules/inventory/service.py:476`、`:501`、`:549` 的领用编辑、提交和取消；`:738`、`:758`、`:806` 的调拨操作；`:1072`、`:1093`、`:1141` 的盘点操作；`backend/app/modules/replenishments/service.py:134`、`:175` 的补货提交和取消。
- **证据与触发条件：** 库存申请的编辑、提交和取消读取主单时不加锁，审批使用行锁。编辑先按草稿通过检查后，另一请求可能提交、审批，随后编辑再写入明细。补货提交和取消也可能基于旧状态互相覆盖。
- **根因：** 同一状态机各入口没有统一使用主单锁或版本条件。
- **影响：** 审批内容与最终明细不一致，或状态与审计记录矛盾。执行阶段的库存余额锁不能保证审批内容未被修改。
- **修复：** 所有编辑及状态迁移统一锁定并刷新主单，再检查状态、修改明细并提交；也可使用版本号和条件更新。
- **验证：** 双连接覆盖编辑与提交、提交与取消、编辑与审批等交错执行。
- **可信度：** 高可信风险；未运行并发复现。

### H-04 撤权后重新登录可能回放旧幂等响应

- **位置：** `backend/app/core/idempotency.py:193`、`:231` 的用户标识与响应回放；`backend/app/modules/system/service.py:150` 的 `_invalidate_role_members`；`tests/test_idempotency_api.py:34` 的现有撤权测试。
- **证据与触发条件：** 中间件校验有效令牌后以 `user:{id}` 查找缓存并直接回放，没有重新执行接口权限与资源范围校验。角色变更使旧令牌失效，但用户重新登录后仍使用相同用户标识。现有测试只覆盖旧令牌。
- **根因：** 幂等记录跨令牌版本复用，回放不重验当前授权。
- **影响：** 撤权用户若持有原幂等键和请求内容，可能在缓存有效期内读到原成功响应中的业务数据；回放本身不会再次执行业务写入。
- **修复：** 回放前重验授权和资源范围，或将响应与授权版本绑定并在权限变化时失效，同时保留防重复执行语义。
- **验证：** 创建含业务数据的响应，撤权、重新登录后复用同一键和请求，确认旧响应不可读取且业务未重复执行。
- **可信度：** 高可信风险；具体接口的响应内容和授权变更路径仍需复现。

### H-05 补货可由无关订单标记为全部完成

- **位置：** `backend/app/modules/replenishments/service.py:186` 的 `complete_replenishment`。
- **证据与触发条件：** 完成时仅检查订单属于同一供应商且处于正式下单、部分到货或完成状态，然后将全部补货明细标记 `FULFILLED`；未比较产品、单位及数量。相同供应商的其他产品订单可通过现有检查。

- **可信度：** 已确认代码行为；最终业务影响取决于“完成”的业务定义。

### H-06 Agent 将质量隔离库存计入可用量

- **位置：** `backend/app/modules/ai/agent_tools.py:179` 的 `query_inventory`、`:238` 的 `replenishment_plan`；`backend/app/modules/ai/text2sql.py:307`；`backend/app/modules/inventory/service.py:103` 的库存读取模型。

- **修复：** 由调用方控制元数据与关联的数据库事务，并设计对象失败补偿和孤儿清理。
- **验证：** 在上传后注入关联写入失败和进程中断，检查恢复、重复提交及清理。
- **可信度：** 已确认事务边界；残留规模和现有运维清理能力未验证。

### M-05 同步扫描阻塞异步上传事件循环

- **位置：** `backend/app/modules/files/controller.py:21` 的异步 `upload_file`；`backend/app/modules/files/service.py:353`；`backend/app/modules/files/scanner.py:20` 的 `scan_content`。
- **证据与触发条件：** 异步端点读取文件后直接调用同步上传服务；启用扫描时执行同步 `subprocess.run`。供应商质量资料与验收报告也使用该上传服务。
- **根因：** 阻塞扫描、数据库和对象存储操作直接运行在异步请求路径。
- **影响：** 慢扫描或存储延迟可能拖慢同一事件循环上的其他请求；程度取决于部署和并发。
- **修复：** 将阻塞部分移至有界线程池或独立任务，控制并发并保持扫描失败时的拒绝行为。
- **验证：** 模拟慢扫描，同时请求健康接口和 SSE，测量延迟及资源占用。
- **可信度：** 高可信风险。

### M-06 业务日期依赖服务器时区

- **位置：** `backend/app/modules/deliveries/service.py:176` 的默认收货日期；`backend/app/modules/jobs/service.py:94` 的逾期扫描；`backend/app/core/time.py:17` 的 `business_today`。
- **证据与触发条件：** 已有北京时间业务日期工具，但收货和扫描仍用 `date.today()`。服务器为 UTC 且北京时间刚过午夜时，日期仍为前一天。
- **根因：** 业务日期协议未统一应用。
- **影响：** 跨时区部署时收货日期、逾期告警和部分统计可能偏差一天。
- **修复：** 逐项将业务日期计算统一到 `business_today()`，同时保留历史时间来源区分。
- **验证：** 固定北京时间午夜前后的时刻，在 UTC 和上海进程时区下比较结果。
- **可信度：** 高可信风险；实际部署时区未验证。

### M-07 浮点短交数量可能导致收货被拒绝

- **位置：** `frontend-design/apps/web-chemicalops/src/views/warehouse/deliveries/modules/receive.vue:132`；`backend/app/modules/deliveries/service.py:148` 的 `receive_delivery`。
- **证据与触发条件：** 前端用 JavaScript 浮点计算计划减实收，后端用 `Decimal` 精确检查。已用 Node 和 Python 验证：计划 `0.3`、实收 `0.2` 时短交为 `0.09999999999999998`，十进制和不等于 `0.3`。
- **根因：** 二进制浮点结果传入精确十进制业务约束。
- **影响：** 合法的小数短交可能被拒绝，用户无法完成收货。
- **修复：** 使用十进制字符串运算，或由后端根据计划和实收计算短交，统一数量精度契约。
- **验证：** 覆盖 `0.3/0.2`、多位小数及整数的页面到接口测试。
- **可信度：** 已确认计算及契约不匹配；未做浏览器复现。

### M-08 Agent 补货建议权限码错误且潜在范围未裁剪

- **证据与触发条件：** Agent 检查 `procurement.replenishments.read`，实际权限码为 `procurement.replenishment.read`。普通有权用户通常被判为无权，未完成补货量记零。该聚合本身也没有应用补货列表的申请人和部门范围。
- **根因：** 权限码和资源范围逻辑重复实现且发生漂移。
- **影响：** 建议量可能偏大；若只修正权限码而不加范围约束，可能泄露超范围汇总。
- **修复：** 统一权限定义并复用补货服务的可见范围，无权或范围不完整时明确结果限制。
- **验证：** 分别以管理员、普通采购员和部门受限用户测试本人及他人补货记录。
- **可信度：** 权限码错误已确认；修正后的越权为高可信风险。

### M-09 供应商准时率分母包含不可判定记录

### M-10 多个业务选择器只加载前 100 条

### M-11 异步旧响应可能覆盖当前页面上下文

- **位置：** `frontend-design/apps/web-chemicalops/src/views/supplier-portal/shipments/index.vue:65` 的 `onOrderChange`；`frontend-design/apps/web-chemicalops/src/views/finance/reconciliations/modules/items.vue:52` 的 `load`。
- **证据与触发条件：** 快速选择 A 后选择 B，A 若后返回，会覆盖 B 的明细，但选中订单仍是 B；后端检查明细归属并拒绝不匹配提交。财务抽屉关闭并打开其他记录时，旧请求也可能覆盖新内容，保存入口使用当前显示的记录 ID。
- **根因：** 异步返回时未核对请求对象或版本仍是当前上下文。
- **影响：** 显示与当前选择不一致；财务人员可能在错误记录上下文操作，实际提交仍受后端权限和状态校验约束。
- **修复：** 使用请求代次或取消信号，在更新状态和提交前核对对象 ID；切换期间禁用提交。
- **验证：** 人为延迟 A 请求使 B 先返回，覆盖订单选择、抽屉重开及保存。
- **可信度：** 高可信风险；未做浏览器复现。
