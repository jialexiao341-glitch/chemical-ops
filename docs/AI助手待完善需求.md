# ChemicalOps AI 助手待完善需求

> 目标：在现有“只读查询助手”的基础上，逐步建设具备多轮理解、业务分析、风险发现、报告生成和可审计辅助操作能力的 AI 工作台。
>
> 原则：AI 默认只读；任何采购、库存、财务和异常写操作，都必须由用户在正式业务页面确认，并调用现有业务 API 执行。

## 一、当前已有能力

- 支持采购、库存、到货、质量、异常、财务和供应商等业务数据的只读查询。
- 使用白名单数据集、ORM 查询和 SELECT-only 校验保护 Text2SQL。
- 支持普通对话和 SSE 流式对话。
- 支持会话历史、消息持久化和会话删除。
- 支持附件上传、权限校验、ClamAV 复扫、本地解析和 MinerU 解析。
- 支持图片附件的视觉理解。
- 支持查询条件、SQL、结果行、截断状态和附件解析结果 Trace。
- 支持外部 AI 服务失败重试、降级提示、请求指标和结构化日志。

## 九、LangGraph 编排与状态持久化

### 9.1 当前实现现状

当前 Text2SQL 已使用 LangGraph 编排以下流程：

```text
问题理解
  -> 槽位填充
  -> 查询规划
  -> SQL 校验
  -> 只读执行
```

当前实现使用 `MemorySaver`，并且每次请求重新创建 Graph 和随机 `thread_id`。因此目前只能保证单次请求内的图状态，不具备跨请求、跨进程和服务重启后的恢复能力。

### 9.2 Checkpointer 与业务会话的职责划分

LangGraph Checkpointer 和业务会话表不是同一种数据：

| 数据类型 | 推荐存储 | 主要用途 |
|---|---|---|
| 用户可见消息 | `ai_messages` | 展示对话、答案和引用 |
| 会话元数据 | `ai_conversations` | 用户、标题、权限范围、状态 |
| 查询计划和 Trace | `ai_query_runs` 或 `ai_conversation_state` | 多轮查询、结果解释、审计 |
| LangGraph checkpoint | 专用持久化 Checkpointer | 节点状态、暂停点、恢复和故障续跑 |
| 附件和解析结果 | 对象存储 | 原文件、Markdown、报告文件 |
| 长期用户偏好 | MySQL Store 或独立 Store | 常用筛选、偏好和跨会话记忆 |

禁止将完整 LangGraph checkpoint 直接写入 `ai_messages`，避免把内部执行状态和用户可见消息混在一起。

### 9.3 第一阶段：复用 MySQL 保存结构化状态

当前项目主数据库是 MySQL，短期优先采用 MySQL 保存业务层状态，不立即引入新的数据库类型。

建议新增 `ai_query_runs` 或 `ai_conversation_state`，至少保存：

- `conversation_id`。
- 稳定的 `thread_id`。
- 当前 QueryPlan。
- 数据集、指标、时间范围和过滤条件。
- 上一轮结果摘要。
- 当前权限版本或权限摘要。
- 附件 ID、解析状态和引用信息。
- 状态版本和更新时间。

LangGraph 负责流程编排，MySQL 负责业务可见状态和多轮上下文。下一轮请求读取 MySQL 状态后，重新构造 LangGraph 初始状态。

稳定的线程标识建议使用：

```python
thread_id = f"ai:{user.id}:{conversation.id}"
```

要求：

- 每次查询仍然重新校验当前用户权限。
- `thread_id` 不能单独作为权限依据。
- 不保存附件原文、API key、密码或未经脱敏的敏感字段。
- 查询结果只保存必要摘要，完整附件和解析结果放在对象存储。

### 9.4 第二阶段：引入持久化 Checkpointer

当系统支持以下能力时，再引入正式的持久化 Checkpointer：

- 长时间运行的报告生成任务。
- 人工审批中断和恢复。
- 外部 AI 或 MinerU 失败后的断点续跑。
- 多节点、多工具的复杂 Agent。
- 跨进程、跨实例的任务恢复。

可选方案：

1. 实现 MySQL 版 `BaseCheckpointSaver`，保持单一数据库体系。
2. 单独部署 PostgreSQL，使用官方 `PostgresSaver`。
3. 使用 Redis 等外部 Checkpointer，但必须配置持久化、备份和过期策略。

选择标准：

- 生产环境不能使用 `MemorySaver` 作为唯一状态存储。
- Checkpoint 表需要索引 `thread_id`、会话 ID、更新时间和状态版本。
- 必须制定 checkpoint 保留和清理策略，避免长会话无限增长。
- Checkpoint 内容需要进行敏感字段过滤或加密。
- 数据库 checkpoint 和业务审计记录需要能够相互关联。

### 9.5 LangGraph 状态建议

后续统一定义 AI 工作流状态，建议包含：

```text
user_id
conversation_id
thread_id
messages
intent
query_plan
permission_context
attachment_refs
query_trace
citations
tool_calls
retry_count
error_state
approval_state
```

其中：

- `messages` 只保留必要的会话上下文。
- `permission_context` 只保存权限摘要，执行节点仍需实时校验。
- `attachment_refs` 只保存文件 ID 和对象键，不保存原始二进制。
- `query_trace` 保存可解释查询信息，不保存未脱敏敏感数据。
- `approval_state` 为未来草稿确认和人工审批预留。

### 9.6 LangGraph 持久化验收标准

- 使用稳定 `thread_id` 可以继续同一会话的结构化查询上下文。
- 服务重启后，持久化状态可以恢复。
- 多实例部署时不会因内存状态丢失导致会话断裂。
- 人工审批暂停后可以从原节点继续执行。
- checkpoint 和用户可见消息不会重复或互相污染。
- 权限变化后，恢复执行前会重新进行权限校验。
- checkpoint 定期清理，不无限增长。
- 失败恢复不会重复执行已经完成的写操作。

## 十、Redis 使用规划

### 10.1 是否必需

Redis 不是当前 AI 助手的必需组件。现阶段可以使用：

```text
MySQL       业务数据、会话、消息、引用和审计
对象存储    附件原文、MinerU 解析结果和报告文件
LangGraph   AI 查询和分析流程编排
```

暂不为了引入 AI 而强制增加 Redis，避免在业务规模尚未需要时增加部署、监控、备份和故障处理成本。

### 10.2 适合使用 Redis 的场景

后续出现以下需求时再引入 Redis：

- 多实例部署时，在实例之间共享 SSE 流式状态和取消信号。
- MinerU 解析、报告生成、Excel/PDF 导出等异步任务队列。
- 限制单用户并发 AI 请求、模型调用频率和附件解析数量。
- 缓存短期查询计划、模型配置、热点指标和重复查询结果。
- 保存短期的 Agent 运行状态和任务进度。
- 使用 Redis 作为 LangGraph Checkpointer，支持跨进程恢复长任务。

### 10.3 Redis 不应作为唯一数据源的内容

以下内容仍应保存在 MySQL 或对象存储中：

- 用户可见聊天记录。
- 业务审计记录。
- 采购、库存、财务和权限数据。
- AI 最终执行结果。
- 附件原文和 MinerU 完整解析结果。

Redis 中只保存必要的任务状态、缓存值、事件或对象引用，不保存 API key、密码、完整附件正文和未经脱敏的敏感财务数据。

### 10.4 引入顺序

建议按以下顺序建设：

```text
当前阶段：MySQL + 对象存储 + LangGraph
    -> 多轮上下文和 ai_query_runs
    -> Redis 队列、限流、缓存和流式协调
    -> 长时间运行 Agent 的 Redis/PostgreSQL Checkpointer
```

Redis Checkpointer 只有在需要长时间运行、人工审批暂停、断点续跑或多实例恢复时才启用。启用后必须配置：

- AOF 或等效持久化策略。
- 高可用和故障切换方案。
- checkpoint 的 TTL、归档和清理策略。
- 内存上限和淘汰策略。
- 备份、恢复和监控告警。
- checkpoint 敏感字段过滤或加密。

### 10.5 Redis 引入验收标准

- Redis 故障时，核心业务数据和历史会话不丢失。
- 任务重复投递不会重复执行不可逆业务操作。
- AI 请求具备用户级和系统级并发限制。
- 异步任务支持查询状态、重试、取消和失败告警。
- SSE 断开后不会遗留无限期运行的任务。
- Redis 数据可以按任务、会话和时间范围清理。
- Redis 中不出现未经脱敏的敏感内容或附件原文。

### 2.1 多轮上下文查询

支持在同一会话中继承和修改上一轮查询条件，例如：

- “那上个月呢？”
- “只看华东供应商。”
- “把刚才的结果按金额倒序排列。”
- “只显示前五名。”
- “继续分析第二个附件。”

要求：

- 保存结构化 QueryPlan，而不是只保存自然语言消息。
- 明确显示本轮继承了哪些条件、修改了哪些条件。
- 用户可以清空当前查询上下文。
- 权限每一轮重新校验，不能直接复用旧权限结果。

验收标准：

- 多轮查询不会错误继承上一轮的时间范围或数据集。
- 权限变化后，新的查询按当前权限执行。
- Trace 中展示本轮最终生效的完整查询条件。

### 2.2 扩展业务查询范围

补充以下查询主题：

- 采购申请及审批节点、审批耗时和逾期情况。
- 采购订单明细、交付完成率和未交付数量。
- 到货、收货和质量验收之间的关联情况。
- 库存批次、保质期、安全库存和冻结库存。
- 供应商交付及时率、质量合格率和采购金额。
- 异常负责人、处理时长、逾期任务和关闭率。
- 发票、付款、对账和差异明细。

要求：

- 每个数据集明确可查询字段、聚合指标、过滤条件和权限编码。
- 高风险财务字段默认只返回汇总，明细需要额外权限。
- 大结果集使用分页、汇总或时间范围限制。

### 2.3 查询结果图表化

根据结果自动选择合适的展示方式：

- 时间趋势：折线图。
- 供应商或产品排名：柱状图。
- 状态分布：饼图或堆叠柱状图。
- 库存和异常预警：风险表格。
- 订单流程状态：漏斗或阶段分布。

要求：

- 图表数据必须来自同一份已验证查询结果。
- 图表旁显示数据范围、统计口径、单位和更新时间。
- 无法安全确定图表类型时回退到表格。

### 2.4 更完整的来源引用

数据库查询引用应支持：

- 数据集和查询时间。
- 订单号、申请单号、到货单号或异常编号。
- 供应商、产品、批次等业务标识。
- 数据权限范围。

附件引用应支持：

- 文件名和文件 ID。
- 解析器和解析状态。
- 页码、段落、表格或工作表定位。
- 解析结果对象存储地址。

## 三、第二阶段：业务分析与风险发现（P1）

### 3.1 主动发现业务异常

优先支持：

- 供应商连续延迟交付。
- 化学品库存低于安全库存。
- 批次即将过期或已经过期。
- 采购价格明显偏离历史均值。
- 订单长期停留在某个审批节点。
- 质量验收不合格率异常升高。
- 发票、付款和对账金额不一致。

要求：

- 每条风险必须包含事实、计算口径、影响范围和数据来源。
- 区分“数据库事实”和“AI 推断”。
- 不确定时明确提示需要人工确认。
- 支持跳转到对应业务详情页。

### 3.2 生成业务分析报告

支持生成：

- 采购日报、周报和月报。
- 库存风险报告。
- 供应商绩效报告。
- 到货逾期报告。
- 质量异常报告。
- 财务对账差异报告。

报告应包含：

- 结论摘要。
- 关键指标和趋势。
- 异常明细。
- 数据来源和查询时间。
- 待处理建议。
- 报告生成版本和操作者。

### 3.3 附件抽取与对比

支持从报价单、合同、送货单、检测报告和发票中抽取结构化字段：

- 供应商。
- 产品和规格。
- 数量和单位。
- 单价和币种。
- 交付周期。
- 付款条件。
- 证书和资质。
- 缺失字段。

支持多附件对比：

- 报价差异。
- 交付周期差异。
- 付款条件差异。
- 规格和包装差异。
- 证书完整性差异。

要求：

- 每个抽取字段可追溯到文件位置。
- 未识别字段不能由模型猜测填充。
- 结构化抽取结果进入临时草稿，不直接覆盖业务数据。

### 3.4 结果导出

支持将查询和分析结果导出为：

- Excel。
- CSV。
- PDF。
- 可打印的业务报告。

要求：

- 导出内容继承当前用户权限。
- 记录导出人、导出时间、查询条件和数据范围。
- 大文件使用后台任务生成，并提供状态查询。

## 四、第三阶段：辅助操作与审批闭环（P2）

### 4.1 生成业务草稿

AI 可以生成但不能直接提交：

- 采购申请草稿。
- 异常处理任务草稿。
- 付款申请草稿。
- 供应商沟通邮件草稿。
- 补货建议草稿。

### 4.2 用户确认后执行

执行流程必须是：

```text
用户提问
  -> AI 读取数据
  -> AI 生成结构化草稿
  -> 用户在正式页面查看和修改
  -> 用户明确确认
  -> 调用现有业务 API
  -> 返回执行结果
```

禁止：

- AI 直接执行任意 SQL 写操作。
- AI 直接修改采购、库存、财务或权限数据。
- AI 绕过现有权限、审批和幂等校验。

必须记录：

- AI 建议内容。
- 建议生成时使用的数据来源。
- 用户确认人和确认时间。
- 实际执行人。
- 实际调用的业务 API。
- 执行前后关键字段。
- 最终成功或失败结果。

## 五、第四阶段：AI 质量与运营管理

### 5.1 评测体系

建立固定回归集，覆盖：

- 常见业务查询。
- 多轮查询。
- 空结果和超大结果。
- 权限越权。
- 敏感数据脱敏。
- Text2SQL 危险输入。
- 附件解析成功、失败、超时和缺失结果。
- SSE 中断和外部服务失败。

### 5.2 质量指标

持续统计：

- 查询成功率。
- 查询计划解析成功率。
- SQL 白名单拒绝率。
- 答案引用完整率。
- 用户重试率。
- 外部模型失败率。
- MinerU 失败率和平均耗时。
- 首 Token 时间和完整响应耗时。
- 用户反馈的正确/错误比例。

### 5.3 用户反馈

支持对每个回答进行：

- 有帮助。
- 无帮助。
- 数据错误。
- 引用错误。
- 权限问题。

反馈需要关联：

- 会话和消息。
- 查询 Trace。
- 模型版本。
- 用户反馈原因。

## 六、安全和权限要求

- 每次业务查询重新校验当前用户权限。
- 业务资源和附件权限不能只依赖会话创建时的快照。
- 默认隐藏手机号、密钥、密码、完整财务敏感字段等内容。
- 日志不写入原始问题、答案、附件正文和带参数 SQL。
- 限制单次查询行数、附件数量、上下文长度和图片大小。
- 外部服务不可用时，明确返回降级状态，不能编造结果。
- 所有写操作必须进入现有业务 API 和审批流程。
