# ChemicalOps 后端生产化补齐方案

本文基于当前后端代码结构进行整理，目标是把已有业务型 MVP 推进到可安全试用、可持续运维、可逐步交付的后端服务。本文不是对旧进度文档的复述，也不假设所有客户都有相同的银行、税务或化学品监管要求。

## 一、当前判断与完成目标

当前后端已经覆盖采购申请、询价报价、采购订单、到货、质量验收、库存、退货/补货、财务单据、供应商门户、文件和 AI 只读查询等模块；已有 JWT/RBAC、部分行锁、审计记录、请求幂等、健康检查、指标及备份/恢复工具。

目前主要短板不是缺少业务模块，而是生产配置、数据库升级、安全运营和多实例运行的保障还没有形成一致的强制流程；部分能力虽有代码实现，也需要在目标部署环境验证。本文建议分三层推进：

1. **内部试点门槛：** 生产配置拒绝危险默认值；数据库升级可追踪、可恢复；关键写流程有真实 MySQL 并发和故障测试；权限和文件安全通过验收；备份恢复实际演练。
2. **稳定运行门槛：** 登录防护、会话撤销、集中指标与告警、可靠后台任务和明确的故障处理流程。
3. **客户业务闭环：** 根据目标客户决定银行/税务系统和化学品法规能力，不把未经确认的行业规则写成通用假设。

完成标准不是“所有功能都做完”，而是每个上线功能都有明确责任边界、配置方式、失败行为、验证证据和恢复办法。

## 二、生产配置强制安全门

### 为什么要补

开发环境通常允许占位密钥、关闭病毒扫描、宽松 CORS 或非强制幂等，方便本地启动。若生产部署依赖人工记得改环境变量或手动运行检查脚本，漏配时服务仍可能启动并接受请求。此类错误通常不会在普通功能测试中暴露，直到令牌被伪造、文件未扫描、重复写入或浏览器跨域策略过宽时才造成影响。

### 补完后的效果

- 危险配置不会静默进入生产环境。
- 部署平台能得到明确的失败原因，而不是服务看似正常、实际处于降级状态。
- 开发、测试、预发布、生产的配置边界可以被自动检查和审计。

### 怎么落实

1. 建立唯一的生产配置校验入口，例如 `validate_runtime_settings(settings)`；应用启动和部署检查脚本调用同一套规则，避免两份规则逐渐不一致。
2. 生产环境至少检查：`DEBUG=false`、随机且足够长的 JWT 密钥、非空且独立的数据库/对象存储凭据、管理员初始密码已替换、演示账号未启用、正式 CORS 来源清单、AI 写工具关闭、文件扫描配置有效、对象存储桶可用、幂等策略已确定。
3. 明确生产存储策略：若支持本地文件后端，必须说明其仅适用单机持久盘并配置备份；多实例环境应要求共享对象存储。文件扫描应验证扫描程序可执行并做实际扫描探针，不能只检查配置字符串非空。
4. 在 FastAPI `lifespan` 开始接收流量前执行校验。生产配置错误时抛出启动异常并以非零状态退出；数据库或对象存储暂时不可用时，由部署平台的 readiness 探针阻止流量，并设置合理的重试/启动策略。
5. 将生产配置检查放入 CI/CD 发布门禁；检查结果不得输出密码、令牌或完整连接串。
6. `Idempotency-Key` 是否在生产强制，应与前端和所有 API 客户端的支持同步上线，避免服务端先强制、客户端仍不能发送。

### 验收标准

- 用占位 JWT 密钥、默认管理员密码、缺失扫描器或非法 CORS 启动生产环境时，进程明确拒绝启动。
- 使用正确配置时，启动检查确认 MySQL、对象存储和文件扫描能力可用。
- 生产检查和服务启动共用相同校验逻辑；错误信息指出配置项名称但不泄漏配置值。
- 预发布环境可以完整执行与生产相同的部署检查。

## 三、数据库迁移与恢复流程

### 为什么要补

全新数据库初始化和已有数据库升级是两种不同操作。全量建库 SQL 含有删除表语句，因此只能用于受保护的空库初始化；线上升级若靠人工挑选多个迁移脚本，容易漏跑、错序、重复跑或无法确认数据库处于哪个版本。MySQL 的部分 DDL 会隐式提交，不能假设整个迁移脚本都能像普通业务事务一样回滚。

### 补完后的效果

- 每个环境都能回答“当前数据库版本是什么、还差哪些迁移”。
- 发布失败时能判断迁移是否已部分执行，并按已演练步骤恢复。
- 新环境初始化和线上升级不会误用同一条破坏性路径。

### 怎么落实

1. 保留全新环境初始化流程，但要求空库检查、显式确认目标库名，并拒绝生产数据库误用全量 schema 初始化脚本。
2. 选择一个统一迁移执行机制：采用 Alembic，或保留编号 SQL 并实现统一 runner。不要长期让“每个迁移一份单独执行脚本”成为发布操作手册。
3. 建立迁移版本表，记录版本号、校验和、开始/结束时间、执行结果和应用版本。runner 应按顺序执行、获得数据库级迁移锁、跳过已成功迁移，并在校验和变化时失败退出。
4. 迁移分为预检、备份确认、应用、迁移后校验四步。预检可检查重复键、字段兼容、预计影响行数和磁盘空间；危险数据变更不得自动猜测如何合并。
5. 为 MySQL DDL 制定恢复策略：优先采用向前修复迁移；需要回滚时恢复迁移前备份或执行经过演练的补偿迁移。不要把“脚本支持再次运行”误当成“迁移可回滚”。
6. 对历史重复数据准备逐条处理报告：主键、来源业务单据、重复条件、保留/合并/归档规则、执行人和复核结果。迁移检测失败时继续保持 fail-closed。
7. 在 CI 中至少验证空库初始化、从上一发布版本升级、重复执行无变化、迁移中断后可恢复；在预发布环境使用与生产同版本的 MySQL 演练。

### 验收标准

- 有唯一命令可查询数据库版本并按序升级。
- 在已有库上升级不会执行全量 `DROP/CREATE` 初始化。
- 迁移前自动备份或验证已存在可用备份，并记录备份标识。
- 空库、旧版本库、重复运行和中断恢复四类场景有可复现记录。
- 定期恢复演练能将备份恢复为可登录、可读取核心业务数据的服务。

## 四、账号安全与令牌撤销

### 为什么要补

密码哈希和 JWT 解决了密码不明文保存及请求认证问题，但它们本身不会阻止密码猜测，也不会自动使已签发令牌失效。用户停用后当前用户查询可以拒绝其请求；但改密后旧令牌仍可能在有效期内继续使用。若账号被盗或员工离职，缺少快速撤销能力会扩大风险窗口。

### 补完后的效果

- 登录暴力尝试的成本增加，账号异常行为可被发现和处置。
- 管理员停用用户、用户改密或安全事件发生后，可以及时撤销现有会话。
- 用户可安全地结束单个设备会话或结束全部会话，权限变更有审计记录。

### 怎么落实

1. 增加登录失败保护：按账号和来源 IP 组合限速，连续失败采用递增等待时间；错误响应不泄露“用户不存在”还是“密码错误”。避免永久锁号造成简单拒绝服务，并提供管理员解锁/审计。
2. 限速状态必须适配部署形态：多 worker 或多实例使用共享 Redis/数据库存储；不能只放进单进程内存，否则攻击者可通过切换 worker 绕过限制。
3. 引入会话撤销机制。简化方案是在用户表维护 `auth_version`，JWT 携带签发版本，每次认证与用户当前版本比较；改密、停用用户或安全重置时递增版本。若要求设备级退出，再增加会话表和 JWT `jti`。
4. 评估刷新令牌：访问令牌保持较短有效期，刷新令牌轮换并可撤销；明确登出、改密、角色权限变化和“登出所有设备”的语义。
5. 对密码修改、管理员重置密码、角色变化、账号停用和失败阈值触发记录审计事件；日志不记录密码、完整 JWT 或验证码。
6. 预留密码重置/邀请流程。邮件或短信服务接入前，令牌应一次性、短时有效且只存哈希。
7. MFA/SSO 不应盲目作为所有 MVP 的前置条件；如果目标客户已有身份提供方或有强制要求，再定义 OIDC/SAML 集成范围。

### 验收标准

- 超过配置阈值的失败登录会触发可观测的延迟/限制，成功登录后按策略恢复。
- 停用用户、修改密码或管理员撤销会话后，旧令牌立即或在明确的短窗口内失效。
- 多进程部署时限速及撤销行为一致。
- 关键账号操作有审计记录，敏感凭证不会写入日志。

## 五、幂等策略与业务写入可靠性

### 为什么要补

网络超时会让客户端不知道写请求是否已经成功；用户再次点击可能创建重复单据、重复扣库存或重复登记付款。统一幂等中间件解决了部分重试问题，但默认允许无幂等键；而当前实现会缓冲带键请求的响应体，不适合 SSE 等长流。正在处理中的记录若遇进程崩溃，也需要清理或恢复机制。

### 补完后的效果

- 客户端安全重试不会重复产生业务副作用。
- 并发重复提交能得到确定结果；复用同一个键但请求不同会明确冲突。
- 流式响应不会因普通写接口的缓存策略而失去实时性。

### 怎么落实

1. 制作写接口清单，逐项标记：必须幂等、由业务唯一约束保护、只允许一次状态转换、或明确不支持重试。覆盖创建、提交、审批、付款登记、收货、库存执行、文件上传等入口。
2. 给幂等策略定义稳定语义：键按用户/租户、HTTP 方法、路径和请求摘要隔离；键必须在客户端一次业务操作的所有重试中保持相同，不能每次重试重新生成。
3. 将幂等键要求逐步设为生产必需，并确认 Web 前端、供应商门户、后台任务和外部 API 客户端都能正确发送。
4. 设置 `IN_PROGRESS` 租约和超时恢复。处理进程崩溃后，不能永久阻塞相同键；恢复前须确认业务事务是否完成，避免删除记录后再次执行已提交操作。
5. 只对普通、大小受限的 JSON 写响应做响应缓存；回放时保留必要状态码、内容类型及业务相关响应头。超大响应、文件流、SSE 不进入通用缓冲路径。
6. 对 SSE 单独设计轮次标识和恢复语义，或者明确其不接受通用幂等键；不要为了统一而缓存整条 AI 流。
7. 将并发正确性同时落实在数据库：关键唯一约束、行锁或原子更新与应用幂等互补，不能只依赖中间件。

### 验收标准

- 同一用户、同一请求和同一键并发发送时，最多产生一份业务副作用并返回一致结果。
- 同一键用于不同请求时稳定返回冲突。
- 发生业务 4xx、5xx、超时、服务重启、响应中断时，重试语义明确且不会重复扣库存/付款。
- SSE 仍逐段到达客户端；文件响应不会被读入无界内存。
- 核心库存、收货和财务场景在真实 MySQL 并发测试中通过。

## 六、测试覆盖与发布门禁

### 为什么要补

单元测试可证明部分规则，接口测试可证明请求/响应契约；但只有针对真实数据库的并发测试、完整状态机测试和部署测试，才能覆盖锁、唯一索引、事务边界、迁移和配置错误。SQLite 测试通过并不能证明 MySQL 行锁或 DDL 行为正确。

### 补完后的效果

- 每次改动都能自动拦截核心流程回归、权限遗漏和迁移问题。
- 发布人员可以看到哪些风险已验证、哪些仍需人工验收。
- 生产事故能够定位到缺少的测试类别并补入长期门禁。

### 怎么落实

1. 为各业务模块建立同一测试矩阵：正常流转、非法状态、越权、资源不存在、并发竞争、重复请求、事务失败回滚和分页边界。
2. 优先补齐采购订单、询价、到货、质量验收、异常任务和系统权限的完整状态转换；覆盖“驳回后修改重提”“部分到货”“复检”“重复付款流水”等真实边界。
3. 使用真实 MySQL（临时容器或 CI 服务）运行涉及行锁、唯一约束、DDL、事务隔离和迁移的测试；可继续用 SQLite 做快速单元测试，但不能替代 MySQL 验证。
4. 为外部服务使用可控替身：模拟 MinIO 不可用、病毒扫描超时/拒绝、AI 超时/限流、MinerU 解析失败和 scheduler 中断。
5. 在 CI 设置分层门禁：静态检查与单测、MySQL 集成测试、前端构建/契约验证、迁移升级验证；依赖安全扫描作为发布检查。
6. 对关键风险生成覆盖率或场景清单，而不只追求单一行覆盖率百分比。并发测试需说明连接数、worker 数、通过条件和执行时间。
7. 维护一套预发布验收脚本，登录不同角色，跑采购至库存以及财务关键闭环，并验证 readiness、文件上传/下载和告警。

### 验收标准

- CI 在干净环境可重复安装、建库、迁移、执行后端测试并完成前端契约构建。
- 核心业务状态机与越权矩阵有明确用例和责任模块。
- 并发测试使用目标数据库引擎，失败注入能证明事务不留半成品。
- 发布记录包含 commit、迁移版本、测试结果和未覆盖风险。

## 七、监控、后台任务与恢复能力

### 为什么要补

进程内指标只属于当前 worker；重启后重置，多 worker/多实例也不会自然聚合。独立循环脚本可以运行定时扫描，但若部署多个调度器或任务执行一半崩溃，需要能判断谁在执行、执行到哪里、是否可安全重跑。没有恢复演练的备份也不能证明数据可恢复。

### 补完后的效果

- 服务异常、外部依赖故障、任务积压和性能退化能及时发现。
- 后台任务可以追踪每次执行及失败原因，在多实例环境避免无意重复调度。
- 数据丢失或迁移失败后有经验证的恢复路径。

### 怎么落实

1. 将 API、AI、文件解析、扫描器、数据库连接池及后台任务指标导出到集中监控系统；多 worker 场景使用 Prometheus 多进程支持或 OpenTelemetry/OTLP。
2. 采集请求量、错误率、P50/P95 延迟、数据库池等待、AI/MinerU/对象存储失败、解析积压、逾期扫描时长和重试次数。标签只用有限枚举，不放用户 ID、单据 ID、问题文本或文件名，避免敏感信息和高基数爆炸。
3. 设置告警阈值和处理人：数据库不可用、连续 5xx、病毒扫描不可用、迁移失败、后台任务连续失败、备份缺失和存储空间不足。
4. 为任务增加运行记录（任务类型、运行 ID、开始/结束、状态、尝试次数、错误摘要、处理数量）。多实例时使用数据库租约/锁或专用任务队列进行 leader/任务领取；任务本身仍需幂等。
5. 对通知或未来邮件/银行 API 采用 outbox 或可重试任务记录，避免业务事务提交成功但外部通知永久丢失。
6. 自动化数据库备份、加密并复制到独立故障域，设置保留期；定期执行恢复演练，记录 RPO/RTO 和恢复耗时。
7. 区分 liveness 和 readiness：liveness 只判断进程是否活着，readiness 检查接流量所需依赖；外部依赖短暂故障不能导致探针语义混乱。

### 验收标准

- 多 worker/多实例指标可聚合；服务重启后历史指标仍由监控平台保留。
- 定时任务多实例运行不会重复产生业务副作用，失败可追溯和重试。
- 告警能触发到明确的处理通道，并有演练记录。
- 按既定 RPO/RTO 从备份恢复到可登录、可查询和可继续处理业务。

## 八、财务与化学品外部闭环

### 为什么要补

业务系统里手动把付款标为已付，只能记录操作人员提供的结果，不能证明银行实际扣款成功；人工录入发票也不能替代税务验真。化学品的分类、标签、SDS、储存与运输限制取决于产品和司法辖区。若系统呈现为“已合规”却没有权威数据源或明确责任边界，会带来账务和安全风险。

### 补完后的效果

- 财务状态可追溯到真实支付/银行流水来源，减少重复付款与人工对账。
- 化学品关键安全资料、版本和有效期能关联到产品/供应商/库存批次，并在过期或不符合条件时提示。
- 系统明确哪些判断来自外部系统、哪些是人工确认、哪些仅是提醒。

### 怎么落实

1. 先与业务方确定一期范围：是否必须自动对接银行、是否要求电子发票验真、使用国家/地区、涉及化学品类别、SDS 来源和更新责任人。没有此确认，不应先写供应商专属 API 或把法规规则硬编码。
2. 财务按可逐步交付的顺序推进：先支持受控的银行流水文件导入和对账；随后根据客户银行接入 API/Webhook；支付回执使用外部交易号唯一约束、签名校验、幂等键和状态回查。
3. 将税务验真封装为可替换 provider，保存验真时间、外部单号、原始结果摘要、失败原因和人工复核记录；不把身份证、税号等敏感信息写入普通日志。
4. 化学品资料先建立版本模型：SDS/TDS 文档、语言/地区、发布/生效/到期时间、供应商、产品及批次关联、审核状态和替换关系；过期提醒进入现有任务/通知机制。
5. 根据目标法规再实现 GHS 分类/标签、仓储兼容性、禁限用、运输资料等规则；规则应有来源、版本、生效日期、测试样例和负责人，支持规则更新留痕。
6. 外部 API 调用使用超时、有限重试、签名/凭证托管、响应脱敏、对账补偿和人工异常队列。外部系统不可用时不得把“未确认”误标为“成功”。

### 验收标准

- 银行导入/API 的重复记录不会创建重复付款；流水状态可与系统付款状态核对。
- 外部支付或税务服务超时后，系统保留待确认状态并支持安全重试/人工核对。
- SDS/TDS 版本及有效期可追溯到关联产品/供应商，过期和缺失规则通过业务验收。
- 每个监管规则都有目标地区、规则版本、来源和业务负责人。

## 九、建议实施顺序

| 优先级 | 工作包 | 原因 | 完成条件 |
|---|---|---|---|
| P0 | 生产配置 fail-closed；迁移 runner/版本记录；备份恢复演练 | 关系到凭证安全和数据可升级、可恢复 | 危险配置拒绝启动；已有库可按序升级；恢复演练成功 |
| P1 | 登录防护与令牌撤销；幂等接口清单及 SSE 例外；MySQL 状态机/并发测试 | 关系到账号接管、重复写入和账实一致 | 安全/重复/并发验收矩阵通过 |
| P1 | 集中监控告警；后台任务运行记录与多实例协调 | 关系到服务出故障后能否发现、定位和恢复 | 告警演练、多实例任务演练通过 |
| P2 | 银行/税务接入、化学品法规能力 | 价值取决于目标客户、地区和已有系统 | 需求与数据源确认后逐个 provider/规则交付 |

**建议不要把 P2 的外部集成当作“生产安全门”的前置条件。** 单组织内部试点可以先用经审计的人工对账和合规资料流程；但必须明确系统状态的含义、人工职责和未自动核验的范围。

## 十、实施与交付约定

每个工作包按以下流程完成：

1. 形成接口/配置/数据迁移设计和风险清单。
2. 实现代码及迁移；旧数据变化必须有预检、备份与复核记录。
3. 补单元、集成、并发或故障测试；涉及 MySQL 锁和 DDL 时使用 MySQL 验证。
4. 在预发布环境部署并执行验收脚本。
5. 记录验证环境、配置版本、数据库版本、测试结果、未覆盖风险和回滚/恢复步骤。
6. 发布后观察错误率、任务状态、数据库和对象存储指标，达到预设观察期后再关闭发布任务。

本方案本身不代表以上工作已经完成；每项验收结果应以代码、测试、预发布演练或生产观测证据为准。
