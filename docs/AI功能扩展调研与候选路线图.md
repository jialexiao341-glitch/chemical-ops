# ChemicalOps AI 功能扩展调研与候选路线图

> 调研日期：2026-09-28。本文用于选择后续功能，不表示候选能力已经上线。商业产品信息来自厂商公开资料，开源项目用于参考业务流程或技术方案；具体效果仍需在 ChemicalOps 的数据和权限规则下验证。

## 1. 先看结论

ChemicalOps 已有受权限约束的业务问答、化学品资料问答、订单追溯、自然语言筛选、运营晨报、规则预警和经人工确认的采购申请草稿。下一阶段更值得做的是把 AI 放进一张具体单据或一条异常的处理过程：**整理证据 → 指出差异或影响 → 给出可核查的建议 → 由用户处理**。

建议优先评估三条产品线：

1. **质量验收助手**：核对检验报告、检测值、证书和验收记录；化工业务特色最鲜明。
2. **批次影响分析**：发现问题批次时，追踪库位、流水、领用和调拨，生成待核查清单。
3. **财务差异助手**：比较订单、收货、对账、发票和付款，定位差异及未结算原因。

若目标是最快做出可展示的闭环，先从“质量验收助手”的**人工上传报告、只读核对**版本开始。若目标是体现 ChemicalOps 的差异化，再做“批次影响分析”。

## 2. 现有基础与边界

以下按本仓库的[业务数据与 AI 联动路线图](业务数据与AI联动路线图.md)和[项目简介](../README.md)整理：

| 已有基础 | 目前仍缺少的环节 |
| --- | --- |
| 业务查询白名单、权限校验、来源记录、部分跨模块订单追溯 | 更多数据集的统一口径；复杂追问与生产角色权限矩阵验证 |
| 化学品资料解析、检索、章节引用 | 工作台附件入口；名称/别名到 CAS 的识别质量；文档版本差异核对 |

| 采购申请草稿预览与用户二次确认 | 将异常中的证据和建议带到草稿；其它业务草稿流程 |
| 验收结果、检测结果 JSON 和报告附件字段 | 产品/检测项目的标准值、单位和判定规则需进一步规范 |
| 订单、到货、库存、对账、发票、付款等单据链路 | 多单据差异视图；真实业务数据下的金额、数量和引用核对 |

目前的 [RAG 混合评估](evaluation/RAG混合评估报告-200条.md)中，149 条可回答题有 127 条召回全部指定证据；22 条失分中的 17 条在名称识别阶段未能定位化学品。**名称与别名解析应作为资料类新功能的前置修复**，否则新增 SDS 比对或附件问答也会继承这一问题。

## 5. 候选功能清单

“优先级”是基于当前项目的数据基础、业务辨识度和实现依赖作出的建议，并非市场产品效果排名。

| 候选功能 | 用户看到的结果 | 主要依赖 | 建议 |
| --- | --- | --- | --- |
| **A. 质量验收助手** | 报告原文、提取值、系统录入值和判定依据并排；标出缺项或冲突，生成结论草稿 | 报告附件入口；产品检测标准、单位及人工审核 | **P1** |
| **B. 批次影响分析与召回演练** | 从批次展示当前库位、历史流转、来源单据和待核查对象；导出待办清单 | 批次/流水来源关联完整性；领用和调拨去向 | **P1** |
| **C. 财务差异助手** | 订单、收货、对账、发票和付款的数量/金额差异表及未结算原因 | 币种、税额、部分收货/开票和作废口径 | **P1** |
| **D. 异常处置助手** | 打开临期、低库存或逾期异常后，看到来源、影响、负责人及可选动作 | 现有规则提醒与订单追溯；建议反馈记录 | **P1** |
| **E. SDS 版本与资料变更核对** | 新旧版本字段差异、原文页码、可能受影响的产品/批次 | 名称/别名解析修复；版本管理；权威判定规则 | **P2** |
| **F. 供应商履约画像与比价情景试算** | 价格、交期、短交、验收和异常记录的分项指标；调整权重后比较候选供应商 | 评分规则、可比产品和样本量下限 | **P2** |
| **G. 供应商变更影响分析** | 从报价或确认函提取变化，列出相关订单、库存和成本影响 | 文档字段提取；订单行级关联；人工确认 | **P2** |
| **H. 盘点差异与仓储作业解释** | 盘点前后数量、冻结/解冻及出入库流水时间线 | 来源单据覆盖率、不同单位处理 | **P2** |
| **I. 临期消耗与补货预测** | 在库、在途、历史消耗、预计缺口和预测误差一起展示 | 足够长的真实流水、稳定交期和单位换算规则 | **P3** |
| **J. 库位与作业建议** | 建议优先使用、调拨或调整库位，说明空间与作业收益 | 库位容量、距离、储存限制和兼容性规则 | **P3** |

P1 表示适合进入近期方案设计；P2 表示需要先补数据或界面；P3 表示依赖较长期的真实运营数据。P1 的四项也无需同时开发。

## 6. 三个适合先评审的最小版本

### 方案 A：质量验收助手

- **入口**：质量验收详情中的“核对报告”。
- **第一版流程**：用户选择有权限的报告 → 提取批次号、检测项目、数值、单位和结论 → 对照验收记录与已配置标准 → 显示原文位置和差异 → 检验员修改、确认并自行提交验收。
- **第一版范围**：先选一类常见报告和少量有明确标准的产品；只生成核对意见，不自动判定合格或放行库存。
- **验收指标**：关键字段准确率、原文定位正确率、漏报的关键冲突数、人工修改率与核对耗时。

### 方案 B：批次影响分析

- **入口**：库存批次或质量异常详情中的“查看影响范围”。
- **第一版流程**：输入批次号 → 固定只读查询来源到货/验收、当前余额、冻结状态及库存流水 → 绘制流转时间线 → 汇总系统中可见的待核查位置和记录。
- **第一版范围**：仅声称已记录在 ChemicalOps 内的去向；没有客户销售或系统外使用记录时明确标为“系统未记录”。
- **验收指标**：来源单据关联覆盖率、数量守恒校验通过率、权限隔离和人工复核一致率。

### 方案 C：财务差异助手

- **入口**：采购订单或对账单详情中的“核对差异”。
- **第一版流程**：按单据逐项比较订单、已验收收货、对账、已核验发票、已付款和结算状态 → 用规则算出差额 → AI 解释阻塞环节并给出可打开的来源。
- **第一版范围**：同币种逐笔核对；不同币种不合并；不自动通过发票、审批或登记付款。
- **验收指标**：金额与数量差异的数据库复核一致率、遗漏环节数、错误引用数和人工核对时间。

## 7. 建议实施顺序

1. **共同基础**：修复化学品名称/别名识别；补工作台附件选择和页/段落引用；为候选功能准备固定业务样本、权限矩阵和数值期望值。
2. **选择一个 P1 闭环**：优先做质量验收助手，或根据目标用户选择批次影响分析。先只读核对与证据展示，再增加人工确认后的草稿或任务。
3. **横向扩展**：把统一的“来源卡片、差异预览、确认与审计”组件复用到财务、供应商和异常中心。
4. **积累真实数据后**：再验证消耗预测、智能补货及库位建议的收益和误差。

所有候选功能都应保持现有权限、业务校验和审计约束。数值计算、阈值和单据状态由确定性服务给出；模型负责解释、整理文档和提出候选建议。对于化学品储存、质量放行及付款等决定，界面应展示依据并保留相应岗位的确认步骤。

## 8. AI 结果应该出现在哪里

AI 能力不应只局限在 AI 工作台，也不应把每次回答都推送给用户。建议按用户正在做的事分成三个触达位置：

| 触达位置 | 适合承载的内容 | 建议交互 |
| --- | --- | --- |
| **AI 工作台** | 自由提问、跨模块业务查询、化学品资料问答、运营晨报和历史会话 | 用于发现能力和探索问题；查询结果展示口径、引用和可打开的业务来源。普通问答默认只保留在会话中，不主动通知。 |
| **业务单据页面** | 与一张验收单、一个库存批次、一张对账单或一条异常直接相关的分析 | 从单据内启动对应助手，在当前页面或侧栏显示证据、差异和建议；用户可回到原业务流程继续核查或处理。 |
| **通知与待办** | 有明确负责人、需要跟进且存在可跳转业务对象的事项 | 推送简短摘要、紧急程度和业务页面入口；完整分析、来源依据和确认操作留在对应单据或待办详情中。 |

### 推送边界

- 不推送普通聊天回答、每次查询结果或仅供参考的建议，避免通知噪声。
- 仅当规则或业务事件发现需要关注的事项，且能够确定接收角色或负责人时，才考虑生成待复核提醒。
- 通知说明发生了什么以及为什么需要关注；AI 生成的解释和候选处理办法应标明依据，并由用户在业务页面核对。
- 质量放行、库存处置、付款和审批等操作继续由原业务流程及相应岗位确认，不能因收到通知而自动执行。
- 推送和待办应沿用现有权限校验、通知记录及审计要求；用户打开详情时仍按当前权限读取业务数据。

### 结果留存建议

普通问答继续作为个人会话历史保存。与业务单据绑定、可能影响后续判断的分析，建议保存关联对象、使用的数据口径与时间、来源记录、AI 建议以及用户的复核结论，便于回看和审计；AI 结论不应覆盖或替代业务单据中的正式字段与状态。推送只作为提醒和入口，不应成为唯一的结果存放位置。

以质量验收助手为例：检验员从验收单启动“核对报告”，在验收上下文查看提取值、原文位置、系统录入值和标准差异；发现需要处理的冲突时，再向负责检验员或质量角色发待复核提醒。提醒跳回该验收单，用户在那里完成判断。运营晨报则继续由工作台生成，用户确认接收范围后再推送。

当前实现与规划边界：AI 工作台已有普通问答、业务查询、自然语言筛选、采购申请草稿预览和运营晨报入口；晨报支持用户确认接收角色后推送。其它候选助手的单据内入口、业务关联分析留存及事件驱动通知属于后续建设，不代表已经上线。

建议落地顺序：先在质量验收单内提供按需启动和结果复核；之后为确有时效要求的质量异常或批次风险增加定向待办/通知；最后再把通用的来源展示、结果留存和复核状态复用到财务差异及异常处置场景。

### 质量验收助手首版进度（2026-09-28）

**状态：首版已接入质量验收流程。**验收列表和结果抽屉提供“核对报告”入口，可上传并关联报告、查看已有附件，并启动只读核对。系统提取报告中的批次号、检测项目、数值和原文引句，检查原文定位；后端对照到货批次及验收记录中的检测结果 JSON，标出一致、差异、缺项和批次不符。核对后，有原文依据的值可作为候选内容带入验收录入表单，由检验员修改并自行提交；已有检测结果不会被候选值覆盖。

报告上传、关联、查看和核对接口已接入现有文件权限；检验员可处理自己负责验收单的报告。三份流程报告已关联到本地开发库的 `QA-26001`、`QA-26002`，覆盖批次核对、项目一致、结果缺项和多份报告补充核对；可从项目根目录运行 `scripts/run_quality_report_flow.py` 重跑关联与核对。

首版限制：产品检测标准尚未结构化配置，因此系统不能判定指标合格；项目别名仍需人工确认；扫描件依赖已启用的文档识别服务。核对结果按需生成并显示在验收页，尚未作为业务关联的历史分析记录保存，也不会因差异自动推送通知。流程报告中的检测值是拟制内容，用于验证解析和核对路径，不是实验室实测结果或放行依据。完整数据说明见 [质量报告流程材料](quality-reports/README.md)。

**下一步：**用经过审核的真实检验报告和对应产品标准验证提取与判断口径；之后再设计核对结果留存、跨负责人复核权限及异常待办推送。

### 开发环境业务记录整理（2026-09-28）

质量验收列表中的批次结论，以及采购、询价、到货、库存和财务关联记录已清理生成器标记和占位式备注，并按现有状态改写业务文案。存量修订前保存了本地数据库快照；数据之间的关联、数量和业务状态保持原样。未来扩充数据使用统一编号和文案函数。

这些本地业务记录仍是用于流程验证的合成数据，界面保留开发环境提示；自然化文案不代表实际交易、检验、库存或资金流水。历史 AI 会话保留原文。

## 9. 评审时需要决定的事

1. 首位使用者是谁：检验员、仓管、采购员还是财务人员？
2. 第一版使用演示数据还是准备一批脱敏的真实单据和报告？
3. 最想改善哪个指标：核对耗时、异常处理时长、临期损耗、对账差错，还是供应商选择质量？
