# 运行监控与后台任务

## 部署前升级

任务历史表由迁移 `023_scheduler_job_runs` 创建。发布新版本前，在目标环境执行统一迁移流程：

```powershell
uv run python scripts\migrate_database.py upgrade
```

API 启动会校验迁移台账；未应用 `023` 时服务不会报告就绪。

## 多副本调度

持续运行的 `scripts/run_scheduler.py` 使用 MySQL 命名锁 `chemicalops_scheduler_leader`。同一数据库只能有一个实例持锁并执行周期任务；其他实例等待锁释放后接管。进程正常退出会显式释放锁，连接异常断开时 MySQL 会释放该会话的锁。该协调只覆盖此脚本中的定时执行，手工 `POST /api/v1/jobs/overdue-scan` 仍可独立触发；异常来源唯一约束和服务层防重负责避免重复创建同一活动异常。

建议将调度器作为独立进程部署，与 API 副本分开伸缩。多副本同时运行调度器时，备用实例会持续等待主锁；使用 `--once` 时如果锁已被占用，该次调用会退出而不会排队执行。

每轮周期执行会在 `scheduler_job_runs` 写入一条记录。状态为 `RUNNING`、`SUCCEEDED` 或 `FAILED`；记录包括运行 ID、尝试次数、开始/结束时间、扫描/创建数量和最终异常类型。查询最近运行记录：

```http
GET /api/v1/jobs/runs?limit=50
```

该接口要求 `operations.exceptions.read` 权限，最多返回 200 条。进程在运行中崩溃时，记录会保留为 `RUNNING`，可结合开始时间和调度周期识别中断轮次。

## Prometheus 指标

`GET /metrics` 暴露当前 API worker 的请求计数及延迟直方图。每个 worker 都有独立的进程内计数器；Prometheus 应发现并分别抓取每个 API 副本的地址，避免只经负载均衡器抓一个共享地址。以服务或路由聚合：

```promql
sum by (method, path, status) (rate(chemicalops_api_requests_count[5m]))
```

P95 延迟：

```promql
histogram_quantile(
  0.95,
  sum by (le, method, path) (
    rate(chemicalops_api_request_duration_seconds_histogram_bucket[5m])
  )
)
```

直方图使用固定秒数分桶，覆盖 5ms 到 10s，并提供 `+Inf` 桶；标签仅包含 HTTP 方法、路由模板和状态码。未匹配路由统一标为 `unmatched`，避免把单据 ID 等动态路径值写入指标标签。任务运行历史是持久数据；API 请求指标在进程重启后会重置，由 Prometheus 保留历史序列。

## 当前边界

- 后台定时任务依赖 MySQL 命名锁，因此调度器要求 MySQL 8。连接断开后的锁释放由 MySQL 会话管理。
- 本地指标不会跨进程自行存储；多副本汇总由 Prometheus 抓取和 PromQL 聚合完成。目标环境仍需配置副本发现、告警接收人和告警规则。
- 任务历史接口只展示最近记录；失败详情保存异常类型，不保存异常正文、SQL 参数或请求内容。
- 上线验收仍需在目标部署环境验证主调度实例故障后备用实例接管，并确认 Prometheus 抓取到全部 API 副本。
