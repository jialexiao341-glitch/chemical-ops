## 冻结门禁：保持拦截，待批准后迁移

`scripts/check_evaluation_fixtures.py` 与 `offline-guards-v1-manifest.json` 均保持原样；未创建新的 manifest，未降低失败退出码，未跳过门禁用例。

独立核对发现：

- 校验器写死的 v1 manifest SHA256 为 `c417d355a8a6499c09c76d625579128dc640e93b0fac9877ded46f5557b1cc80`。
- 提交 `4f1b115` 中的 manifest 字节 SHA256 已是 `3f58382fb047f93ab562883a8bc60f1a82b9a6051b0f78ec2c74856c55b31d05`，当前文件归一化 LF 后与该提交相同。此锚点不一致不是本轮新增。
- 数字样本 JSON 的差异有 CRLF/LF 因素；`scripts/agent_evaluation_data.py` 的内容相对于冻结版本确实变化：新增化学品身份、询价单位/数量、税费口径字段，以及报价 15/16。相关变化已由后续报价能力提交引入，但 v1 冻结清单没有同步。
- 本轮还修正了评测变体 INSERT 和评分器独立预期；这些受审阅的代码修改也必须反映在新的基线版本中，不能假装与旧文件哈希相同。

**拟提交用户批准的具体方案**（尚未应用）：

1. 保留 v1 作为历史记录，新增 `offline-guards-v2-manifest.json`，并更新校验器固定指向的版本和静态 manifest 哈希锚点。
2. v2 固定覆盖以下 5 个文件：`offline-numeric-associations-v1.json`、`agent-business-v1-cases.json`、`scripts/agent_business_cases.py`、`scripts/agent_evaluation_data.py`、`scripts/evaluate_agent_tasks.py`。前两项的题目与数字预期内容不更换，仍为 12 条数字关联样本、120 个业务场景，另保留 20 个 RFQ 控制场景。
3. 使用明确的文本摘要规则：仅把 CRLF 转为 LF，再计算 SHA256；不删除空白、不重排 JSON、不忽略尾部空行或业务数值，运行时不自动接受文件变化或重建哈希。
4. 为这 5 个文件和 manifest 分别保留/增加篡改后必须失败的用例，并增加仅换行符变化可以通过的用例；全部通过后再跑全量回归。

自动审批拒绝了切换新 manifest 并重算哈希的动作，理由是可能将未经独立审阅的漂移纳入基线、削弱原有完整性校验。审批拒绝后没有采用其他方式修改门禁。需要用户审核本记录和对应代码差异并明确批准后，才能应用上述方案。
